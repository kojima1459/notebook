# 委任(難易度で振り分ける)

## 1. 難易度の物差し(10段階)

| 段 | 目安 | 担当 | 例 |
|---|---|---|---|
| 1〜4 | 仕様が1枚で閉じる・正解が機械的に決まる・壊しても検問で必ず見つかる・軽い配線 | **Gemini 3.1 Pro**(`gemini-3.1-pro-preview`。既定。クセは強いが Sonnet 級。**軽いタスクは全部こいつ**) | 仕様どおりの新規モジュール起草／純関数テストの起草／文書の下書き(使い方・手順・メール・Teams)／ログ・CSV の整形・集計／翻訳・言い換え／表の書き起こし／既存コードの要約・索引作り／3ストリーム目のレビュー(根拠つき所見だけ採る)／config の説明文・modules.json の note の起草／フロントエンド寄りの雛形(HTML/CSS/SVG) |
| (1〜2 で速さ優先) | 数秒で返ってほしい雑務 | Gemini 3.8 flash(`--model gemini-3.8-flash`) | 1行の言い換え・件数集計・整形 |
| 5〜7 | 既存コードの縫い目を跨ぐ・複数ファイルの配線・config/登録の追従・Fix 波 | **Sonnet** | 配線(1〜数行×5ファイル)／Fix 波(裁定表どおり)／仕様突合レビュー(班B)／文書の反映 |
| 8〜9 | 壊しにいく・設計の穴を見つける・実機事故の原因調査 | **Opus** | 敵対的レビュー(壊す班・2周目 Fix 検証)／原因が一意に定まらない調査 |
| 10 | 裁定・仕様・検収・push・ユーザーへの説明・**司令塔と PO の役割そのもの** | **Fable(司令塔)** | spec/HANDOFF/CLAUDE.md／マイクロ修正／LibreOffice 検問(直列)／最終検問・検品と手直し／配布 |

Gemini 3.1 Pro の実測(2026-09-06): 同じキーで呼べる。小さな入力でも約40秒かかる(3.8 flash は1〜4秒)ので、**まとめて1回で頼む**(細切れに何度も呼ばない)。

迷ったら1段上へ倒す。**Gemini に出すのは「文字列を入れて文字列が返れば済む」仕事だけ**(ツールも git も走らない)。**敵対的レビューの後の最終検証・最終検問・最終検品と、そこで見つかったエラーの手直しは委任しない=Fable 自身が責任を持って行う**(ユーザー裁定 2026-09-06)。Gemini は「パシリ」: 難易度の見立てと仕事の切り出しは司令塔の職務であり、Gemini の得意(文字列の生成・整形・下書き・フロントエンド寄りの雛形)に合わせて切り出す。

## 2. Gemini の呼び方

```bash
python3 tools/gemini_worker.py <prompt.txt> <out.txt>                 # 既定 gemini-3.1-pro-preview
python3 tools/gemini_worker.py <prompt.txt> <out.txt> --model gemini-3.8-flash   # 速さ優先の雑務
```
- キーは環境変数 `GEMINI_API_KEY` か `~/.gemini_key`(順に探す)。**リポジトリに置かない・値を出力しない**。無ければ「呼べない」とユーザーへ言い、Claude 側(Sonnet)で代替する。
- プロンプトは1ファイルに全部入れる: 役割1行 → 出力形式(区切りマーカー・前置き禁止) → 必須ルール(CLAUDE.md §10/§11 の該当箇所を貼る) → 仕様書全文 → 参考ファイル全文(`nl -ba` で行番号付き)。**Gemini はリポジトリを見られない**ので、必要なものは全部貼る。
- 複数ファイルを書かせるときは `=====FILE <path>=====` … `=====END=====` で区切らせ、Python で分割して置く。

## 3. Gemini の成果の受け取り方(ここを省くと事故る)

1. **司令塔が全文を読んで検収する**(R38 で起草2本に3点修正: 固定長配列の引数渡し／ハンドラ内の `On Error Resume Next`／ログ引数)。
2. **lint → LibreOffice compile → pure** を通す(いつもの検問)。
3. **Gemini の「測った」「確認した」は信じない**: git・ファイル計測・実行はできないのに「HEAD xxx」「18,348 字」「実測 5ms」と**推定を事実のように書く**。数値・行番号・HEAD はすべて司令塔が実測し直す。レビュー所見は**根拠の行を自分で開いて再現できたものだけ**採る。
4. 文書の下書きは `ground-truth` の典拠(出荷 config の実測値・実装の文字列)に照らしてから反映する。

## 4. 波の組み方(テンプレ)

1. 司令塔が spec を書く(契約=公開 API・手順・config・配線箇所・テスト観点)。
2. **並行投入**: Gemini(新規モジュール＋純テストの起草)‖ Sonnet(配線・config・登録)。触るファイルを完全に分ける。
3. 司令塔: 検収 → lint → LO → 検問コミット。
4. **並行投入**: Opus(壊す班)‖ Sonnet(仕様突合)‖ Gemini(3ストリーム目)。
5. 司令塔が裁定表(spec §レビュー)→ Sonnet が Fix 波 → Opus の2周目 → final-gates。
