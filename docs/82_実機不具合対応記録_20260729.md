## 1. Excel: `'Open' メソッドは失敗しました`（解消済み）

### 原因

07-28 に追加した `Password:=` / `WriteResPassword:=` 引数。
暗号化ブックでパスワード入力ダイアログが出て固まるのを防ぐための引数
（レビュー M-11）だが、環境によっては **保護されていない普通のブックまで
開けなくする**。

### 直し方

`OpenForExtract()` で「引数つき → 引数なし」の順に試す。
どちらで通ったかをセッション中おぼえて、次から無駄打ちしない。
通った方は `usage_log` に `excel_open_mode` として1行残す。

**なぜこの方法か**: どちらか一方を選ぶ判断を、開発側の推測ではなく
実機の挙動に委ねた。M-11 の意図（ダイアログで固まらせない）は
「引数つきで失敗 → 引数なしでも失敗 → 取込失敗として返す」で保たれている。

### 確認

実機ログに以下が出たことを確認済み。

```
excel_open_mode: この端末ではパスワード引数なしでブックを開けました
```

## 2. Word: err#462（未解消・原因特定中）

### 現状

`.doc` / `.pdf` が全滅。エラーは
`実行時エラー 462: リモート サーバーがないか、使用できる状態ではありません`。

07-29 に「非表示+パスワード無効化 → 非表示 → 表示」の3段フォールバックを
実装したが、実機ログに **`word_open_mode` が1行も出なかった**。
つまり最後の砦である「表示（Visible=True）」まで降りても失敗している。

これは「07-28 に `Visible=False` へ戻したのが原因」という当初の見立てが
**誤りだった**ことを意味する。Visible の有無は原因ではない。

### 今回入れたもの（原因特定のため）

推測で直すのをやめ、**どのCOM呼び出しで落ちたか**をログに残す。

| 段階名 | 対応する呼び出し |
|---|---|
| `Word起動` | `CreateObject("Word.Application")` |
| `表示切替` | `word.Visible` / `word.DisplayAlerts` |
| `文書オープン` | `word.Documents.Open(...)` |
| `ページ数取得` | `doc.ComputeStatistics(2)` |
| `本文取り出し` | `doc.GoTo` / `Range.Text` |
| `後始末` | `doc.Close` / `word.Quit` |

- `err_log` の詳細が `[Word起動/開き方1] ...` の形になる
- 全モード失敗時に `usage_log` へ `word_open_fail` を1行出す
- **`Word起動` で落ちているなら、残り2モードは試さず即座に打ち切る**
  （開き方を変えても届かないため。1ファイルあたり約5秒の無駄を削る）
- err#462 の文言を「Wordがインストールされているか」「手で起動できるか」
  「セキュリティ製品が他アプリからのWord操作を止めていないか」を
  確かめる案内文に差し替えた

### 次に見るところ

実機ログの段階名で切り分ける。

| 段階名 | 意味 | 確認すること |
|---|---|---|
| `Word起動` | Word のプロセスが起動できていない | Word が入っているか／手で起動できるか／セキュリティ製品のブロック |
| `文書オープン` | Word は起動したがファイルを開けない | 保護ビュー、ファイルブロック設定、そのファイル固有の破損 |
| `ページ数取得` 以降 | 開けたが途中で Word が落ちた | ファイル固有の問題の可能性が高い |

## 3. 大きな `.xlsx` で「メモリが不足しています」

### 原因

`ExtractSheetText` が `used.Value` で **シート全体を1回で読んでいた**。
UsedRange が 100万行×数十列まで伸びた業務ブック（書式や空白セルの残骸で
簡単にそうなる）では Variant 配列だけで数百MB〜GB級になり、
32bit Excel の 2GB 空間を使い切って落ちる。
しかも落ちた時点でそのファイルの取込は全滅する。

### 直し方

**行ブロック単位の一括読み**に変えた。

```
MAX_CELLS_PER_READ   = 100,000  1回の一括読みの上限セル数
MAX_CELLS_PER_SHEET  = 400,000  1シートから取り込む上限セル数
MAX_COLS_PER_SHEET   = 256      横方向の上限
MAX_CHARS_PER_SHEET  = 300,000  1シートの本文の上限文字数
```

- COM往復は「行数 ÷ ブロック行数」回で済む（1万行でも数十回）
- 1回あたりの確保量に上限がかかる
- ブロック読みに失敗したらブロックを半分にして1回だけ再試行
- それでも駄目ならそのブロックだけ諦める（5回失敗でシートを打ち切り）
- 上限で切った場合は本文末尾に `[※このシートは大きいため一部のみ取り込みました]`
  を入れる

**なぜこの方法か**: MASTER_SPEC §12「ループ内Range直接アクセス禁止」の
狙いは *セル1個ずつのCOM呼び出しを避けること* であって、
*サイズ無制限の一括読みを保証すること* ではない。
ブロック読みは §12 の狙いを満たしたまま、確保量に上限をかけられる。

セル数だけでなく文字数の上限も置いたのは、1セルに数千文字ある備考欄の
シートではセル数が少なくてもメモリを使い切るため。埋め込み費用の歯止めも兼ねる。

## 4. `err#9 インデックスが有効範囲にありません` でファイル全体が取込失敗

### 原因

`ChunkAllPagesStructured` のページ単位ループに保護がなく、
1ページ（1シート）の処理で実行時エラーが出ると **ファイル全体が失敗**していた。
88チャンク取れるはずの資料が丸ごと0件になる。

### 直し方

ページ単位で `On Error GoTo SkipPage` を張り、落ちたページだけ飛ばす。

- 組み立て途中のブロックは捨てる（壊れたページの続きを次ページへ繋ぐと内容が混ざる）
- 飛ばした数を `modChunker.SkippedPageCount()` で取れるようにする
- `modShelf.IngestFile` がそれを読み、0でなければ `usage_log` へ
  `chunk_skipped_pages` を1行残す

**なぜこの方法か**: 資料は「全部入るか、全部入らないか」ではない。
読めたページは入れる方が利用者の役に立つ。
ただし**黙って減らすと誰も気づけない**ので、必ずログに残す
（「88チャンク入るはずが70だった」を後から追える）。

## 5. 予防として入れたもの

### 5.1 vba_lint の静的チェック追加

実機のコンパイルエラーは LibreOffice のコンパイルチェックでは
検出できない（`Option VBASupport` が名前解決を遅延するため）。
同じ型の事故を二度起こしたので、静的側で止める。

| チェック | 検出するもの |
|---|---|
| `check_module_level_refs` | モジュール分割で置き去りにされたモジュールレベル定数・変数への参照 |
| `check_undefined_proc_refs` | 同じく置き去りにされたヘルパープロシージャへの参照 |
| モジュールレベル宣言の位置 | 宣言がプロシージャ定義より後にある（実機コンパイルエラー） |
| `check_cp932_safe` | 実行文中の CP932 外文字（VBEへの注入時に `?` へ化ける） |
| モジュール容量 WARN | 28,000字で警告（上限30,000字の手前で気づく） |
| `check_handler_exit` | エラーハンドラを `Resume` 以外で抜けている（§5.2） |

本記録の作業中、実際に以下を検出して未然に防いだ。

- `modExtractorExcel` の新規定数4本が宣言部より後ろにあった（実機コンパイルエラー）
- `modExtractorWord` のログ文に `〜`(U+301C) が入っていた（CP932外・`?` に化ける）

### 5.2 エラーハンドラの抜け方（`Resume` を使う）

§4 の修正を書いた直後に、その修正自体が**効かない**書き方だったことに気づいた。

VBAは「エラーハンドラ実行中」という状態を持ち、これを解除できるのは
**`Resume` と、プロシージャを抜けること**だけである。
`On Error GoTo 0` はトラップの登録を消すだけで、この状態は解除しない。

```vba
For p = ...
    On Error GoTo SkipPage
    ...処理...
    GoTo NextPage
SkipPage:
    skipped = skipped + 1
    On Error GoTo 0      ' ← これでは抜けられない
NextPage:
Next p
```

この書き方だと **1ページ目の失敗は拾えるが、2ページ目の失敗は
`SkipPage` へ飛ばずに呼び出し元へ突き抜ける**。
「1ページの失敗で資料全体を失わない」ための修正が、2ページ目以降で効かない。
しかもテストで1件しか壊さなければ、通ってしまう。

正しくは `Resume NextPage`。

同じ形が既存コードにも5か所あった（`Failed:` → `Finish:` の落とし込み）。
いずれも直後にプロシージャが終わるため実害は出にくいが、
後始末ブロックで起きたエラーが呼び出し元へ素通りする
（フォルダ同期なら残りのファイルが中断する）ので、まとめて `Resume` に直した。

| 場所 | ハンドラ |
|---|---|
| `modShelf.IngestFile` | `Failed:` → `Resume Finish` |
| `modShelfSync.SyncNow` | `Failed:` → `Resume Finish` |
| `modAsk`（回答本体） | `Fail:` → `Resume Done` |
| `modEmbed.EmbedPending` | `EscOrErr:` → `Resume AfterLoop` |
| `modEnrich.EnrichPending` | `EscOrErr:` → `Resume AfterLoop` |

lint に `check_handler_exit` を追加して、同じ書き方を今後は WARN で止める。

### 5.3 `On Error GoTo 0` の誤用防止

`modShelf.IngestFile` に一時的な `On Error Resume Next` を足す際、
`On Error GoTo 0` ではなく `On Error GoTo Failed` で戻している。
`0` にすると**関数の Failed ハンドラごと解除**され、以降の実行時エラーが
利用者の画面へ素通りする（レビュー H-3 と同じ型の事故）。

## 6. 実機テスト依頼の判断

**`.doc` / `.pdf` が取り込めることを確認できるまで、同僚への依頼は止めること。**

取込は本ツールの入口で、ここが通らないと以降の機能（検索・回答・出典・配信）を
一切評価できない。依頼した側の時間を無駄にするだけでなく、
「使えないツール」という第一印象だけが残る。

Excel の取込は解消済みなので、`.xlsx` だけで一通り触ることは可能。
ただし社内資料の主力は PDF と Word であり、それが通らない状態での
評価には意味がない。

### 依頼前に自分の PC で確認すること

1. `.doc` を1つ取り込む → 成功するか
2. `.pdf` を1つ取り込む → 成功するか
3. 失敗した場合、`usage_log` の `word_open_fail` と
   `err_log` の `[段階名/開き方N]` を確認する
