## 1. Excel: `'Open' メソッドは失敗しました`（解消済み）

### 原因

07-28 に追加した `Password:=` / `WriteResPassword:=` 引数。
暗号化ブックでパスワード入力ダイアログが出て固まるのを防ぐための引数
（レビュー M-11）だが、環境によっては **保護されていない普通のブックまで
開けなくする**。

### 直し方

`OpenForExtract()` で「引数つき → 引数なし」の順に試す。
どちらで通ったかをセッション中おぼえて、次から無駄打ちしない。
通った方は `usage_log` に `excel_open_mode` として1行残す。

**なぜこの方法か**: どちらか一方を選ぶ判断を、開発側の推測ではなく
実機の挙動に委ねた。M-11 の意図（ダイアログで固まらせない）は
「引数つきで失敗 → 引数なしでも失敗 → 取込失敗として返す」で保たれている。

### 確認

実機ログに以下が出たことを確認済み。

```
excel_open_mode: この端末ではパスワード引数なしでブックを開けました
```

## 2. Word: err#462 ― 真因は「後始末の失敗が原因を上書きしていた」

### ログから確定したこと（推測ではない）

07-30 のログにこう出ていた。

```
E0302  modExtractor.ExtractFile
  ...企画書.pdf : err#462: リモート サーバーがないか、使用できる状態ではありません。 [localcopy=ok]
```

**この書式が決定的な証拠**である。`.pdf` の取込が普通に失敗したなら、
`ExtractPdfWithFallback` が組む `errDetail = "Word: … / Acrobat: …"` の形で出るはずだった。
そうではなく `err#462: … [localcopy=ok]` ――
これは `ExtractFile` 自身のエラーハンドラ `ExtractFailed:` の書式である。

つまり **抽出アダプタは False を返して終わったのではなく、例外で抜けていた**。

### なぜ例外で抜けたか

VBA には **有効(enabled)なハンドラ** と **稼働中(active)なハンドラ** の区別がある。
ハンドラへ飛んだ瞬間から `Resume` / `Exit` までの間に起きたエラーは、
**そのプロシージャでは一切捕まえられず呼び出し元へ投げ返される**。
`On Error Resume Next` を書いても効かない。

`modExtractorWord.TryExtractOnce` はこうなっていた。

```vba
Failed:
    errDetail = 本当の原因            ' ← 正しく作っている
    If Not doc Is Nothing Then
        On Error Resume Next          ' ← 稼働中なので無効
        doc.Close 0
        On Error GoTo 0
    End If
    If Not word Is Nothing Then
        On Error Resume Next          ' ← 同じく無効
        word.Quit 0                   ' ← 死んだWordを叩いて err#462
        On Error GoTo 0
    End If
    TryExtractOnce = False            ' ← ここへ到達しない
```

この結果、

1. **本当の最初のエラーは捨てられ**、後始末の err#462 だけがログに残った
2. `Extract` の**開き方フォールバック（3通り）は一度も走っていなかった**
   ―― だから `word_open_mode` が1行も出なかった
3. **PDF の Acrobat フォールバックも一度も走っていなかった**

07-29 に入れた「開き方を3通り試す」修正は、**到達不能なコード**だった。
「Visible が原因ではなかった」のではなく、**Visible=True を試してすらいなかった**。

### 同時に分かること

`word` が `Nothing` なら後始末は何も叩かないので上書きは起きない。
上書きが起きていた以上、**`CreateObject("Word.Application")` は成功している**。
つまりこの端末では **Word は起動するが、その直後に死ぬ／届かなくなる**。

### 直し方

**(a) 後始末を別 Sub（`Cleanup`）へ切り出した。**
呼ばれた側は新しいエラー文脈を持つので、その中の `On Error Resume Next` は正しく働く。
これで本当の原因が `errDetail` として返り、フォールバックが実際に走る。

**(b) 起動しない選択肢を追加した（開き方4 = 相乗り）。**
自分で起動した Word が使えない環境（ライセンスの初回起動待ち、EDR/DLP が Office の
子プロセス起動を止める等）は実在する。`GetObject(, "Word.Application")` で
**すでに開いている Word へ相乗り**する。

| 開き方 | 内容 |
|---|---|
| 1 | 自分で起動（非表示）+ パスワード引数 |
| 2 | 自分で起動（非表示） |
| 3 | 自分で起動（表示） |
| 4 | **起動中の Word へ相乗り（GetObject。自分では起動しない）** |

- 相乗り先は利用者の Word なので **`Quit` しない**（編集中の Word を閉じたら大事故）。
  表示状態も触らない。`AutomationSecurity` を変えたら必ず元へ戻す。
- 起動そのものに失敗したときは 2・3 を試すのは無駄なので **4 へ直行**する。
- 開き方4で「Word が1つも開いていない」(err 429) なら、
  「Word を開いたままもう一度お試しください」と案内する。

**(c) どの COM 呼び出しで落ちたかを段階名で記録する。**

| 段階名 | 対応する呼び出し |
|---|---|
| `Word起動` | `CreateObject` / `GetObject` |
| `表示切替` | `word.Visible` / `word.DisplayAlerts` |
| `文書オープン` | `word.Documents.Open(...)` |
| `ページ数取得` | `doc.ComputeStatistics(2)` |
| `本文取り出し` | `doc.GoTo` / `Range.Text` |
| `後始末` | `Cleanup` |

`err_log` の詳細が `[文書オープン/開き方2] …` の形になり、
全モード失敗時は `usage_log` に `word_open_fail` が1行出る。

### 同じ誤りが全体で 57 箇所あった

このハンドラの書き方は 1 箇所の凡ミスではなく、コードベース全体の癖だった。
lint に検査（`check_resume_next_inside_handler`）を足して洗い出したところ
**36 ファイル 57 箇所**。全て機械的に同じ形へ直した。

```vba
Failed:
    Dim failDesc As String: failDesc = Err.Description   ' Resume で Err は消える
    Resume FailedCleanup
FailedCleanup:
    On Error Resume Next          ' ハンドラを抜けたのでここからは有効
    ...従来の後始末...
```

`Finish:` / `Done:` のように**正常系からも落ちてくるラベル**は、
そのまま `Resume` を置くと正常終了時に**実行時エラー20**になる。
該当箇所はラベルの直前に `GoTo` を入れて正常系が `Resume` を跨ぐようにし、
この罠も lint（`check_resume_on_fallthrough_label`）で止めるようにした。

## 3. 大きな `.xlsx` で「メモリが不足しています」

### 原因

`ExtractSheetText` が `used.Value` で **シート全体を1回で読んでいた**。
UsedRange が 100万行×数十列まで伸びた業務ブック（書式や空白セルの残骸で
簡単にそうなる）では Variant 配列だけで数百MB〜GB級になり、
32bit Excel の 2GB 空間を使い切って落ちる。
しかも落ちた時点でそのファイルの取込は全滅する。

### 直し方

**行ブロック単位の一括読み**に変えた。

```
MAX_CELLS_PER_READ   = 100,000  1回の一括読みの上限セル数
MAX_CELLS_PER_SHEET  = 400,000  1シートから取り込む上限セル数
MAX_COLS_PER_SHEET   = 256      横方向の上限
MAX_CHARS_PER_SHEET  = 300,000  1シートの本文の上限文字数
```

- COM往復は「行数 ÷ ブロック行数」回で済む（1万行でも数十回）
- 1回あたりの確保量に上限がかかる
- ブロック読みに失敗したらブロックを半分にして1回だけ再試行
- それでも駄目ならそのブロックだけ諦める（5回失敗でシートを打ち切り）
- 上限で切った場合は本文末尾に `[※このシートは大きいため一部のみ取り込みました]`
  を入れる

**なぜこの方法か**: MASTER_SPEC §12「ループ内Range直接アクセス禁止」の
狙いは *セル1個ずつのCOM呼び出しを避けること* であって、
*サイズ無制限の一括読みを保証すること* ではない。
ブロック読みは §12 の狙いを満たしたまま、確保量に上限をかけられる。

セル数だけでなく文字数の上限も置いたのは、1セルに数千文字ある備考欄の
シートではセル数が少なくてもメモリを使い切るため。埋め込み費用の歯止めも兼ねる。

## 4. `err#9 インデックスが有効範囲にありません` でファイル全体が取込失敗

### 原因

`ChunkAllPagesStructured` のページ単位ループに保護がなく、
1ページ（1シート）の処理で実行時エラーが出ると **ファイル全体が失敗**していた。
88チャンク取れるはずの資料が丸ごと0件になる。

### 直し方

ページ単位で `On Error GoTo SkipPage` を張り、落ちたページだけ飛ばす。

- 組み立て途中のブロックは捨てる（壊れたページの続きを次ページへ繋ぐと内容が混ざる）
- 飛ばした数を `modChunker.SkippedPageCount()` で取れるようにする
- `modShelf.IngestFile` がそれを読み、0でなければ `usage_log` へ
  `chunk_skipped_pages` を1行残す

**なぜこの方法か**: 資料は「全部入るか、全部入らないか」ではない。
読めたページは入れる方が利用者の役に立つ。
ただし**黙って減らすと誰も気づけない**ので、必ずログに残す
（「88チャンク入るはずが70だった」を後から追える）。

## 5. 予防として入れたもの

### 5.1 vba_lint の静的チェック追加

実機のコンパイルエラーは LibreOffice のコンパイルチェックでは
検出できない（`Option VBASupport` が名前解決を遅延するため）。
同じ型の事故を二度起こしたので、静的側で止める。

| チェック | 検出するもの |
|---|---|
| `check_module_level_refs` | モジュール分割で置き去りにされたモジュールレベル定数・変数への参照 |
| `check_undefined_proc_refs` | 同じく置き去りにされたヘルパープロシージャへの参照 |
| モジュールレベル宣言の位置 | 宣言がプロシージャ定義より後にある（実機コンパイルエラー） |
| `check_cp932_safe` | 実行文中の CP932 外文字（VBEへの注入時に `?` へ化ける） |
| モジュール容量 WARN | 28,000字で警告（上限30,000字の手前で気づく） |
| `check_handler_exit` | エラーハンドラを `Resume` 以外で抜けている（§5.2） |
| `check_resume_next_inside_handler` | ハンドラ稼働中の `On Error Resume Next`（無効なのに保護しているつもりになる。§2） |
| `check_resume_on_fallthrough_label` | 正常系からも落ちてくるラベルの `Resume`（実行時エラー20） |

本記録の作業中、実際に以下を検出して未然に防いだ。

- `modExtractorExcel` の新規定数4本が宣言部より後ろにあった（実機コンパイルエラー）
- `modExtractorWord` のログ文に `〜`(U+301C) が入っていた（CP932外・`?` に化ける）

### 5.2 エラーハンドラの抜け方（`Resume` を使う）

§2 に詳述。要点は「VBAはハンドラ稼働中のエラーを同一プロシージャでは捕捉できず、
`On Error Resume Next` も `On Error GoTo 0` もその状態を解除しない」。
解除できるのは `Resume` とプロシージャ終了だけ。
§4 のページ単位の修正も、最初は 2 ページ目以降で効かない書き方になっていた
（`On Error GoTo 0` では抜けられない）。

同型 57 箇所（36 ファイル）を一括で `Resume` 方式へ直し、
lint 2 本（`check_resume_next_inside_handler` /
`check_resume_on_fallthrough_label`）で再発を止める。

### 5.3 `On Error GoTo 0` の誤用防止

`modShelf.IngestFile` に一時的な `On Error Resume Next` を足す際、
`On Error GoTo 0` ではなく `On Error GoTo Failed` で戻している。
`0` にすると**関数の Failed ハンドラごと解除**され、以降の実行時エラーが
利用者の画面へ素通りする（レビュー H-3 と同じ型の事故）。

## 6. 実機テスト依頼の判断

**`.doc` / `.pdf` が取り込めることを自分の PC で確認できるまで、同僚への依頼は止めること。**

取込は本ツールの入口で、ここが通らないと以降の機能（検索・回答・出典・配信）を
一切評価できない。依頼した側の時間を無駄にするだけでなく、
「使えないツール」という第一印象だけが残る。

### 依頼前に自分の PC で確認すること

1. `.pdf` を1つ取り込む → 成功するか
2. `.doc`（または `.docx`）を1つ取り込む → 成功するか
3. `.xlsx` を1つ取り込む → 成功するか（これは 07-29 時点で成功を確認済み）

**1・2 が失敗した場合、Word を開いたままにしてもう一度試す。**
この端末は Excel から Word を起動できない可能性が高く、
その場合は開き方4（起動中の Word へ相乗り）で通る。
通ったときは `usage_log` に

```
word_open_mode: この端末では開き方4(起動中のWordへ相乗り)で成功しました
```

が出る。**この1行が出たら、同僚への依頼時に「Word を開いたまま試してください」を
手順書へ明記する必要がある**（`docs/41_実機テスト依頼手順_同僚向け.md`）。

それでも失敗する場合は、`usage_log` の `word_open_fail` と
`err_log` の `[段階名/開き方N]` を確認する。段階名で切り分けられる。

| 段階名 | 意味 | 次に確認すること |
|---|---|---|
| `Word起動` | Word のプロセスへ届いていない | Word が入っているか／手で起動できるか／開き方4も 429 なら Word を開いてから再試行 |
| `文書オープン` | Word は生きているがファイルを開けない | 保護ビュー、ファイルブロック設定、そのファイル固有の破損 |
| `ページ数取得` 以降 | 開けたが途中で落ちた | そのファイル固有の問題の可能性が高い |

### 未解決として残しているもの

- `CSV-DX 新種保険アイデア集 13案.pdf` が `localcopy=failed`
  （%TEMP% へのコピー自体が失敗）。原因は未特定。
  FileCopy の失敗理由（ロック／パス長／権限）をログへ出す改善は次回。
- Azure API キーのローテーション（運用作業。コードでは対応不可）
- `seed/seed_pack.xlsx` のベクトル化（リボンのある PC で実施）
