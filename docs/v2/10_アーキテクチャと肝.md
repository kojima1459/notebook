# アーキテクチャと「肝」

> このツールが「なぜ社内で動くのか」「なぜ他のやり方より優れているのか」を一枚で理解するための文書。

---

## 0. 一行でいうと

**自分たちでAPIキーを一切持たず、社内に既に配布済みの「AIリボン（リボンちゃん）」に相乗りして、Excel単体で動く・出典付きの社内ナレッジQAボット。**

---

## 1. 肝（コアの設計思想）— ここが一番大事

### 肝①：APIキーを自分で持たない（最大の発明）

普通、社内でAI機能を作ろうとすると「APIキーをどう秘匿するか」「情シスにどう許可をもらうか」で詰む。V1（初代）はまさにそこで死んだ（後述）。

V2は、**社内に既に全社配布されている AIリボン（リボンちゃん）が持っている Azure OpenAI 接続にそのまま相乗りする**。

```
チャットボット  ──呼び出し──▶  Application.Run("ChatGPT", ...)      ← リボンちゃんの関数
チャットボット  ──呼び出し──▶  Application.Run("GetEmbeddings", ...) ← リボンちゃんの関数
```

これにより：

- **新しいAPIキーが不要**（リボンちゃんが持っている。我々は値すら知らなくてよい）
- **情シスの新規承認が不要**（既に許可済みのリボンの機能を使うだけ）
- **攻撃面が増えない**（我々のファイルに秘密情報がゼロ）
- **コスト管理も既存の枠内**（リボンちゃんのAzure契約に乗る）

> これが「動く社内AIツール」を最短で出すための核心。技術的な賢さより、**既存の動いている資産に相乗りする判断**が勝因。

### 肝②：単発質問ではなく「多段パイプライン＋根拠の3階層」

隣のチャットボットは `ChatGPT(質問)` の単発呼び出し。V2は精度のために多段にした：

```
質問
 → Step0 意図解釈（intent）：真意・前提を抽出し検索用サブクエリに分解
 → Step1 ルーター：990件のナレッジから関連チャンクを12件に絞る
 → Step2 過去Q&A検索：承認済みの過去回答を最大3件引く（自己学習）
 → Step3 ドラフト：約款・ガイドラインを根拠に構造化回答（各主張に出典 [#N]）
 → Step4 自己検証：各主張を出典と照合し、根拠なき断定を削除/修正
 → 回答表示（自信度バナー 🟢🟡🔴 ＋ 出典 ＋ 深掘り候補）
```

**根拠の3階層**（商品部の「AIが勝手に解釈して誤るのでは」という懸念への回答）：

| 階層 | 中身 | 扱い |
|---|---|---|
| ① 第一次根拠 | 約款・引受ガイドライン・商品規定 | 可否の最終根拠。必ず出典 [#N] |
| ② 商品部公式Q&A | 商品部の過去の公式回答事例 | 強い参考。軸にするが①で裏付ける |
| ③ 補足知識 | 一般的な損保実務知識 | 可否の根拠にしない。「実務上は」と明示 |

**事実（資料に明記＝[#N]付き）と推論（実務上の解釈）を見出しで物理的に分離**して出力する。

### 肝③：自己学習する（フィードバックループ）

`feedback` シートに Q&A が貯まる。`pending`（個人即時有効）→ `approved`（全体展開）→ `rejected`+`correction`（誤り訂正）の3状態。次に似た質問が来たら過去の良い回答を優先参照する。使うほど賢くなる。

### 肝④：ナレッジ入れ替え可能（横展開の前提）

VBAコードもプロンプトも**商品非依存**。`knowledge_base` シートのチャンクと `dept_scope` を入れ替えるだけで、別グループ（団体障害など）のボットになる。→ 詳細は `60_横展開_再現手順書.md`。

### 肝⑤：単一ファイル・自己インストール配布

エンドユーザーは `.xlsm` を1つ開くだけ。アドイン登録も情シス作業も不要。開いた瞬間に18モジュールが自動インストールされUIが組み上がる（後述）。

### 肝⑥：全部フェイルセーフ

- 埋め込み失敗 → 全件LLMルーターに自動フォールバック（質問は止まらない）
- 意図解釈失敗 → そのStepを飛ばして続行
- 保存失敗 → 握りつぶして処理継続

「動かない」を構造的に潰してある。

## 2. 全体構成図

```
【オフライン前処理（Mac / Python）— 開発者が一度だけ】
  生テキスト/PDF
    → structure_chunker.py（条文単位でチャンク化）
    → enrich_chunks.py（Geminiで 1行要約・キーワード・領域タグ・書類種別を付与）
    → add_*_chunks.py（貼り付けテキストや商品部Q&Aを追加）
    → dist/index/chunks_enriched.json（990チャンク）
    → build_chatbot_v2.py
    → dist/Chatbot_v2.xlsm（ナレッジ埋め込み済み・配布可能）

【オンライン・ベクトル化（社内PC / 一度だけ）— 開発者が一度だけ】
  Chatbot_v2.xlsm を社内PCで開く
    → admin パネル → ①接続テスト → ②全件ベクトル化
    → リボンの GetEmbeddings で 990件をベクトル化
    → veryHidden の kb_vectors シートに保存
    → config の rag_enabled = TRUE
    → 保存 → これが「本番配布ファイル」

【実行時（各営業PC）】
  質問入力 → modPipeline が上記パイプラインを実行
    → rag_enabled=TRUE なら：埋め込みで40件に絞ってからルーターLLMが12件選択
    → rag_enabled=FALSE なら：全件をルーターLLMに見せて12件選択（従来）
```

## 3. Excelシート構成（データはぜんぶシートに載っている）

| シート | 役割 |
|---|---|
| `main` | チャットUI（入力・出力・🟢🟡🔴・教えてBOX 等） |
| `config` | モデル設定・動作モード（`rag_enabled`, `mock_llm` 等）。**コード変更なしで挙動を変える** |
| `system_prompt` | LLMへの指示（ルーター/ドラフター/検証者） |
| `department` | 部署マスタ（dept_id, 名称, dept_scope） |
| `manifest` | ナレッジ元の一覧（source, 領域, 書類種別） |
| `knowledge_base` | 全チャンク（後述の10列）。**ナレッジの本体** |
| `kb_vectors` | 各チャンクのベクトル（veryHidden）。Phase2の心臓 |
| `feedback` | 過去Q&A（pending/approved/rejected） |
| `usage_log` | 利用ログ |
| `vba_src` | 18モジュールのソース（自己インストーラがここから読む） |
| `admin` | 管理者用ベクトル化パネル（hidden） |

`knowledge_base` の列：
```
chunk_id | source | display | domain | doc_type | section_header | summary | keywords | full_text | dept_scope
```

## 5. ハイブリッド・ベクトル化の仕組み（技術的な肝）

「ハイブリッド」とは **埋め込み（意味検索）＋ LLMルーター（推論で最終選択）＋ 富化メタデータ（要約・キーワード）** の3つを組み合わせている、という意味。純粋なベクトル検索ではない。

### なぜハイブリッドか
- 純ベクトル検索だけだと「関連はするが質問の答えにならない」チャンクを拾う。
- LLMルーターだけだと、990件すべてを毎回プロンプトに載せる必要があり、グループを増やすと破綻する。
- **埋め込みで40件に粗く絞り、LLMが推論で12件を精選する**ことで、両方の弱点を消す。

### ベクトル化の対象テキスト（`modVectorize.ComposeText`）
チャンク本文だけでなく **要約 ＋ キーワード ＋ 本文** を連結して埋め込む。これで「質問の言い回しがナレッジ本文と違っても、要約・キーワード経由でヒットする」確率が上がる。

### 実行時の流れ（`modRetrieve.BuildRouterTableHybrid`）
```
rag_enabled = FALSE → 従来どおり全件表をLLMに渡す（完全に同じ挙動）
rag_enabled = TRUE  → 1. 富化された質問文を GetEmbeddings でベクトル化
                      2. 部署可視の kb_vectors を全件 CosineSim でスコアリング
                      3. ストリーミング top-K で上位40件を選ぶ
                      4. その40件だけで従来のルーター表を作る
                      5. ルーターLLMが40件から12件を選ぶ
  ※ 埋め込み失敗・候補ゼロ → 自動で全件表にフォールバック（止まらない）
```

text-embedding-3-small のベクトルは L2 正規化済みなので、コサイン類似度＝内積。VBA側は安全のため両対応（`modEmbeddings.CosineSim`）。

## 6. 配布バイナリの作り方（自己インストーラ方式）

ここが**最大の技術的ブレイクスルー**（詳細な経緯は `20_開発の記録`）。要点：

1. **本物のExcelが作った** スケルトン `.xlsm`（`build/template_skeleton.xlsm`）から出発する。
2. openpyxl で `keep_vba=True` でデータシートを足す（vbaProject.bin はバイト単位で保持）。
3. vbaProject.bin の中の **2ストリームだけ**を外科的に差し替える：
   - `ThisWorkbook` → 自己インストーラのコード
   - `dir` の ThisWorkbook MOFFSET → 0
4. 18モジュールのソースは `vba_src` シートに文字列として埋め込む。
5. 開くと `Workbook_Open` → インストーラが `vba_src` を読み、VBProject API で全モジュールを生成 → 最後に `modBoot.Boot` を呼んでUIを構築。

結果、**バイナリの99.9%がExcel自身の出力とバイト同一**になり、ガチガチの社内Excelでも受け入れられる。

> 前提：「VBAプロジェクトオブジェクトモデルへのアクセスを信頼する」がON である必要がある（社内PCでは既にONだった）。
