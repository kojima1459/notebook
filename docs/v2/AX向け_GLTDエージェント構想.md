## 2. 背景・目的

### GLTDという商品の難しさ

GLTDは設計レバーが多く、引受難易度が高い商品。

- **設計レバー**：補償割合（50〜66.7%）、てん補期間（2年〜65歳満期）、免責期間（30〜180日）、加入方式（全員・自由選択）、公的給付との調整方式
- **情報非対称**：企業の離職率・休職データを開示してもらわないと適切な設計が困難
- **逆選択リスク**：健康不安のある企業が選択的に加入する傾向
- **長いリードタイム**：提案→設計→引受判断まで複数ステップ

現状、営業担当が「どう設計すればいいか」を本社に問い合わせる照会が多発。引受担当の暗黙知・経験値に依存しており、担当者によって回答品質にばらつきがある。

### なぜ今

1. **V2ナレッジQAチャットボット（新種・一般向け）で横展開の型ができた** → GLTD版への転用が現実的になった
2. **MS&AD AX株式会社が設立（2026/6/1）** → AIエージェント開発基盤を外部調達できる可能性が生まれた
3. **部長の問題意識と一致** → 「AIエージェントで設計を気軽にできるようにしたい」

## 3. フェーズ設計

### Phase 1：GLTDチャットボット版（現環境で実現可能）

**概要：** 既存のV2ナレッジQAチャットボットのナレッジを入れ替えてGLTD対応版を作る。

- **入力：** 約款・引受ガイドライン・社内FAQ・過去の照会事例
- **出力：** 引受判断に関するQA（「この場合の免責期間の考え方は？」「全員加入でなければ逆選択リスクはどうなる？」等）
- **制約：** 保険料計算不可（コード実行環境がないため）
- **実現方法：** `60_横展開_再現手順書.md` に従いナレッジ入替のみ。コード変更なし
- **インフラ：** 社内AIリボン（Azure OpenAI）＋ Excel VBA。追加費用なし
- **着手条件：** 約款・引受ガイドラインの入手

**価値：** 照会件数の削減。「まずチャットボットに聞く」文化の醸成。

---

### Phase 2：GLTDエージェント版（AX経由で実現）

**概要：** 企業データを入力すると、最適な設計案を提示・比較・試算できるAIエージェント。

#### Phase 2のイメージ

```
営業担当
  │
  │ 「従業員300名・IT企業・過去2年で精神疾患5件・平均年収600万」を入力
  ▼
[GLTDエージェント]
  │
  ├─ ① データ分析エージェント（離職率・業種リスク・公的給付水準を評価）
  ├─ ② 設計提案エージェント（複数プランのてん補期間・免責期間・補償割合を試算）
  ├─ ③ 逆選択チェックエージェント（リスク要因を抽出・引受上の懸念点を提示）
  └─ ④ 報告書生成エージェント（提案書ドラフトを自動作成）
  │
  ▼
「推奨プランA/B/C + 引受上の確認事項 + 提案書ドラフト」を出力
```

#### Phase 2に必要なもの

| 必要要件 | 内容 | 現状 |
|---|---|---|
| **AIエージェント基盤** | function calling（ツール呼び出し）+ ループ実行 | ❌ 社内リボンでは不可 |
| **コード実行環境** | 保険料試算・データ集計 | ❌ 社内PCでは不可 |
| **開発環境** | APIキー+ターミナル+クラウド実行 | ❌ 社内PCでは不可 |
| **データ連携** | 企業の契約データ・損害データ参照 | ❌ 現状はシステム未連携 |
| **ガバナンス** | 業務データをAIに通す際の情報セキュリティ基準 | ❌ 未整備 |

→ **すべての不可要件が「AXが解決すべき課題」と完全一致する。**

## 4. なぜ現環境では作れないか（AIエージェントの構造的制約）

### AIエージェントとは

「単一の質問に答える」ではなく、**ツールを呼び出しながら複数ステップを自律的に実行するAI**のこと。

```
ユーザー入力
  → AIがタスクを分解
  → ツール呼び出し（検索・計算・DB参照・外部API）
  → 結果を評価して次のツールを選択
  → 必要なら追加ループ
  → 最終回答を生成
```

このループ処理（function calling）と外部ツール接続が核心。

### 社内AIリボンの制約

| 機能 | エージェントに必要か | リボンの状況 |
|---|---|---|
| function calling（ツール呼び出し） | ✅ 必須 | ❌ エンドポイント未提供 |
| コード実行 | ✅ 必須（試算等） | ❌ 制限あり |
| 外部API連携 | ✅ 必須 | ❌ 制限あり |
| エージェントループ | ✅ 必須 | ❌ シングルターン補完のみ |
| 長大プロンプト | ✅ 必要 | ⚠️ 〜3000行制限 |

→ **社内AIリボンでAIエージェントは構造的に作れない。** これは運用でカバーできる問題ではなく、プラットフォーム設計の問題。

### バイブコーディング（Vibe Coding）で作れるか

「AIに自然言語で話しかけながらコードを生成させる開発手法」がバイブコーディング。

**個人PCがあれば作れる：**
- Claude Code（CLIツール）をインストール
- AnthropicのAPIキーを取得（有料：月数千〜数万円）
- 「GLTD設計エージェントを作って」と日本語で指示するだけでコードが生成される

**社内では現実的でない：**
- 社内PCはターミナル使用不可
- ブラウザ制限により外部APIキーの利用も困難
- 個人PCで業務データを処理すると情報管理上の問題が生じる

→ バイブコーディング自体は「難しいもの」ではなく、**環境さえあれば誰でもできる**。問題は環境がないこと。ここがAXへの相談案件になる。

## 5. Claudeでエージェントを作る方法（参考整理）

「ウェブかデスクトップでエージェントが作れる画面があった気がする」について整理する。

### Claudeのエージェント関連機能

| 機能 | できること | 必要なもの | 本格度 |
|---|---|---|---|
| **Claude.ai Projects** | カスタム指示+ドキュメント登録。毎回読み込む賢いアシスタント的利用 | claude.aiアカウント | ★☆☆ |
| **Claude Code（CLI）** | ターミナルで対話しながらコード生成・実行。バイブコーディングの本丸 | 個人PC+APIキー | ★★☆ |
| **Claude API Managed Agents** | APIでエージェント定義→ツール呼び出し+ループをAnthropicが管理。本格エージェント | APIキー+開発環境 | ★★★ |
| **MCP（Model Context Protocol）** | ClaudeをGitHub/Slack/DB等の外部ツールに接続する標準プロトコル | APIキー+MCP対応環境 | ★★★ |

「ウェブかデスクトップで見た設定画面」は **Anthropic Console** か **Claude.ai Projectsの設定** と思われる。ただしそこだけで本格エージェントが完結するわけではなく、コードとAPIキーが必要。

### 個人での試し方（参考）

```
1. claude.ai にサインアップ（個人アカウント）
2. 「Projects」でGLTD用の指示とドキュメントを登録
3. チャット感覚で引受相談ができる「簡易版」として使える
→ これがPhase 1の先行体験版として使える（業務データ投入は自己判断で）
```

### 背景・目的

- GLTDは設計複雑性・情報非対称・逆選択リスクから引受担当への照会が多発
- 営業・引受担当の「設計ノウハウの属人化」を解消したい
- 社内AIリボンでは構造的にエージェント機能が実現できないため、外部開発基盤が必要
- Phase 1（チャットボット版）は内製済みV2の横展開で実現可能。Phase 2（エージェント版）をAXに相談したい

### 展開余地

- **部内横展開**：GLTD → 傷害・賠責 → 他新種商品へのナレッジQA展開
- **全社展開**：AX提供の開発基盤に乗せることで、他本部・他商品ラインへの応用
- **外販可能性**：「GLTDエージェント」を代理店向けツールとして展開
- **データ活用**：エージェントとの対話ログが引受ルールの改善・商品改定の材料になる
