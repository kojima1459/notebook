```

  ↓ 方針転換：社内の AIリボン（リボンちゃん）に相乗り

V2（現行）  リボン経由 ChatGPT/GetEmbeddings + 単一xlsm

```

## 致命的だったボトルネック

### ① 直接APIキーを持つと詰む
V1は Gemini API を直接叩き、個人キーを難読化して埋め込む設計だった。
- 社内ネットワーク/プロキシ/セキュリティで外部API直叩きが通らない。
- 「キーをどう秘匿するか」「情シスにどう承認させるか」で永遠に進まない。
- **学び**：社内でAIツールを通すなら、**自分でキーを持たない**のが最短。
  → 既に許可されて全社で動いている資産（リボンちゃん）に相乗りする。

### ② 大きなバイナリindexは運べない
V1は埋め込みindexを19MBのバイナリで持っていた。配布・更新・社内配信のすべてで重荷。
- **学び**：データは**Excelシートに載せる**。ベクトルも `kb_vectors` シートにCSV文字列で持つ。
  Excelが運搬・更新・差分の問題を全部吸収してくれる。

### ③ 手作りの vbaProject.bin は社内Excelに拒否される（最大の難所）
V2で「VBAを含むxlsmをプログラムで生成」しようとしたが、
手で組んだ vbaProject.bin（CFBライタ / OVBA圧縮 / パフォーマンスキャッシュ）は
ガチガチの社内Excelが「壊れている」と拒否した。何度も作り直しても通らない。

## ブレイクスルー

### 突破口① 自己インストーラ方式（③の解決）
発想の転換：**バイナリをゼロから作るのをやめ、本物のExcelが作ったファイルを“ほぼそのまま”使う。**

1. 本物のExcel製スケルトン `.xlsm` から出発。
2. vbaProject.bin の中の **2ストリームだけ**を差し替える
   （`ThisWorkbook`＝インストーラ / `dir`のMOFFSET＝0）。
3. 18モジュールのソースは `vba_src` シートに**文字列として**埋め込む。
4. 開くと `Workbook_Open` がインストーラを起動し、`vba_src` を読んで
   VBProject API でモジュールを自動生成 → `modBoot.Boot` でUI構築。

**結果**：バイナリの99.9%がExcel自身の出力とバイト同一 → 社内Excelが受け入れる。

> **今日見つけた追加の罠**：初回オープン時、インストーラは走るが、
> その場で新規追加された `Auto_Open`/`Workbook_Open` は**遡って発火しない**。
> → インストーラの末尾で明示的に `Application.Run "modBoot.Boot"` を呼ぶことで解決済み。
> （写真で全18モジュールが入っていたのに「何も起きない」ように見えたのはこのため。実際は成功していた）

### 突破口② Phase2 ハイブリッド検索（精度と拡張性の両立）
従来のルーターは「990件の要約表を丸ごとLLMに見せてID選択」。
1グループなら持つが、複数グループ統合で破綻する天井があった。
- 埋め込みで40件に粗く絞り、LLMが12件を精選する2段構えに。
- **`rag_enabled` で完全にゲート**。FALSEなら従来と1ミリも変わらない。
- 埋め込み失敗→全件フォールバック。**つまり「ONにして悪化することがない」設計**。
- **学び**：本番テストできない環境（Mac・社内PC未入手）で安全に攻めるには、
  「失敗しても従来挙動に戻るゲート」を必ず噛ませる。

### 突破口③ Phase3a 評価モデルの刷新（使われる仕掛けへ）
当初は ○正しい / ×間違い の正誤判定だった。だが：
- 「AIを採点する」感覚で、現場では押されない。
- 押されないと学習ループが回らない。
- **刷新**：🟢スッキリ解決 / 🟡もう少し知りたい / 🔴まだ不安・要確認 の
  「**どう着地した？次どうする？**」モデルへ。各反応が次の行動（深掘り/本社照会）に直結。
- 学習価値（旧○＝pending、旧×訂正＝rejected+correction）は保ったまま、
  新ステータス（more/unsure）は学習ループに**混入しない**（検索対象外）よう設計。

## テスト戦略（本番で触れないものをどう検証したか）

「Macでも社内PCでも事前にテストできない」という制約下で、壊さないために：

1. **mock_llm モード**：リボンが無くても、決定的な擬似ベクトル/擬似応答で
   パイプライン全体をMacで通せる。
2. **オフライン等価検証**：Phase2のストリーミングtop-Kアルゴリズムを Python に移植し、
   総当たり参照実装と **3000回のランダム試行＋エッジケース**で完全一致を確認してから出した。
3. **シンボル表チェック**：全ボタンの OnAction とモジュール間呼び出しが、
   実在する Public プロシージャに解決することを機械的に確認してからコミット。
4. **段階リリース**：Phase 0+1 → レビュー → Phase 2 → Phase 3a と、
   一度に飛ばさず一段ずつ。

## 設計判断として残しておきたい「やらなかったこと」

| 検討したが見送り | 理由 |
|---|---|
| ベクトルの量子化/バイナリ化 | VBAでの実装リスク大。実ボトルネックは保存でなく計算で、効果が見合わない |
| 次元削減（1536→256）の即時導入 | 効果はあるが、**再ベクトル化の前**にしか入れられない。本番安定後に検討（`50_ロードマップ`） |
| チャット吹き出しUI（Phase3b） | 機能は増えず見た目だけ。一番壊れやすい。実機で使われ始めてから |
| SharePoint自動同期 | まずローカル運用で価値を確かめてから |
