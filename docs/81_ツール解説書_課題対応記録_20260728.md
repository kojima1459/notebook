## 1. 対応した課題 — 何を・どう直し・なぜその方法にしたか

### 【最重要】#9 単段と多段でスコア式が異なる（+ #8 が同時に解消）

**解説書の記述より、実態は遥かに深刻だった。**

解説書は「`GramBonus` が `SearchExpanded` にしか無い」と書いていたが、コードを突き合わせると次の状態だった。

| | 単段 `Search` | 多段 `SearchExpanded` |
|---|---|---|
| スコア式 | `modSparse`（文字 bigram + BM25 + 完全一致）**← 実測 R@1 32%→84%** | 旧方式（`KeywordBonus` + `GramBonus` + `FullTextBoost`） |
| config 既定 | — | **`retrieve_mode=multi` = こちらが既定** |

つまり **測って上げた検索精度が、既定の構成では一度も使われていなかった**。単段だけを新実装に差し替えて、既定パスである多段を置き去りにしたまま「84% に上がった」と記録されていたことになる。

**どう直したか**: 多段側のスコアリングを `modSparse` へ寄せ、**スコア式をモジュール内に1つだけ**にした。旧方式の関数群（`KeywordBonus` / `GramBonus` / `FullTextBoost` / `BigramsIfSingleToken` / `TokenizeQuery`）と関連定数は削除した。

**なぜこの方法か**:
- 加点の係数を勘で調整するのではなく、**既に実測してある側の実装へ寄せる**のが唯一の根拠ある選択だから。ベンチ用のコーパス（実物6資料 180チャンク＋31問）はリポジトリに含まれない（社内資料のため）ので、この場で再測定はできない。**測れないときに数字をいじるのは、直したふりにしかならない。**
- これで #8（加点上限 +0.64 が大きい／`FullTextBoost` は本文が長いほど有利）も同時に消える。BM25 は文書長で正規化されるため、**長いチャンクが有利になる構造そのものが無くなる**。#8 は加点の大きさの問題ではなく、**式が2つあったこと**が根だった。
- 多段が例外で単段へフォールバックしたときに結果が変わる問題も、式が1つなら起きない。

**#9 後半（deep 検証段に `DomainGuard` 未注入）**: 検証段にも注入し、さらに「下書きの `(要確認)` は根拠が弱い箇所に意図的に付けたもの。抜粋で裏付けられない限り外さない」と明示した。下書きが正しく付けた確認マークを検証段が落とすと、**確認が要る数字が確認不要の顔をして残る**。保険の金額・期限・料率でこれが起きると実害が出るため、プロンプトの1行で防げるなら防ぐ。

### #10 失効タイマーの誤作動（知識の誤消去）

`modGuard.TouchReach` の発火条件が「チャンネルが1件以上見つかったとき」だったため、**共有フォルダには到達できているが、まだどの部門も正典を発行していない**状態では到達記録が更新されず、30日後に**利用者が自分で取り込んだ資料まで消えていた**。**PoC の初期状態（共有パスは設定済み・正典は未発行）がまさにこの条件**である。

**どう直したか**: 判定を `modShare.Reachable()`（共有フォルダのルートへ到達できたか）に変更した。

**なぜこの方法か**: 解説書は「1行の修正で済む」としていたが、**同じ判定を各所が自前で持つと必ずまたズレる**。前回のレビュー対応で共有フォルダの到達性判定を `modShare` に集約済み（1セッション1回だけ実測してキャッシュ）だったので、失効タイマーもその単一情報源を読むだけにした。追加のコストはゼロで、以後「到達したか」の定義が食い違うことがない。

### #11 獲得できるが表示されないバッジ4種

判定は12種、表示は8種。**共有知フライホイールに最も貢献した行為を称える4種**（`fb10` / `fb50` / `qa_share10` / `gapfill`）が、獲得しても本人に見えなかった。

**どう直したか**: 表示側の配列に4要素を足すのではなく、**判定を持っている `modStats` を単一情報源**にした（`BadgeCatalog` / `BadgeEarnedOn`）。表示側（`modDash` / `modHub`）は読むだけになった。`modDash` のバッジ棚は**件数から行数を算出**するようにし、バッジを増やしてもレイアウト定数を触らずに済む。

**なぜこの方法か**: 解説書は「表示側3箇所の配列に4要素を足すだけ」と書いていたが、それは**同じ表を3つ維持し続ける**という意味で、次にバッジを足したときに同じズレが起きる。これは前回レビューの C-1（配信タグを書く側と消す側が別々に文字列を組み立てていた）と**まったく同じ失敗の型**である。同じ失敗を2度踏まないために、構造の方を直した。表の整合（4配列の長さ一致・id 重複なし・空要素なし・落ちていた4種の存在）は純ロジックテスト10件で固定した。

### #7 `binary_rag` が既定パスで不作動

粗選別（`modBitwiseOpt.Prefilter`）が単段 `Search` にしか組み込まれておらず、既定 `retrieve_mode=multi` では一切効かなかった。**多段は「クエリ数 × 全チャンク」の総当たりで deep なら最大5周する**ので、速くしたい場所にこそ効いていなかったことになる。

**どう直したか**: 多段側へ配線した（粗選別はクエリごとに実施）。**`binary_rag` の既定は `FALSE` のままなので、既定の挙動は変わらない。**

**なぜこの方法か**: 既定を `TRUE` にする判断は、実機の本棚規模での実測が要る。**配線だけ済ませて、有効化は測ってから**にした。あわせて、次元が混在していて候補が本棚を代表できないときは粗選別を辞退して全件比較へ退避する（前回対応の L-1）。「速いが一部見えない」より「遅いが全部見える」を選ぶ方針は変えていない。

### #1 `vba_src` 自己書き換え（実害2点のみ封鎖）

方式そのものは変えられないが、この方式が抱えていた実害は塞いだ（前回レビュー対応）。

- 注入に失敗しても無条件で `Save` していたため、**壊れた状態がファイルに固定化**されていた → 1件でも失敗したら保存しない
- インストーラが予約する `OnTime` の時刻を残していなかったため解除できず、**閉じても数秒後に Excel が勝手に開き直して保存までしていた** → 予約時刻を記録して確実に解除

### #4 旧 UI と新 UI の併存（一部）

- 到達不能な Public プロシージャ **11本を削除**（`modVault.OnVault*` 5本ほか）。`modUIDashboard` は既に削除済みだった
- 起動時の再実行パスが**旧ホーム UI だけを Hub の上に描き直していた**バグを修正（既知の「タブが常時表示されない」「位置がずれる／再描画で直る」の最有力の原因）

### B2 `publish_key` が一般配布ビルドに入る

**どう直したか**: 発行者用ビルドは `--publisher` を明示したときだけ作られ、環境変数 `MYBOOKSHELF_PUBLISH_KEY` から焼き込む。**出力ファイル名も `MyBookshelf_発行者用.xlsm` に変わる**。

**なぜこの方法か**: 解説書の提案は「`publish_key` を空にしたコピーを一般配布する」だったが、**手作業の除去は必ず忘れる**。しかも忘れたことに気付く手段が無い（2つのブックは見た目で区別できない）。ビルドの時点で物理的に別物にし、**既定は常に安全な側**（利用者用）になるようにした。環境変数が設定されていても `--publisher` が無ければ焼き込まず、その旨を表示する。

### B3 バージョン更新時のデータ移行（新規実装）

**どう直したか**: 引き継ぎ機能を実装した（`modMigrate` + ❓ヘルプの導線2本）。

| データ | 引き継ぎ | 方式 |
|---|:---:|---|
| my_knowledge / my_vectors / my_manifest | ✅ | 置換。`origin` は `self` のまま（パック経由と違い `pack:` に化けない）。**manifest が運べるので移行後もマイ本棚の一覧に出る** |
| my_stats（EXP / バッジ / 連続日数 / 節約時間） | ✅ | キー単位で併合 |
| config | ⚠️ 一部 | **新版に存在するキーだけ**引き継ぐ |
| `mock_llm` / `build_stamp` / `publish_key` / `azure_embed_*` | ❌ | **意図的に除外** |

**なぜこの方法か**:
- **パックを流用しなかった理由**: パックは「他人に配る知識」の器であって「自分の環境まるごと」ではない。実際パック経由だと `origin` が `self` → `pack:` に変わり、`my_manifest` も統計も運べず、移行後に一覧から消えて同期・削除の対象外になる。
- **config を上書きではなく併合にした理由**: 新版で増えたキーを古い設定で潰すと、**新機能が既定で無効のまま配られる**。新版のキー集合を正とし、値だけ引き継ぐ。
- **ビルドが決める値を意図的に除外した理由**: ここを運ぶと「利用者用ブックに発行キーが復活」「本番ビルドにモックが復活」となり、**せっかく塞いだ B1/B2 が引き継ぎ経由で復活する**。移行機能そのものが穴にならないようにした。
- **安全装置**: 読み込み時に `embed_dim` を照合し、次元が違うファイルは**取り込む前に止める**（入れてから気付くと本棚が全件で次元不一致になる）。本棚が空でないブックへの読み込みには置換の確認を必ず出す。

## 3. 対応しなかった課題と、その理由

| # | 課題 | 対応しなかった理由 |
|:--:|---|---|
| 1 | `vba_src` 自己書き換えが単一障害点 | **これは修正対象ではなく決定対象**。「VBA プロジェクトへのアクセスを信頼」を全社で有効化できるかどうか（§12.2 #4）で、通常の xlsm 方式へ設計変更するかが決まる。技術判断ではなく、情報システム部門との調整結果に従うべき事項なので、こちらで方式を変えるべきではない。実害2点だけ先に封鎖した |
| 4 | 旧 UI と新 UI の完全な一本化 | 画面の作り直しになり、**PoC 直前に入れる変更としてリスクが釣り合わない**。死にコードの削除と重畳バグの修正で、実害（動かないボタン・画面の重なり）は消してある。一本化は PoC で「どの画面が実際に使われたか」を測ってから決める方が、削る対象を間違えない |
| 7 | `binary_rag` の既定を `TRUE` にする | 配線は済ませたが、**既定を変える判断には実機の本棚規模での実測が要る**。粗選別は「上位N件に絞ってから精査する」仕組みなので、N の妥当性は実データに依存する。測らずに既定を変えると、速くなった代わりに何が落ちたか誰も分からない |
| 8 | 加点係数そのもののチューニング | **測定できない環境で数値をいじらない**という判断。ベンチ用コーパス（実物6資料・31問）はリポジトリに含まれない（社内資料のため）。式の統一で構造的な偏り（長文有利）は消えているので、係数の微調整は実機データで測ってから |
| 13.1 #1〜#6 | 検索スコープ引数の追加（種目別・商品別の絞り込み） | `Search` / `SearchExpanded` への引数追加は `my_knowledge` の列追加、パック形式（`pack_chunks`）、`ValidatePack` の互換性検査まで波及する。**PoC 期間中の小改修としては重すぎる**という解説書 §13.2-C の評価に同意する。まず A（資料名に種目を入れる）と B（種目ごとにチャンネル）を運用で試し、横断質問のニーズを測ってから設計すべき |
| 13.3 | `optDiffDoc`（約款差分）の UI 結線 | 未結線の機能を結線するのは**バグ修正ではなく機能追加**。今回の作業（レビュー指摘への対応）と混ぜると、変更の範囲が判定できなくなる。結線するなら diff_report シートからの脱出導線もセットで要るので、独立した作業として扱う |
| 13.3 | `feature_tts`（読み上げ） | **提供不可**。AI リボンが読み上げ API を公開していないため実体を作れない。config 説明欄に既定 FALSE のまま変更しない旨を明記済み |
| — | チャット履歴・`insight_inbox` の引き継ぎ | 引き継ぎ対象から意図的に外した。履歴とログは**新しい版の記録として作り直す**のが素直で、運ぶと「いつの版で起きたエラーか」が混ざって障害調査の役に立たなくなる |
| B1 | Azure API キーのローテーション | **コードでは閉じられない運用作業**。テストコードに平文で入っていた期間があるため、露出済みとして無効化・再発行が必要。コード側は「もう漏らさない」状態にしたが、既に配った分は取り消せない |

## 4. 実機で確かめること（今回分）

macOS 上の静的解析とヘッドレスのコンパイル／純ロジックテストでは検証できない範囲。

1. **#9 の検索精度** — 既定構成（`retrieve_mode=multi`）で、条番号や固有名詞を含む質問が正しい資料を引くこと。**今回はじめて多段側に新スコアリングが乗るため、体感が変わる可能性がある**（設計上は良くなる方向）
2. **#10 の失効タイマー** — 共有パスを設定済み・正典は未発行の状態で起動し、`my_stats` の最終到達日が当日に更新されること
3. **#11 のバッジ表示** — ダッシュボードに12種すべて表示され、バッジ棚がチャート枠と重ならないこと。Hub 側も12種出ること
4. **#7 の粗選別** — `binary_rag=TRUE` にしたとき、多段でも `binary_rag_debug` の所要 ms が出ること（従来は単段でしか出なかった）
5. **B2 の発行者用ビルド** — `MyBookshelf.xlsm` に発行ボタンが出ないこと。`MyBookshelf_発行者用.xlsm` には出ること
6. **B3 の引き継ぎ** — 旧ブックで書き出し → 新ブックで読み込み → **マイ本棚の一覧に資料が並ぶ**（`my_manifest` が運べている証拠）こと。EXP・バッジ・連続日数が戻ること。`publish_key` が**復活していない**こと
7. **ヘルプパネル** — 引き継ぎボタン2つが表示され、閉じたときに残らないこと
