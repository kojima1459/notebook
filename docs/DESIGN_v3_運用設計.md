# Nexus Agent 運用設計 v3 — 部門ナレッジ配信・事故防止・スケール

2026-07-26 / 対象: 約12,000名(子会社・海外含めるとそれ以上)

この文書は「動く仕組み」ではなく「**壊れない運用**」を決めるためのもの。
実装は本文書の各節に1対1で対応している。

---

## 1. 購読制はやめる(v2からの設計変更)

### v2の誤り
「必要なチャンネルだけ購読する」設計にしていた。これは間違い。

利用者の実際の行動は「今日は商品、明日はシステム、明後日は経費精算」であり、
**聞く前に「どの分野か」を自分で判断して購読操作をする**という手順が挟まった時点で、
ポータルを探し回るのと同じ認知負荷が発生する。解決したかった問題を作り直している。

### v3の設計
**既定で全チャンネルを自動購読する。** 外したい人だけ外せる(既定は全部オン)。

これが成立する根拠(チャンク試算):

| 対象 | 粒度 | 1件あたり | 件数 | チャンク |
|---|---|---|---|---|
| 部門正典(Q&A形式) | 質問+確認済み回答 | 1〜2 | 500件/部門 | 500〜1,000 |
| 6部門合計 | | | 3,000件 | 3,000〜6,000 |
| 個人の本棚 | 原文資料 | 140/100ページ | 20冊 | 〜2,800 |
| **合計** | | | | **6,000〜9,000** |

上限20,000に対して十分な余裕がある。**成立の条件はただ一つ**:

> **正典に原文マニュアルを丸ごと入れない。** 正典は「確認済みQ&A + 要点」に限る。
> 100ページの約款を丸ごと入れると1部門で数千チャンクを食い、この試算は崩れる。
> 原文が必要な人は自分のマイ本棚に個別に入れる。

この一線を運用ルールとして守れるかが、スケールするかどうかの分岐点。
アプリ側は使用量を常時%表示し、8割を超えたら警告を出す(自動では消さない)。

### 「全社共通」チャンネルは作らない
定義できる人がいない、管理する部署が決まらない、という時点で運用が破綻する。
**チャンネルは実在する部門と1対1**にする(商品部/システム部/人事部/法務部/…)。
責任の所在が組織図と一致していれば、担当者が異動しても引き継ぎ先が自明になる。

## 2. 発行(publish)の運用 — 手を動かすのは役職なしの若手

### 前提
発行者は専門家ではない。ミスは必ず起きる前提で設計する。
**「間違えられない設計」ではなく「間違えても戻せる設計」**にする。

### 発行の5ステップ(ウィザード)
1. **チャンネル選択** — 既存から選ぶか新規作成。名前は部門名そのまま
2. **内容確認** — 何件・どの資料が出るかを発行前に一覧表示
3. **PII走査** — 既存の modPii を必ず通す。個人情報が1件でもあれば発行を中止
4. **発行者確認** — 発行キー(config publish_key)の入力。空欄なら発行不可
5. **発行** — 旧版を _archive へ退避 → 新版を書く → version.txt を更新

### 事故が起きたときの取り消し
発行画面に「**直前の版に戻す**」を用意する。_archive から1つ前を復元し、
version.txt を巻き戻す。購読者は次回起動時に自動で旧版へ戻る(版が変われば
必ず置換されるため、誤った内容は各PCから消える)。

**これが最重要**: 誤った正典が配信され続ける事故を、発行者が1人で・数十秒で
止められること。承認フローを挟むと止められなくなる。

### 発行ログ
`channels/<名前>/publish_log.txt` に「日時・発行者・件数・版番号」を追記する。
誰がいつ何を出したかが常に追える。責任の所在が曖昧にならない。

## 3. 同時アクセス(朝の一斉起動)

### 想定される事故
- 始業直後に数千人が同じ version.txt / pack.xlsx を同時に読む
- ファイルサーバの同時接続上限に当たる
- 読み取り中に発行者が書き換えて、壊れたファイルを読む

### 対策
1. **起動時に読むのは version.txt(数十バイト)だけ**。pack.xlsx(数MB)は
   利用者がクリックしたときだけ読む。一斉起動で流れるトラフィックを最小化する
2. **ランダム遅延(ジッター)**: 起動時のチェックを 0〜3秒のランダム待機後に行う。
   全員が同一ミリ秒に殺到するのを構造的に避ける
3. **リトライ**: 読み取り失敗は 3回まで、待ち時間を 200/400/800ms と伸ばす
   (共有フォルダI/Oの既存実装と同じ方式)
4. **ローカルへコピーしてから開く**: pack.xlsx は %TEMP% にコピーしてから
   Workbooks.Open する。読み取り中のロックを共有側に残さない。発行者が
   書き換えても、こちらが読んでいるのはコピーなので壊れない
5. **失敗しても起動は絶対に止めない**: 全経路 On Error Resume Next。
   同期できなければ「あとで再試行」として静かに次回へ回す

### 発行中の不整合を防ぐ
version.txt は **pack.xlsx を書き終えた後に最後に書く**。
購読者は version.txt を見て判断するので、「新しい版番号なのに中身が古い/壊れている」
という状態が原理的に発生しない。

## 4. 端末セキュリティ(PC紛失・持ち出し)

VBAとxlsmという配布形態の限界を正直に書く。**完全な防御は不可能**。
できるのは「拾った人が中身を読むまでの手間を上げる」「時間が経てば無効化する」。

### 実装する3層
1. **所属チェック**: 起動時に Windows のドメイン/ユーザー名を確認する。
   config allowed_domain と一致しなければ、知識シートを一切開かず案内だけ出す
2. **有効期限(kill switch)**: config knowledge_expire_days(既定30)。
   共有フォルダに最後に到達できた日から N 日が経過したら、
   my_knowledge / my_vectors の中身を自動で消去する。
   社内ネットワークから切り離された端末は、放っておけば空になる
3. **PII走査の常時適用**: 正典に個人情報を載せない(発行時に強制)

### やらないこと(できないこと)
- ブック自体の暗号化 → VBAプロジェクトを開ける人には無意味
- 完全なアクセス制御 → ファイル共有の権限設定(IT部門の管轄)に依存する

**この3層は「万一のときの被害を小さくする」ためのもので、
機密度の高い資料を入れない運用ルールと併用して初めて意味を持つ。**

## 5. 利用データ(プロダクトオーナー向け)

### 集める
- 画面別の表示回数(Hub/チャット/ナレッジ/ダッシュボード)
- 質問回数・モード別・所要秒
- 部署別・利用者別の利用回数
- 「解決した/微妙/違う」の比率
- 答えられなかった質問(既にgapとして収集済み)

### 集め方
各PCが日次で1ファイルだけ共有フォルダ `telemetry/<user>_<yyyymm>.txt` に
上書きする(1人1ファイルなので競合しない)。オーナーは集計画面で読み込む。

### プライバシー
- 質問の**全文は送らない**。先頭40字までに切る(傾向把握には十分)
- 送信していることを「使い方」シートに明記する。黙って集めない

### 危険な利用の検知
usage_log には従来どおり全質問が**ローカルに**残る。
共有側には要約のみ。オーナーは集計画面で「注意語を含む質問」の件数だけ見られる。

## 6. 匿名フィードバック

既存のご意見箱はメール(mailto)で本文を送る形式のため、実名になる。
**匿名の投書箱**を別に用意する:
共有フォルダ `feedback/` に、ユーザーIDを含まないファイル名で書き込む。
オーナーは集計画面から一覧で読む。誰が書いたかは記録しない(復元もできない)。

---

## 7. 音声(MP3/MP4)について

**現状、登録できない。** 対応形式は PDF / Word / Excel / テキスト / 画像(スクショ)。

対応するなら文字起こしが必須で、選択肢は2つ:
- 社内AIリボンに Whisper 系の文字起こしAPIがあれば、それを呼んで取り込む
- なければ Teams/Stream の自動文字起こし結果(テキスト)を取り込む(今すぐできる)

後者は**今日から運用でできる**。会議録画の文字起こしをテキストで落として
📁追加するだけ。前者はリボンのAPI仕様が分かってから実装する。

## 8. 教えてBOXからの移行

競合しない。**教えてBOXに来る前に止める**のが唯一の勝ち筋。

- 商品部の過去Q&A(Excel)は、そのまま「商品部」チャンネルの正典として発行する。
  資産を敵にせず燃料にする
- 他部門は教えてBOX自体が無く、ポータル+Formsで待たされている。
  こちらの方がペインは深い。**答えが即座に返る**という一点だけで乗り換えが起きる
- 移行の号令はいらない。速い方が使われる
