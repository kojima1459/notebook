```

[機能層]    modShelf / modShelfSync / modAsk / modPack / modStats / modDiag / modEnrich

```

依存ルール(`tools/vba_lint.py` が機械検査する。違反があるとexit code 1でビルド前に弾ける):

| ルール | 内容 |
|---|---|
| **R1** | 下層は上層を呼ばない(基盤→機能はNG)。**例外はUI通知コールバック4件のみ**: 機能層→`modUIMain.SetStage`(進捗実況)、`modUIMain.RenderSourcesPreview`(出典先出し)、`modUIMain.RenderAnswer`(回答描画)、`modUIShelf.RenderShelf`(カード再描画)。これ以外のUI参照は引き続き禁止 |
| **R2** | `opt*` モジュール名の直接参照(`optTts.` 等のトークン)はコアのどのモジュールにも書かない。呼び出しは必ず `modFeatures.InvokeFeature` / `Application.Run` の文字列経由 |
| **R3** | リボン関数(`ChatGPT`/`GetEmbeddings`)の `Application.Run` は `modGateway` 内のみ。opt層も自前でRunせず `modGateway.TryRibbonRun` を使う |
| **R4** | **純ロジックモジュール**(`modUtil`/`modChunker`/`modPii`/`modTypes`/`modChrome`と各Pureテスト)は`Worksheets`/`Range`/`Application`/`ThisWorkbook`/`MsgBox`に触れない(LibreOffice実行互換のため) |
| **R5** | エラーを握りつぶさない。`On Error Resume Next` は1行スコープ(直後に`On Error GoTo 0`)のみ。失敗は`modLog`に必ず残す |
| **R6** | **エラーハンドラの中で `On Error Resume Next` を書かない**(効かない)。後始末は別Subへ切り出すか、`Resume <ラベル>` でハンドラを抜けてから行う。詳細は §6-2 |

### R6 の背景 ― VBAの「稼働中のハンドラ」

VBAには **有効(enabled)なハンドラ** と **稼働中(active)なハンドラ** の区別があります。
ハンドラへ飛んだ瞬間から `Resume` / `Exit` / プロシージャ終了までは「稼働中」で、
**この間に起きたエラーは、そのプロシージャでは一切捕まえられず呼び出し元へ投げ返されます**。
`On Error Resume Next` を書いても効きません。

2026-07-30 に実機で `.doc`/`.docx`/`.pdf` の取込が全滅した原因はこれでした。

```vba
Failed:
    errDetail = 本当の原因            ' 正しく作っている
    If Not word Is Nothing Then
        On Error Resume Next          ' ← 稼働中なので効かない
        word.Quit 0                   ' ← 死んだWordを叩いて err#462
        On Error GoTo 0
    End If
    TryExtractOnce = False            ' ← ここへ到達しない
```

結果として、後始末の err#462 が呼び出し元まで飛んで**本当の原因を上書き**し、
さらに `Extract` の開き方フォールバックも PDF の Acrobat フォールバックも
**一度も走っていませんでした**（戻り値で返らず例外で抜けるため）。
落ちてはいないので、ログを見ても「462が出た」しか分かりません。

正しい書き方は2つです。

```vba
' (a) 後始末を別Subへ切り出す(呼ばれた側は新しいエラー文脈を持つ)
Failed:
    errDetail = ...
    Cleanup doc, word          ' Cleanup 内の On Error Resume Next は効く

' (b) Resume でハンドラを抜けてから後始末する
Failed:
    Dim failDesc As String: failDesc = Err.Description   ' Resume で Err は消える
    Resume FailedCleanup
FailedCleanup:
    On Error Resume Next
    ...後始末...
```

**(b) の注意**: `Resume` はエラーが起きていないと実行時エラー20になります。
`Finish:` / `Done:` のように**正常系からも落ちてくるラベル**では、
ラベルの直前に `GoTo` を置いて正常系が `Resume` を跨ぐようにしてください。

どちらの誤りも `tools/vba_lint.py` が ERROR で止めます
(`check_resume_next_inside_handler` / `check_resume_on_fallthrough_label`)。

R1の4件例外は、後から追加されたものです(初期案では機能層からUIへの参照は完全禁止でしたが、
実装を進める中で「進捗実況」「回答描画」等をUI層モジュールに書かせると今度は機能層側の
処理フローが分裂してしまう矛盾が判明し、PM裁定でこの4件だけ例外化しました)。**新しい
UIコールバックが必要になっても、まずこの4件で足りないか検討し、増やす場合はMASTER_SPEC
§3の例外リストと`tools/vba_lint.py`のR1判定を両方更新してください**(片方だけ直すと
lintが実装と食い違ったまま黙って通ってしまいます)。

`tools/README.md` の「依存層(R1)の判定基準」表のとおり、lintはディレクトリ単位で層を
判定します(`src/core`=基盤層、`src/ingest`/`src/qa`/`src/pack`/`src/stats`=中間層、
`src/ui`=UI層、`src/opt`=opt層、`src/test`=対象外)。§3の論理図とはmodDiagの扱いが
異なる(論理図では機能層だが配置は`src/core`=基盤層)ので、`modDiag`から中間層/UI層への
参照を書くとlintエラーになる点に注意してください。

## 3. データフロー

### 3-1. 取込(資料を1つ追加したとき)

```
ファイル選択(ダイアログ or フォルダ同期)
  → modExtractor.ExtractFile          抽出(拡張子ディスパッチ)
  → modChunker.ChunkPages             チャンク分割(700字/オーバーラップ150字)
  → chunk_id付番+my_knowledge追記     (embedded=0)
  → modEmbed.EmbedPending             modGateway.GetEmbedding → my_vectors追記 → embedded=1
  → my_manifest upsert(status確定)   done/partial/failed/image_pdf
  → modUIShelf.RenderShelf            カード再描画(R1例外)
```
オーケストレーションの主体は `modShelf.IngestFile`。フォルダ差分同期は
`modShelfSync.SyncNow` が新規/更新/消失を判定してから同じ`IngestFile`経路に載せます。

### 3-2. 質問(⚡すぐ聞く / 🔍しっかり調べる)

```
質問入力+モード選択
  → modRetrieve.Search                質問をベクトル化→my_vectors内積検索(+キーワード加点)
  → modUIMain.RenderSourcesPreview    出典先出し(R1例外。ドラフト生成前に表示)
  → modPrompts.BuildXxxPrompt         プロンプト組み立て(quick/deep draft/deep verify)
  → modGateway.CallLLM                AIリボンへ問い合わせ(mock_llm時はダミー応答)
  → modUIMain.RenderAnswer            回答描画+出典表示(R1例外)
```
オーケストレーションの主体は `modAsk.Answer`。🔍しっかり調べるはdraft→verifyの2段階、
⚡すぐ聞くは1段階です。検索0件のときはLLMを呼ばず定型文を返します(E0601はログのみ)。

## 5. 変更の入れ方(このリポジトリで守られてきた順序と、その理由)

```
① MASTER_SPEC.md を更新   契約(シグネチャ・シート列・エラーコード)を先に決める
② 実装(.bas/.cls)を書く   ①で決めた契約どおりに書く
③ tools/vba_lint.py の CONTRACT辞書を追従  ②で公開関数を増減したら必ず一緒に直す
④ テスト(vba_lint→run_lo_tests)を緑にする
⑤ ビルド(build_mybookshelf.py --dev/--prod)して自己検証OKを確認
```

**①を飛ばして②から始めない理由**: `tools/vba_lint.py`はMASTER_SPEC §7の契約を
人間が読んで書き起こした`CONTRACT`辞書と実装を突き合わせる仕組みです(MASTER_SPEC
本文を自動パースしているわけではありません)。実装だけ変えてMASTER_SPECを直さないと、
次にこのモジュールを触る人(人間もAIエージェントも)がMASTER_SPECを読んで「契約はこう」と
誤解したまま作業してしまいます。実際にこのプロジェクトでは、Wave2で機能層から
UIモジュールを呼ぶ実装が複数箇所で発生し、それぞれ個別にR1違反として直すのではなく、
**MASTER_SPEC §3のR1例外リストを4件に拡張する裁定を先に行ってから**、実装とlintの
CONTRACTを両方その裁定に合わせて直す、という順番で収拾しました(§3の「Wave2 PM裁定」の
注記はその記録です)。同様に、Wave3では「出典プレビューだけでは回答生成の根拠として
不十分」という問題が見つかった際も、先に`modTypes.Hit`と`modRetrieve`/`modPrompts`の
契約をMASTER_SPEC側で確定させてから実装を直しています(§7.1の「Wave3 PM裁定1」の注記)。

**③を忘れると起きること**: 新しいPublic関数を追加しても、`CONTRACT`辞書の対象モジュールが
`"closed": True`(契約にあるPublicが過不足なく揃っている必要がある)の場合、lintが
「契約に無いPublicがある」としてERRORを出します。**既存のPublic関数の中身(ロジック)だけを
直す分にはCONTRACT辞書の更新は不要**です(シグネチャが変わらないため)。関数を追加/削除/
シグネチャ変更したときだけ、MASTER_SPEC §7とlintのCONTRACT辞書を両方更新してください。

## 6. テストハーネス3層の使い方

詳細は `tools/README.md` にあります。ここではエージェント/開発者が最初に知っておくべき
要点だけをまとめます。

```bash
python3 tools/vba_lint.py          # 静的Lint(実行しない。全.bas/.clsを読むだけ)
python3 tools/run_lo_tests.py      # LibreOffice headlessでの実行テスト+コンパイルチェック
```

呼び出し順は **vba_lint.py → run_lo_tests.py**(静的チェックの方が速く、基本的な
間違いはここで先に弾ける)。

| 層 | ツール | 何を確認するか |
|---|---|---|
| 1. 静的Lint | `tools/vba_lint.py` | Option Explicit / VB_Name一致 / 30,000字以内 / 型落ち・Integer禁止 / §7公開契約との一致 / R1〜R4依存ルール / opt直接参照検出等12項目(exit code非0=違反あり) |
| 2. LibreOffice実行 | `tools/run_lo_tests.py` | モード1: 純ロジックテスト(`modTestRunner.RunAllPureTests`)を実行。モード2: 全モジュール(Excel依存含む)の構文コンパイルのみ(実行はしない) |
| 3. 実機受入 | `docs/40_受入チェックリスト15分.md` | 配布先PCでの人手確認(診断→mockでE2E→リボン実呼び出し→取込→質問→パック→終了確認) |

### 既知のLO/VBA差異(要点。全リストは`tools/README.md` §3・§4)

- LibreOffice Basicは配列を戻り値に持つ`Public Function Foo(...) As String()`をそのまま
  コンパイルできない(ハングする)。ハーネスが`.xba`変換時にだけ`As Variant`へ機械的に
  書き換えて回避している(元の`.bas`ファイル自体は変更しない。実際にビルドされる`.xlsm`は
  元の`As String()`のまま)。**新しく配列を返すPublic関数を書くときはこの制約を知っておく**。
- **セルの書式・数式・Shapes(ボタン)の実際の見た目**はLO headlessでは検証できない
  (§7.6のUI系モジュールは構文チェックは通るが、レイアウトの正しさは実機受入で確認する)。
- `Application.Run`によるリボン関数呼び出しはLO側では実行されない
  (ハーネスは実行されないコードパスとして扱う設計なので問題にはならない)。
- 32,767字を超えるセル書込み、`xlErrorHandler`経由のESC中断など、Excel API固有の
  実行時挙動もLO側では検証できない。

- **エラー処理の意味論はLOでは検証できない**。`On Error Resume Next` が稼働中ハンドラで
  無効になること(R6)、`Resume` without error が実行時エラー20になること、いずれも
  LO Basic では再現しません。**このクラスの誤りはlintでしか止められない**ため、
  `check_resume_next_inside_handler` / `check_resume_on_fallthrough_label` を
  静的側の防波堤として置いています(2026-07-30 に実機で36ファイル57箇所を検出)。

**結論(`tools/README.md`より)**: 「LOで通る」は「Excelで通る」を保証しない。両方の層に
加えて、UIレイアウトやリボン実呼び出しが絡む変更は必ず§11.3の実機受入チェックリストで
確認すること。

### 6-2. 「落ちないので気づけない」不具合を静的側で止める

実機でしか出ない不具合のうち、**LO のコンパイル・純ロジックテストを素通りする**種類は
lintに検査を足して止めています。過去に実機まで漏れた4クラスは全て検査済みです。

| 検査 | 実機で何が起きたか |
|---|---|
| `check_module_level_refs` | モジュール分割で定数が置き去りになり「変数が定義されていません」で起動不能 |
| `check_undefined_proc_refs` | 同じくヘルパーが置き去りになり「Sub または Function が定義されていません」で取込全滅 |
| `check_resume_next_inside_handler` | 後始末の失敗が本当の原因を上書きし、フォールバックが全て死んでいた |
| `check_resume_on_fallthrough_label` | 正常終了時に `Resume` を踏んで実行時エラー20 |

**新しい実機不具合を直したら、同じ型を機械が止められるかを必ず検討してください。**
止められるなら検査を足す。足せないなら、なぜ足せないのかをこの表に書く。
「気をつける」で終わらせると、同じ型が必ずもう一度来ます。

#### 2026-07-31(R7)で足せなかったもの ― 理由の記録

| 実機で何が起きたか | なぜlintで止められないか | 代わりに何をしたか |
|---|---|---|
| ダッシュボードのヘッダーボタンが**画面外**(x≈700〜920pt)に置かれ、「ナビが無い」と報告された | 「見えるかどうか」は列幅・DPI・ウィンドウ幅で決まる実行時の幾何で、静的解析からは1ptも計算できない | 座標を手で置くのをやめ、`modChrome.FlowLeft/FlowRight` に流し込ませた。枠を超える置き方が**存在しない**関数なので、算数はLO実行テストで固定できる。新しいクロムを書くときは必ずこの2関数を通すこと |
| Hubの統計タイル4枚で**値だけが消えた**(`hub_tile_empty` は0件=値は空でない) | 1つのShapeに2段落を入れて `Paragraphs(2)` に別書式を当てる方式は、はみ出した段落が描画されないだけで**エラーを出さない**。lintから見ると正常なコード。しかも `Paragraphs(2)` は他の6箇所(プロフィール・ナビ・お知らせ等)で正常に使えているため、トークン自体を禁止すると誤検知だらけになる | タイルだけ「ラベルShape+値Shape」の2枚構成にして段落操作を廃止し、描画のたびに `hub_tile_drawn idx=<n> len=<値の文字数>` を1行 usage_log へ残すようにした。**次に消えたら、値が空なのか座標が悪いのかをログだけで切り分けられる**(切り分けの手がかりを実装側に埋め込むのが、静的検査を足せないときの代替手段) |
| ナビを4枚→3枚に減らしたあと、`4 * (NAV_H + NAV_GAP)` という**枚数の直書き**が残って右列に空白が出た | 定数式が実際の描画枚数と一致しているかは、ループの回数と突き合わせないと分からない(現状のlintは手続き間の値追跡をしない) | 枚数を `NAV_COUNT` 定数に一本化し、描画ループも `For i = 0 To NAV_COUNT - 1` にした。**繰り返す数は必ず1箇所に持つ** |

## 7. ビルドの仕組み(build/build_mybookshelf.py)

```bash
python3 build/build_mybookshelf.py --dev    # mock_llm=TRUE。開発・動作確認用
python3 build/build_mybookshelf.py --prod   # mock_llm=FALSE。配布用
```

1. `build/template_skeleton.xlsm`(本物のExcelで作られた.xlsmのコピー。中の
   `vbaProject.bin`は「本物」でどのExcelでも文句なく開ける)をopenpyxlで読み込み、
   MASTER_SPEC §4の全22シートを生成する。
2. openpyxlでファイルを保存後、`build/ovba_write.py`(R35からの配布方式B・完成品vbaProject.bin生成)が
   モジュール集合全体と ThisWorkbook ストリームをビルドして `vbaProject.bin` を生成する。
   **opt機能の撤去はモジュール台帳 `build/modules.json` から該当行を1行削除するだけでよい**(コアは無傷)。
3. ビルド後、生成物を再オープンして自己検証する(モジュール集合と台帳の一致/各モジュール本文がバイト一致/
   ThisWorkbook が仕様どおり/全MODULEOFFSET=0/`_VBA_PROJECT` 無害化確認/Sheet1 codeName確認)。
   **失敗したらexit 1**。R35開発用フォールバック(`--vba-mode installer`)もこの検証を通す。

**モジュール30,000字制限**(MASTER_SPEC §7冒頭の契約上限。Excel自体のセル技術上限
32,000字より厳しく設定してある)を超えると、ビルドがその場で`BuildError`を出して止まります。
1モジュールが肥大化してきたら、`modTestsPure`→`modTestsPure2`のように分割してください
(分割時は元モジュールの末尾から新モジュールの`Run~`を呼ぶ形にすると、
`modTestRunner.RunAllPureTests`側の呼び出し一覧を変えずに済みます)。

`--allow-missing`は開発途中の動作確認用オプションで、**最終ビルドでは使用禁止**です
(モジュール台帳に列挙されたファイルの欠落を警告に緩和して続行してしまうため)。
