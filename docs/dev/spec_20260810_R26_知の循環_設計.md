# R26 知の循環・本命セット 要件定義/設計（2026-08-10 GO受領）

対象3機能: (1)一般アシスタント3段化 (2)会話メモリ一本化(モード間引き継ぎ) (3)洞察カード保存。
ソクラテスモード・週次ダイジェストは保留(ユーザー裁定)。**着手はR25(実機第11報の不具合修正)完了後**(同じチャット画面を触るため衝突回避)。

## 0. 設計原則

- 凍結モジュール(modAsk/modBoot/modShelf/modRetrieve/modPrompts)には一切触れない。3機能とも**凍結の外側で完結する設計**を採る(実現可能性は調査済み: AskGeneralはmodAppState、記憶の永続化はmodStateのキー経由で外から読み書き可能)。
- 実装は新設モジュール中心(modGenPipe/modConvBridge/modInsightCard)。容量逼迫モジュール(modApp残2,065/modGateway残1,478/modHub残187/modKnowledge残373)への追記は各1〜3行の配線のみに抑える。
- 全ての新規経路で: 失敗はusage_log/err_logへ必ず記録(無言失敗禁止)、DisplayAlerts等のUI副作用なし、LLM呼び出しはmodGateway.CallLLM経由(mock_llm対応=devビルドで検証可能)。

## 1. 一般アシスタント3段化(R26-1)

### 現状(調査確定済み)

- modApp.bas:191-199 一般分岐はsendSpeed(quick/deep/thorough)を**無視**して `AskGeneral(q, "")` を呼ぶ。
- modAppState.AskGeneral(:118-185)は常に quick_effort(low)/quick_verbosity(low)/quick_model 固定の1回呼び出し。
- モードトグルUI(modApp.OnToggleSpeed)は既存。トースト文言に「一般アシスタントでは使われない」旨の注記(R21)があり、これを撤去する。

### 要件

| モード | 呼び出し構成 | effort/verbosity | 狙いの体感 |
|---|---|---|---|
| ⚡すぐ聞く | 1回(現行同等) | low/low | 即答・簡潔 |
| 🔍しっかり聞く | 1回+構造化指示 | **medium**/high | 深さと構造(前提→本論→含意→次の一手) |
| 入念に聞く | 多段: 起草→検証→改稿(最大2周) | high/high | 検証済みの深い回答 |

- effort設計の根拠(Webリサーチ確定): high vs medium は一般タスクで有意差が薄く、highが効くのは多段推論。しっかり=medium+プロンプト構造化が費用対効果最良。入念の起草段のみhigh。
- 入念の多段パイプライン(CoVe型・modGenPipe新設):
  1. **起草**: 深掘りプロンプトで回答生成。
  2. **検証**: 別呼び出し(検証者ペルソナ)が「回答の主張から検証質問を3〜5個生成し、各々に自答して、誤り・根拠薄弱・見落としを列挙。問題なければ verdict:PASS」形式で査読(自己採点の楽観バイアス対策=起草と別呼び出し・別ペルソナ。判定形式を機械可読に固定)。
  3. **改稿**: 検証で指摘があった場合のみ、指摘を反映して改稿。
  4. ループ上限: 検証→改稿を**最大2周**(実証知見: 自己改善は2〜4周で頭打ち、大半は1〜2周目)。verdict:PASSで早期終了。
  5. 回答フッター(R20⑧の既存機構)に「入念に聞く・検証n回」を表示(体感差の可視化)。
- config新キー(既定値): gen_deep_effort=medium / gen_deep_verbosity=high / gen_thorough_effort=high / gen_thorough_verify_effort=medium / gen_thorough_loops_max=2。
- usage_log: `gen_mode`(mode/所要ms/検証周回数/PASS到達か)を毎回記録。検証パース失敗時は`gen_verify_parse_fail`を記録し**起草回答をそのまま返す**(利用者を待たせて壊すより退行)。
- 配線: modApp:199 を `AskGeneral(q, "", sendSpeed)` へ(1行)。AskGeneralは第3引数(Optional mode, 既定"quick")を受け、quick=現行/deep=プロンプト+effort差し替え/thorough=modGenPipe.RunThorough委譲。
- プロンプト(modGenPipe内にPrivate配置・日本語):
  - deep追記: 「まず質問の前提と論点を1〜2行で整理してから、構造立てて答える。表面的な一般論で止まらず、判断基準・具体例・注意点まで踏み込む。最後に『次に考えるべき問い』を1つ添える。」
  - thorough起草: deep追記+「反対説・例外・限界条件も自ら挙げる」。
  - thorough検証: 「あなたは起草者とは別の査読者。回答の各主張について検証質問を作り、自答し、誤り/根拠不足/見落としを specific に列挙。問題がなければ1行目に verdict:PASS とだけ書く。」

## 2. 会話メモリ一本化(R26-2)

### 現状(調査確定済み)

- RAG側: modAsk内 mPrevU/mPrevA、永続化キー nexus_ask_prevu/preva(modState経由、**modAskは毎回LoadStateで読む=外から書けば注入できる**)。
- 一般側: modAppState内 mGenPrevU/mGenPrevA、キー nexus_gen_prevu/preva。
- モード切替時は**意図的に破棄**(modApp.bas:600-605, :734 ClearGeneralMemory)。ここが「文脈が切れる」正体。

### 要件(凍結安全な「橋渡し」方式)

- 新設 modConvBridge: モード切替時(modApp.OnToggleModeの切替確定点)に、**切替元の直前1往復(質問+回答)を切替先の記憶キーへ写す**。
  - RAG→一般: nexus_ask_prevu/preva → nexus_gen_prevu/preva へコピー(mGenPrevU/mGenPrevAへも反映するためmodAppState側に受け口SetGeneralMemoryを1つ追加)。
  - 一般→RAG: nexus_gen_prevu/preva → nexus_ask_prevu/preva へコピー(modAskは次のAnswerでLoadStateするため注入が効く。modAsk不触)。
  - コピー時、切替先の回答側テキスト先頭に `【直前の${元モード名}での文脈】` を1行付与(LLMが出所を誤認しない+利用者にも自然)。長さ上限: 各4,000字で切り詰め(既存記憶の上限作法に合わせる。超過分は先頭を落とす)。
- チャット画面に切替トースト: 「文脈を引き継ぎました(直前の1往復)。引き継がず新規で始める場合は🧹クリア」— 既存のクリアボタンが退避手段になるため新UI不要。
- config: conv_bridge=on(既定)。offで現行(破棄)動作。
- usage_log: `memory_carry`(from/to/文字数)。
- ユースケース検証シナリオ(受け入れ基準): 社内ナレッジで「約款の免責事由は?」→回答→一般へ切替→「この条文の趣旨を保険実務の観点で壁打ちしたい」→**直前の条文内容を踏まえた応答になる**こと(mock_llmではプロンプトに前文脈が含まれることをログで確認)。

## 3. 洞察カード保存(R26-3)

### 要件

- チャットの回答直後に「💾この会話を本棚に保存」導線を出す(常設ピルではなく、**回答フッター行の末尾リンク**として描画=ヘッダーの9ピル過密を避ける。クリックはShapeで受ける)。
- 押下時: InputBoxで題名(既定値=質問文の先頭24字)→ 直前1往復(Q+A)を**通常の取込パイプラインでmy_knowledgeへ登録**(モード問わず。検索で再利用可能にする=ユーザーの「ストックに足す」の実現)。
- **汚染防止(confidence-aware RAGの3層のうち、凍結制約下で実装可能な出所ラベル層を採用)**:
  - 資料名を `💭考察メモ_${題名}` に固定(検索結果・出典表示・本棚の全てで一次資料と一目で区別が付く。modRetrieve不触で成立する唯一の防御層)。
  - 本文先頭に `[このメモはAIとの対話から保存された考察であり、一次資料ではありません。出典として扱わず、根拠は原典を確認すること]` を定型で付与(LLMが出典昇格するのを抑止)。
  - 本棚では💭アイコンで表示(既存のカード描画に資料名先頭絵文字が出る仕組みに乗る)。
- 実装: modInsightCard新設。取込はテキスト直取込の既存経路を再利用(実装調査で入口を特定し、無ければmodVaultのチャンク書込ユーティリティで最小実装。**modShelf/modChunkerは凍結・逼迫のため不触**)。埋め込み生成は既存のembed経路(modGateway)。
- usage_log: `insight_saved`(題名/文字数/チャンク数)。失敗時 `insight_save_fail`+理由。
- 受け入れ基準: 保存→本棚に💭カードが出る→社内ナレッジ検索でヒットし得る→出典表示に💭考察メモ名が出る、の一連をdev(mock)で確認。

## 4. 横断: 導線・UIUX

- モード説明(modMode.Description)を3段の実際の差が伝わる文言へ更新(「すぐ=即答/しっかり=構造化して深く/入念=下書きを自己検証してから」)。
- 初回ヘルプ(docs/10とかんたんガイド)へ3段の説明と💾保存・文脈引き継ぎの説明を追記。
- 待機表示: 入念は多段のため進捗バナーに段階表示(起草中→検証中→改稿中)。既存のRAG進捗バナー機構を流用。

## 5. 検証計画

- 純関数テスト(modTestsPure24新設): 検証verdictパース(PASS/指摘あり/形式崩れ)、ループ上限判定、記憶コピーの切り詰め(4,000字境界・全角)、考察メモの資料名/前置き定型の生成、モード分岐テーブル。
- devビルド(mock_llm)での手動シナリオ: 3モードの応答差(フッター表示含む)/切替引き継ぎ/💾保存→本棚反映。
- 敵対的レビュー観点(実装後): 進捗バナーの残存(③の教訓)/InputBoxキャンセル経路/記憶コピーの二重付与/mock時の多段呼び出し回数/新configキーの後方互換(既存ブックのconfigに無いキー→既定値)。
