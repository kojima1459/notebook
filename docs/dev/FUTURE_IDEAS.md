# Nexus Agent — 拡張アイデア集(採用・見送りの判断根拠つき)

このプロダクトの開発過程で検討し、**あえて実装しなかった**アイデアを、
理由とともに記録する。「なぜやらなかったか」は「何を実装したか」と同じ
くらい重要な設計情報であり、将来同じ議論を繰り返さないための記録。

## 1. スケール時に検討すべき構想(コード化せず、まず運用/合意で解決すべきもの)

### 1-1. Mentor(専門家)のパンク対策 — チケット制/掲示板方式
**課題**: 称号システムにより「〇〇さんに聞けば早い」に質問が集中し、
特定の優秀な社員の負荷が偏る可能性がある。

**構想**: 質問送信にEXPを消費させる「チケット制」、または特定の個人を
指名しない「オープン質問掲示板」方式。

**現時点で実装しない理由**: MVP段階でVBAに組み込むと複雑さが増し
バグの温床になる。ユーザー数・実際の質問集中度が分からない段階での
過剰設計を避けた。**指名質問の負荷が実際に問題化した時点**で、
`modMentor`に「今週の受信数が閾値超なら一時的にボタンを隠す」程度の
軽量ガードを追加するのが現実的な次の一手。

### 1-2. 腐ったナレッジの更新エコシステム — 懸賞金(Bounty)方式
**課題**: ノイズ投票で「古い/誤った情報」と分かっても、誰が正しい情報に
更新するかのインセンティブが無い。

**構想**: ノイズ投票で除外された資料を「更新待ちリスト」に載せ、正しい
情報へ更新してパック再配布した社員に通常の3倍のEXPを付与する。

**現時点で実装しない理由**: 「更新待ちリスト」UI・「これは更新版です」
という関連付けロジックが新たに必要で、既存のシンプルな除外/復帰
フローより複雑になる。除外→管理者による調査→手動での資料差し替えという
現状フローがMVPとしては十分機能する。ユーザー数が増え、ノイズ除外の
発生頻度が高まった段階で再検討。

## 2. コード化を検討し、意図的に不採用としたもの

### 2-1. バイナリ量子化Lv.2〜MAX(GDI+直接描画)
**構想**: Shape描画を廃止し、Windows GDI+ APIを直接呼び出してピクセル
単位でUIを描画すれば描画負荷が実質ゼロになり60fpsで動く。

**不採用の理由**: 大量の`Declare`/ポインタ操作が必須になり、本プロダクトが
一貫して守ってきた「Declare文を1つも使わない(32/64bit環境依存を
原理的に排除する)」という設計原則に真っ向から反する。自己インストーラ
配布との相性も未知数。保守難易度が跳ね上がる割に、現状のShape描画で
実用上十分な体感速度(考え中バブル等の体感速度ハックで補強済み)が
出ている。**費用対効果が見合わないため却下**。

### 2-2. リアルタイムP2Pプレゼンス(タイピングインジケータ)
**構想**: 共有フォルダに0バイトの一時ファイルを置き、0.5秒間隔で監視
して「〇〇さんが入力中...」を表示する。

**不採用の理由**: (1) 0.5秒間隔のポーリングタイマーは、Endgame監査で
固めた「多重OnTime干渉」のリスク面を再び広げる。(2) 社内ナレッジ
ツールとしてのROIが低い(チャットアプリの模倣であり、業務効率化には
直結しない)ギミック性が強い。

### 2-3. Windows APIフック(SetWindowsHookEx等)によるマウスホイール制御
**構想**: SPA感を出すため、ネイティブのスクロールバーを隠しマウス
ホイールを独自ハンドリングする。

**不採用の理由**: フック系APIはエラー発生時にExcelどころかWindows全体の
挙動に影響しうる「禁断の魔法」。`FreezePanes`(ウィンドウ枠の固定)による
標準スクロール活用で同等の体験を安全に実現できている。

### 2-5. 確信度の自己申告([網羅性: 高/中/低])
**構想**: LLMに回答の確信度を自己申告させ、UIに表示する。

**不採用の理由**: LLMの自信自己申告は較正されていない(実際の正確性と
相関が弱い)ことが知られている。保険約款という正確性が重要な文脈で、
「網羅性: 高」という**偽の精度表示**が出た場合、確信度表示が無い場合より
悪い結果(過信による事故)を招くリスクがある。既存の`strict_grounding`
(資料に無ければ「判断できません」と明言させる)の方が安全側に倒れた
設計として優れていると判断。

## 3. 採用済みだが、さらに発展させられる方向性(参考)

- **チーム連帯ボードの部署別内訳**: 現状は組織全体合計のみ。ビーコンに
  `user_department`(既存config)を含めれば、部署別の節約時間比較が
  低リスクで追加できる(`modBoard`のビーコン書式に1列足すだけ)。
- **Mentor返信の連鎖**: 現状は1往復(質問→返信)のみ。返信にも返信ボタンを
  付ければ本格的なスレッド化が可能(設計はほぼ流用できる)。
- **ダッシュボードへのストリーク/称号の統合表示**: 現状はサイドバー
  ウィジェットのみ。`modDash`(ダッシュボード画面)側にも称号・スキン
  解放状況を表示すれば、達成感の可視化面がさらに強化される。
- **設定画面の新設**: `official_pack_path`・`org_saved_goal_h`等、
  現状ヘルプ経由のInputBoxで個別対応しているconfig項目が増えてきたら、
  1つの「⚙設定」画面にまとめることを検討(相棒の命名等、見送った
  機能の受け皿にもなる)。
