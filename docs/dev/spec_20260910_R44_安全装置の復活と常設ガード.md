# R44 仕様 — 安全装置の復活と常設ガード（2026-09-10）

**起点**: ユーザーの問い「本当に製品側が効くの？ 出力プロンプトまで変えるのはどうなの？ 他に影響でない？ 木を見て森を見ずな気がする」。
R43 クローズ後、教えてBOX 12万件から作った部門ナレッジ（7,949件）の検索テストで
**「本棚に答えが無い質問でも 38% は『答えがあるとき』と同じスコアが1位に出る」**を実測したのが直接のきっかけ。

司令塔は当初「回答生成プロンプトに『結論を先に・根拠を示す・相談先を案内する』を足す」と提案したが、
**ユーザーの指摘どおりこれは空提案だった。撤回する。**

## §0. 撤回した提案とその理由（一次情報の確認）

`src/qa/modPrompts.bas` を読み直した結果、提案した内容は**すべて実装済み**だった。

| 提案しようとしたこと | 既存の実装 | 出荷既定 |
|---|---|---|
| 結論を先に | `StyleInstruction`「【結論先行】必ず最初の1～2行で結論を言い切る」（modPrompts.bas:471） | 有効 |
| 結論→根拠→注意点の構成 | 同「【構成】結論 → 根拠や詳細(箇条書き) → 注意点・例外」 | 有効 |
| 根拠（出典）を示す | `CitationInstruction`「各主張の直後に出典」（:494） | 有効 |
| 数値を捏造しない | `DomainGuardInstruction`「抜粋に無い数値は絶対に書かず『資料に記載なし』」（:513） | 有効 |
| 裏付けの弱い記述に印 | 同「【確認マーク】…文末に (要確認)」 | 有効 |
| 資料のみで答える | `GroundingInstruction`（:526） | `strict_grounding=True` |

**つまりプロンプトは既に正しい。** 同じことをもう一度書いても出力は変わらず、
一般モード・壁打ち・NotebookLM 的な使い方への副作用だけが増える。**プロンプトは触らない。**

## §1. 本当の足かせ（実測で特定）

### 1-1. 何が起きているか

検索スコアは **「ベクトル類似度 ＋ KeyScore × 0.06」の合計**である（`modRetrieve.bas:280` / `SPARSE_WEIGHT=0.06`）。
一方、利用者を守る2つの装置は、**その合計を絶対値のしきい値と比べている**。

| 装置 | 実装 | しきい値 |
|---|---|---|
| 低関連度の⚠ | `modAskRetrieve.ApplyLowHitWarning` | `low_hit_warn_score` = **0.3** |
| 信頼度バッジ 🟢🟡🔴 | `modAsk.LastConfidence`（:381） | `confidence_score_x100` = **55** → 0.55 |

`KeyScore` の上限は config `sparse_keyscore_cap`（**旧既定 10**）。
**加点だけで 10 × 0.06 = 0.600** に達し、**0.3 も 0.55 も無条件に超える。**

### 1-2. 実測（教えてBOX ナレッジ 10,996 かけら・質問60件）

| 測ったこと | 結果 |
|---|---|
| キーワード加点だけで 0.55 を超えるかけらの数 | **中央 403 個**（最小 22・最大 3,737） |
| そのようなかけらが2個以上ある質問の割合 | **100%** → 🟢「本棚の資料と強く一致」が**常時点灯** |
| キーワード加点だけで 0.30 を超えるかけらの数 | 中央 2,340 個（最小 227） |
| ⚠ 低関連度警告が出る質問の割合 | **0%**（原理的に出ない） |

この数字は**密検索の点を1点も足していない**。意味がまったく合っていなくても、こうなる。
先に測った「答えが無い質問の 38% が答えがあるときと同じスコアになる」の機械的な正体がこれである。

### 1-3. なぜこれが「部分最適ではない」か

- **資料の種類に依存しない。** Excel でも PDF でも、質問の語を数個含むかけらがあれば同じ。
- **モードに依存しない。** 即答・精査・俯瞰のどれでも同じスコアを見ている。
- **プロンプトでは直せない。** LLM に「自信がないと言え」と頼む話ではなく、
  **UI が『強く一致』と表示している**という表示側の事実誤認。
- 既存コードも同種の問題を認識していた: `modAskRetrieve` の分散判定に
  「SparseBoost 無上限が起こすスケール崩壊（実機 deep gap=390）」「キーワード加点そのものの
  遮断は未達（**要裁定・報告済み**）」という記述がある。**その未裁定の宿題が本件。**

## §2. 裁定

### 2-1. `sparse_keyscore_cap` を 10 → 3（config 既定）

**根拠は算術**: 3 × 0.06 = **0.18**。低関連度の 0.30 にも信頼度の 0.55 にも届かない。
**キーワード一致だけでは、もう安全装置を突破できない。**

**反証を試みた**（加点を下げると「専門用語1語での救済」が壊れるはず）。
その語が1かけらにしか無い専門用語 60 件で実測:

| 加点上限 | 1位で当てる | 上位5 |
|---|---|---|
| 10（旧既定） | 100.0% | 100.0% |
| 5 | 100.0% | 100.0% |
| **3（新既定）** | **100.0%** | **100.0%** |
| 2 | 98.3% | 100.0% |
| 1 | 90.0% | 96.7% |
| 0（加点なし） | 41.7% | 68.3% |

**上限3は救済を1件も失わない。** 0 にすると崩壊するので、加点そのものは必要（この設計判断は正しい）。
一般の質問での順位も実測で悪化しない（伏せた実データ300件・上位5件: 上限10で66.3% → 上限3で68.7%）。

**上書きインストールでも届く**: `modMigrate` の引き継ぎは**ホワイトリスト方式**で、
`sparse_keyscore_cap` は `CFG_KEEP_KEYS` に無い。旧ブックの 10 が新版へ復活することはない。

**注意**: `modSparse.EffectiveKeyScoreCap` はセッション内キャッシュなので、
config を書き換えたときはブックを開き直す必要がある（既存仕様）。

### 2-2. 常設ガード（ユーザー要望・層1 GO 済）

> 「AIによる出力なので必ず出典元を確認した上で判断すること、というガード文言は入れるべき。じゃないと事故が起きるよね」

**プロンプトではなくコードで出す。** LLM に頼むと、書く回と書かない回ができる。

- 文言（単一情報源 `modMode.GuardNoteText`）:
  **`※ AIが資料から作った回答です。使う前に出典を開いて原文を確かめてください。`**
- **末尾に置く。** 先頭に置くと `modLiveStyle.LeadParaIndex`（結論を12pt太字にする段落判定）が
  毎回ガード文を掴み、画面で一番大きい文字が注意書きになる（R43 の ⚠ と 📜 で実際に起きた型）。
- **8pt・muted で描く**（`modLiveStyle.StyleAnswerParas` に「行頭が ※ の段落」の規則を追加）。
  毎回出るものなので、視界には入るが主役にはしない。出典タグと同じ扱い。
- **config `answer_guard_note`（既定 TRUE）で消せる。**
- 本棚を使った回答にだけ付く（`modAsk` の合流点 :283 が `ok And nHits > 0` のときだけ通す既存経路）。
  一般モードの壁打ちには付かない ＝ 確かめる出典が無い回で「出典を確かめろ」と言わない。

### 2-3. 表示専用の注意書きを1か所へ（`modMode.DisplayNotes`）

⚠（条件つき・先頭）と ※（常設・末尾）を**別々の場所で足すと組み合わせ事故**になる
（⚠ の回だけ ※ が消える／前置きが二重になる）。純関数1本に順序・重複排除・有効無効を閉じた。

- `modMode.DisplayNotes(result, maxScore, warnOn, threshold, guardOn)` … 純関数（LO 実行テスト可）
- `modMode.GuardNoteText()` / `modMode.LowHitNoteText()` … 文言の単一情報源
- `modAskRetrieve.ApplyLowHitWarning` は **config を読み最高スコアを出すだけ**に縮退（凍結モジュールは不触）
- **俯瞰ターン（`WasGlobalTurn`）は ⚠ を出さないがガードは出す。**
  俯瞰の hits は score=0 が正しい値なので ⚠ は事実と逆になるが、
  「出典を確かめてから使う」はどのターンでも等しく正しい。

### 2-4. プロンプトの**穴**を塞ぐ（§0 の訂正・6視点の解剖で発見）

§0 で「プロンプトは既に正しい」と書いたが、**それは経路によって正しくなかった。**
6視点の並行解剖（司令塔が全件を一次情報で再検証）が、注入マトリクスの穴を出した。

| 経路（利用者の操作） | DomainGuard（数値の厳格性・(要確認)・断定の禁止） |
|---|---|
| ⚡すぐ聞く `BuildQuickPrompt` | ○ modPrompts.bas:71 |
| 🔍しっかり調べる の4段 `BuildDeepDraftPrompt` / `BuildDeepVerifyPrompt` | ○ |
| **🔍しっかり調べる の既定経路 `modAskOnePass.BuildOnePassPrompt`** | **✕ 無し** |
| **俯瞰（全体像を教えて）`modAskGlobal.BuildGlobalPrompt`** | **✕ 無し** |

**`thorough_onepass` は出荷既定 `on`。** `modAskThorough` は `TryOnePass` が成功した時点で
`Exit Function` するので、**精査モードは4段（ガードあり）へ一度も行かない。**
つまり **「ここ一番で外したくないときに選ぶモードだけ、数値の捏造ガードが外れていた」。**
`ThoroughStyleAddendum` の「断定できない点は『資料からは確認できません』と明示」1文では、
条文番号・金額・期限の捏造は止まらない。

**裁定**: `modPrompts.DomainGuardInstruction` の**可視性だけ** Private→Public にし
（本文は1文字も変えない）、`modAskOnePass` と `modAskGlobal` から1行で呼ぶ。
文言を複製する案は採らない（R38 F7 が単一情報源へ寄せた裁定と正面から矛盾するため）。

**これは「プロンプトを書き換える」ではなく「既にある指示を、抜けていた経路へ通す」。**
新しい指示は1文字も足していない。だから一般モード・壁打ち・NotebookLM 的な使い方への
副作用は無い（それらの経路のプロンプトは触っていない）。

### 2-5. R43 で作った不整合の是正（セル番地の位置）

R43 §4 で Excel のセル番地を**行頭**から**値の直前**（`[B42] 値`）へ変え、
単一情報源の `modPrompts.CitationInstruction` は直した。ところが
`modAskOnePass.bas:560` と `modAskGlobal.bas:539` は**手書きの複製**だったため、
**「抜粋の行頭にある [A6]」と、モデルへ嘘の位置を教えたまま**だった。

R43 の直後に配った部門ナレッジは Excel なので、精査・俯瞰でその資料を引くと
番地の写し方が壊れる。**CLAUDE.md §9（変更したら全呼び出し箇所を grep）の取り残し。**
両方を「値の直前にある [B42]」へ是正した。**複製そのものは残っている**（§3 の課題）。

### 2-6. 触らなかったもの（意図的）

| 触らなかったもの | 理由 |
|---|---|
| `modPrompts`（凍結） | §0 のとおり既に正しい。触ると全モードに波及する |

## §3. 残した課題（根治は別ラウンド・ユーザー裁定待ち）

**2-1 は緩和であって根治ではない。** 加点は 0.18 に縮んだが、**混ざっていること自体**は変わらない。
根治は「順位づけの点数」と「根拠の強さ」を分けること:

- `Hit` 型に `dense As Double` を足し、`modRetrieve` が加点前の素の類似度も入れる
- `modAsk.LastConfidence` は `dense` だけで判定する
- 影響範囲: `Hit` は 20 ファイルで使われるが**シートには保存されない**（追加は後方互換）。
  ただし `modRetrieve` と `modAsk` は**凍結**なので、実施には凍結解除の GO が要る。

**しきい値の実機校正も未了。** 0.3 / 0.55 が社内AIリボンの埋め込みのスケールに合っているかは、
実機のスコア分布を見ないと分からない。R44 は「加点で汚さない」ところまで。

### 解剖の結果（20エージェント・所見55件・敵対的検証14件 → **生存3件・却下11件**）

**却下11件のうち8件は「R44 で既に直っている」による却下**だった。検証班は HEAD（`5d7c2d3`）を読み、
`modAskGlobal.bas:550 に DomainGuardInstruction が入っている（決定的）`／

**＝R44 の修正が意図どおり入ったことの、独立した検証になっている。**

**司令塔の理解を訂正させた本物の反証が2件**（記録として残す）:

1. **「1位と2位の差はチャンク単位で一度も計算していない」は誤り。**
   `modAskRetrieve.bas:82-84` が `modSparse.DiversitySwapPick` を通しており、
   チャンク単位の相対比較は**既に存在する**。R45 #2 を設計するときは、
   ゼロから作るのではなく**この既存の計器を判定へ繋ぐ**方向で検討すること。
2. **「スコア下限が無く『答えが無い』経路が死んでいる」も過大。**
   反証班の指摘どおり、最初の grep（`min_score|score_floor|MIN_SCORE`）が
   実際の識別子と一致しておらず、生きている安全装置を見落としていた。
   **「無い」と言う前に探索範囲を書く**（CLAUDE.md §3-2）の実例。

**生存3件はすべて「一般モード（壁打ち）と橋渡し」**で、いずれも層1（体験が変わる）。
反証班自身が「ここは実装で決めずユーザー裁定へ」と書いている。§3 の表 #5 に集約した。

## §5. 実機で見てほしいこと

1. 回答の末尾に小さく `※ AIが資料から作った回答です。…` が出る（毎回・8pt・淡色）
2. 結論の12pt太字が**従来どおり効いている**（ガードに奪われていない）
3. 本棚に無いことを聞いたとき、バッジが 🟢 のままではなく 🟡 か 🔴 に落ちる
4. 専門用語1語（例: 特約名そのもの）で聞いて、従来どおり当たる
5. 着せ替えを変えてもガード文が読める（muted の可読性）
