# R49 憲章改訂案 ―― 目的を「削る」から「ゼロにする」へ

起草: Fable司令塔 2026-09-18 / **改訂は憲章 §6 によりユーザー裁定事項。これは案であって決定ではない。**

---

## 0. なぜ改訂を提案するか

2026-09-18、プロダクト全体の監査を8観点・40エージェント・敵対的反証つきで実施した。
判定基準には現行の憲章 §1 を使った。その結果、**基準そのものが実際の目標より小さい**ことが
分かった。

| | 書いてあること | 実際にやろうとしていること |
|---|---|---|
| **目的**（§1） | 調べ物の時間を**削り**、個人の知恵を部門の資産にする | **照会業務をゼロにする** |
| **利用者像**（§2） | 保険営業の現場の**営業所員** | **全社員（約12,000名）** |

憲章は R10（2026-07-31）の実機初報を受けて制定された。当時の射程としては正しい。
だが以後50ラウンド近く、**この基準で全ての裁定を行ってきた**。

CLAUDE.md §14 が言うとおり「川の上流が汚ければ下流も汚い」。**憲章はこのプロダクトの
最上流**であり、ここが1段ズレたまま採点を続けると、監査そのものが目標を低く見積もる。

実際、監査の指摘のうち2件は、目的の取り方で重大度が変わった。

| 指摘 | 「削る」が目的なら | 「ゼロにする」が目的なら |
|---|---|---|
| A-4 人に聞いた答えがナレッジに戻らない | あれば良い機能 | **ループが閉じていない＝目的そのものが未達** |
| A-3 ノイズ報告に取り消し導線が無い | 使い勝手の問題 | **全社規模では誤操作は確率ではなく確定事象** |

## 1. 「削る」と「ゼロにする」は、必要な設計が違う

ここが改訂案の核心なので、丁寧に書く。

### 1-1. 当たらなかった質問の扱いが、逆になる

- **「削る」が目的なら**：8割当たれば成功。当たらない2割は、**人に聞けばいい**。
  だから 🔴 を出して「うのみにしないでください」と言えば、誠実さは保たれる。
- **「ゼロにする」が目的なら**：**当たらない2割こそが照会そのもの**。
  🔴 が出た質問をどう吸収するかが、設計の中心に来る。

いまの実装には Mentor（資料の作成者を特定して質問を送る）がある。だが返信は
チャットバブルと usage_log に残るだけで、**`modVault.RegisterKnowledgeText` を一度も
通らない**（`src/ui/modMentor.bas:330-343`。`RegisterKnowledgeText` を src 全体で grep して
modMentor からの呼び出しは 0 件）。

**人が出した答えが知識に戻らないので、同じ照会が次の人にも必ず起きる。**
これは機能の不足ではなく、**「削る」を前提に設計されたから、閉じる必要が無かった**のである。

### 1-2. 「自分で資料を入れる」が成立しなくなる

- **「削る」が目的なら**：自分がよく使う資料を自分で入れるのは自然な運用。
- **「ゼロにする」が目的なら**：照会は **「自分が持っていない知識」** について起きる。
  自分が入れた資料にしか答えられない道具は、原理的に照会を吸収できない。

そして 12,000人が各自で資料を集めて入れるのは現実的でない。実測（`dist/MyBookshelf.xlsm` を
openpyxl で開いて確認）では **`seed_meta` / `seed_chunks` / `seed_vectors` は全て1行（ヘッダのみ）**
＝初期ナレッジ0件。

> **これが監査A観点の結論であり、このプロダクト最大の足かせである。**
> 「全社の知識を1箇所に置き、全員がそこを読む」器が存在せず、代わりに
> 「各自が自分の器を満たし、たまにパックで配る」形になっている。

### 1-3. 誠実さの基準が一段上がる

- **「削る」が目的なら**：バッジは「念のため確認してね」の合図でよい。
- **「ゼロにする」が目的なら**：全社員が**業務判断に使う**。
  バッジの精度そのものが品質になる。

監査 C-2（私が独立に裏どり済み）：`modSparse.bas:82` の `MAX_KEYS = 8` により
coverage が取りうる値は `0 / 0.125 / … / 0.875 / 1.0` の離散値のみ。一方 amber 閾値は
0.9。**0.9 以上を満たすのは 1.0 だけ**なので、実際の判定はこうなっている。

| 実際の挙動 | 条件 |
|---|---|
| 🟢 | キーが**全部**見つかった かつ 山が尖っている |
| 🟡 | キーが**全部**見つかった かつ 山が平ら |
| 🔴 | キーが**1つでも**欠けた |

`conf_cov_amber_x100` は 0.876〜1.0 のどの値を入れても挙動が変わらない **死んだつまみ**である。
R46 で「しきい値1本の実質2値をやめる」として作り直したが、**coverage 側は2値のまま**だった。

### 1-4. 「1人の熱心な人が運用できる」では足りなくなる

部門正典を発行できるのは `publish_key` を持つブックだけで、そのブックは
`--publisher` と環境変数を使って Python でビルドし直した別物でしか作れない
（`build/build_mybookshelf.py:3959-3971`）。

つまり**正典を出せるのはリポジトリとビルド環境を持つ1人だけ**で、これは憲章 §1 が
存在意義に掲げた「追加インストール不要・Excel 1つで完結」とは別の世界の話になっている。

「削る」なら1人の熱心な人がいれば回る。**「全社員が使う」なら、運用の担い手そのものを
設計に含めないと回らない。**

### 1-5. 検問の意味が変わる

- **「削る」が目的なら**：検問は開発者が自分を律するルール。
- **「全社員に配る」が目的なら**：検問は **12,000人に配る前の最後の砦**。

監査 B-1 / G-1：**R47 で「人の注意力では止まらないから機械にした」と宣言した検問2本が、
どちらも自己無効化している。** `doc_gate` の容量台帳検査は書式違いで守るべき台帳を
1行も見ておらず、孤児Public検査は過去の監査報告書を救済辞書にしている。
**どちらも ERROR 0 を返しながら、当の失敗を出荷zipに載せていた。**

## 2. 改訂案（§1 と §2 のみ。§3〜§5 は変更しない）

### 2-1. §1 プロダクトの目的

**現行:**
> 保険営業の現場で、散在する資料とナレッジを「聞けばすぐ返ってくる」形に
> 変え、調べ物の時間を削り、個人の知恵を部門の資産にする。
> 追加インストール不要・Excelファイル1つ(+同梱フォルダ)で完結することが
> 存在意義であり、管理された会社端末でそのまま動くことが生命線である。

**改訂案:**
> 社内の**照会業務をゼロにする**。すなわち「人に聞かないと分からない」を
> 「聞けばすぐ返ってくる」へ置き換え、**答えられなかった質問を、次の人のための
> 知識に変える**。個人の知恵を部門の資産にし、部門の資産を全社の資産にする。
>
> 追加インストール不要・Excelファイル1つ(+同梱フォルダ)で完結することが
> 存在意義であり、管理された会社端末でそのまま動くことが生命線である。
>
> **「削る」ではなく「ゼロにする」と書いた理由**: この2つは必要な設計が違う。
> 「削る」なら当たらなかった質問は人に聞けばよく、🔴 を出せば誠実さは保たれる。
> 「ゼロにする」なら**当たらなかった質問こそが照会そのもの**であり、それを
> 吸収する経路（人へ繋ぐ → 答えを知識へ戻す → 次から機械が答える）が
> 閉じていなければ目的に届かない。**答えの質だけでなく、ループが閉じているかで測る。**

### 2-2. §2 利用者像と前提環境

**現行:**
> - 利用者: ITに詳しくない営業所員。エラーコードもフォルダ構成も知らない。
>   「わけの分からない表示」が一度出たら、その機能は二度と使われない。

**改訂案:**
> - 利用者: **全社員（約12,000名）**。ITに詳しくない人を基準にする。
>   エラーコードもフォルダ構成も知らない。「わけの分からない表示」が一度出たら、
>   その機能は二度と使われない。
> - **その規模で起きること**: 誤操作は確率ではなく**確定事象**になる。
>   1万人が1回ずつ触れば、1%の誤操作は100人に起きる。
>   **取り消せない操作を、既定の位置に置いてはならない。**
> - **運用の担い手も設計に含める**: 知識を入れる人・正典を出す人・
>   投書を読む人が「誰か」を決めずに配ると、その全員分の照会が新しく生まれる。
>   **照会を減らす道具が、新しい照会を生んではならない。**

（`§2` の環境・検証の構造的制約の2項は**変更しない**。Windows / Excel 32bit /
管理端末 / 実機でしか確かめられない層、はそのまま有効。）

### 2-3. §3〜§5 は変更しない

体験原則（UXの憲法）・工学原則（コードの憲法）・プロセス原則は、いずれも
改訂後の目的でも正しい。**むしろ重みが増す。**

- §3-5「利用者のデータは失敗しても失わない」→ A-3（ノイズ報告が取り消せない）が
  この条項の違反であることが、全社規模では一層明確になる
- §4-1「無言の失敗禁止」→ 監査E観点の「失敗を表す値を作ったのに読む側が無い」型が
  この条項の系統的違反である
- §4-6「WARN帯に機能を足さない」→ **ただし後述 §3-3 の裁定次第で前提が消える**

## 2-4. 【裁定済み 2026-09-18】PO による目的の言語化（これが正典）

D1〜D4 は「司令塔の推奨に一任する」との裁定を受けた。**あわせて PO 自身が目的を
言語化した。これが §2-1 の案より具体的なので、憲章にはこちらを採用した。**

> 大きな目的はこのプロダクトを使い**営業が自走し自分で照会を完結**させ、
> **おしえてBOX というクソな照会システム利用者数が減り**、
> **各々が使うアプリケーションが使用頻度に応じて自己成長自己改善し質を高めていくこと**。
> そして **FBや意見で誤った出力や質の低い出力は発行者側で集約し出力精度を高められる**
> ようにして**安定的かつ持続的に運営保守**していけること。
>
> **難しい操作はダメ。使いやすく没入しやすく美しいUIUXで仕事の現場に溶け込むこと。
> 相棒となることだから。**

この文には、私の改訂案に**無かった要件が3つ**含まれていた。憲章へ反映した。

| 要件 | どこに入れたか | なぜ重要か |
|---|---|---|
| **おしえてBOX の利用者数が減ること** | §1 冒頭（達成指標） | **D4 の答えそのもの。**内部の代理指標ではなく**外の実数**で測れる。「たぶん良くなった」で終わらない |
| **使用頻度に応じて自己成長・自己改善** | §1 の3条件の (2) | 「答えが返る」だけでは足りない。**使うほど賢くなる**ことが要件。フライホイールが中核であって付加機能ではない |
| **FB・意見を発行者側で集約 → 持続的な運営保守** | §1 の3条件の (3)、§2 の「運用の担い手」 | **D2 の答えを含んでいる。**「発行者側で集約」は、知識の一次置き場を**発行者中心＝共有側**に置くという意味 |
| **相棒であること・美しい UI/UX** | §1-2（新設） | UI/UX を**装飾ではなく要件**として明文化。迷ったときに最初に開く先でなければ、照会はゼロにならない |

## 3. あわせて裁定してほしいこと（憲章の外だが、憲章と同じ重さ）

### 3-1. 【D1】目的の書き換え → **採用（裁定済み）**

`docs/dev/00_プロダクト憲章.md` の §1・§2 を改訂した。§3〜§5 は変更していない。
文言は上の §2-4（PO の言語化）を正典とし、私の案はそれに合わせて書き直した。

### 3-2. 【D2・最大】知識の一次置き場 → **共有一次（裁定済み・ただし着手は最後）**

PO の言語化にある「**FBや意見で誤った出力や質の低い出力は発行者側で集約し出力精度を高める**」
が、そのまま D2 の答えになっている。**「発行者側で集約」は、品質の一次責任を発行者に置く**
という意味であり、知識の一次置き場も同じ側でなければ集約が成立しない
（個人のブックの中で直しても、誰にも伝わらない）。

**ただし着手は最後にする。** 順序を逆にすると、消える予定の構造に対して直しを積むことになる。
D3 → 検問の修理 → バッジの作り直し → ループを閉じる、を終えてから設計に入る（§4 の順位表）。

現状は **「ブック1個の中に知識があり、そのブックは個人のもの」**。
監査A観点の結論は、これが最大の足かせで**継ぎ足しでは塞げない**、というもの。

| 案 | 形 | 得るもの | 失うもの |
|---|---|---|---|
| **維持** | いまのまま。各自が自分の本棚を作り、たまにパックで配る | 変更ゼロ。オフラインで完結 | 12,000個の空の本棚。照会は減らない |
| **共有一次** | 知識の一次置き場を共有フォルダの正典に移し、各人のブックは**キャッシュ＋個人ナレッジ**だけを持つ | 全社で1つの知識。取込コストが集約される。1人あたりのチャンク数が桁で減りメモリ問題も軽くなる | 共有フォルダへの依存。オフラインでの新規取得ができない |
| **併用** | 全社正典は共有フォルダ、個人資料はブック内 | 両取り | 2つの真実ができる。どちらが正かの規約が要る |

**ゼロから作る話ではありません。** `modChannel`（版差分で取り込む）と `modShare`
（共有フォルダI/O）は既にその方向の部品として存在します。足りないのは
**「ブックの中が正典である」という前提を捨てる裁定**のほうです。

### 3-3. 【D3】30,000字の壁 → **実機で測る（裁定済み・最優先）**

借りた Windows 機での最初の実験にする。プロンプト②に手順を組み込む。

`build/build_mybookshelf.py:4119` を読むと、30,000字を検査する `_make_vba_src` は
**`--vba-mode installer` のときしか呼ばれない**。出荷は既定の `baked` で、この検査を
1行も通らない。しかも `installer` は `--zip` と併用禁止（AMSIに検知されたため）＝
**配布経路に乗らない**。

30,000 の出どころは「モジュールのソースを **Excelのセル1個に収める**」という旧方式の
制約（セル上限32,000字）で、**方式Bへ変えた時点で前提が消えている**。
いま残っているのは `tools/vba_lint.py:64` の自分で課したルールだけ。

この壁が生んだもの：**逼迫18本・実質凍結7本・回避コメント48箇所・受け皿モジュール制度・
「実体は受け皿へ、呼び出しは1行」という作法・`modTestsPure2`〜`48`**。
`src/qa/modAskRetrieve.bas:608` には「キーワード加点そのものの遮断は未達（要裁定）」と
書かれており、**容量を理由に検索の品質改善が実際に止まっている**。

**ただし断定はできない。** 実Excel 32bit の VBA に別の上限が本当に無いかは
**実機でしか確かめられない**（憲章 §2 の「検証の構造的制約」そのもの）。

→ **借りた Windows 機での最初の実験にする**ことを提案する。
30,000字超のモジュールを意図的に作って baked で焼き、実Excelで開いてコンパイルが
通るかを見るだけ。**幻だと分かれば、以後のラウンドが全部軽くなる。**

### 3-4. 【D4】「ゼロにする」の測り方 → **おしえてBOX の利用者数（裁定済み）**

PO の言語化が答えを含んでいた。**主指標は「おしえてBOX という照会システムの利用者数」**
であり、**プロダクトの外にある実数**である。これは決定的に良い。内部の代理指標は
「たぶん良くなった」で終わるが、外の実数は言い訳ができない。

ただし主指標は**うちからは取れない**（おしえてBOX 側の数字）。そこで
**先行指標**を内側に置き、主指標と突き合わせる形にする。

| 種別 | 指標 | 取り方 | いまの状態 |
|---|---|---|---|
| **主** | **おしえてBOX の利用者数／照会件数** | おしえてBOX 側から取る（うちの実装外） | 導入前の値を**先に控えておく必要がある**。これが無いと後から比較できない |
| 先行1 | 🔴 の率（答えられなかった質問の割合） | `usage_log` の既存材料で出せる | **🔴 の判定自体が壊れている**（C-2）ので、先にそれを直す |
| 先行2 | 解決率（✅解決した／❌違う） | 既存ボタン | 押してもらえるかに依存。UI の改善余地 |
| 先行3 | **同じ質問の再発率** | 質問文の近さで集計。実装が要る | **これがフライホイールの効き目そのもの。**再発率が下がる＝自己成長している |

**先行3が最も目的に近い。** 「使用頻度に応じて自己成長・自己改善」が効いていれば、
同じ質問は2度目から機械が答えるので再発率が下がる。逆に下がらないなら、
ループのどこかが切れている。

> **いますぐ PO にお願いしたいこと（実装より先）**:
> **おしえてBOX の現在の利用者数・照会件数を控えておいてください。**
> 導入前の値が無いと、後からどれだけ減ったかを証明できません。

## 4. この案を採った場合、監査の優先順位がどう変わるか

改訂後の憲章を基準にすると、監査28件（＋未検証67件を反証中）の並びはこうなる。

| 順位 | 項目 | 理由 |
|---|---|---|
| 1 | **D3 の実機実験（30,000字の壁）** | 幻なら以後の全ラウンドが軽くなる。他の全ての改修の難易度が変わるので**順序が最初** |
| 2 | **検問の自己無効化（B-1 / G-1 / G-2）** | 「検問が緑」を信じられない状態では、以後どのラウンドの結論も信用できない |
| 3 | **確信度バッジの作り直し（C-1 / C-2）** | 目的が「ゼロにする」なら、バッジの精度は使い勝手ではなく中核品質 |
| 4 | **ループを閉じる（A-4）＋ 取り消し導線（A-3）** | 改訂した目的の本体。閉じていなければ照会は減らない |
| 5 | **観測の穴（E群）** | 「失敗を表す値を作ったのに読む側が無い」型。検査1本で系統的に根治できる |
| 6 | 状態のクリア（D群）・誠実さの機構（H群） | 全社規模で効いてくる |
| 7 | **D2 の知識の置き場所** | 最大だが、1〜6 を終えてから設計に入るべき（順序を逆にすると、消える構造に対して直しを積む） |
