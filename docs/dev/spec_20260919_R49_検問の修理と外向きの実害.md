# R49 裁定書 ― 検問の修理と、外向きの実害

起草: Fable司令塔 2026-09-19 / 判定基準: `docs/dev/00_プロダクト憲章.md`（R49 改訂版）

## 0. このラウンドの起点

ユーザー（PO）の指示は2つあった。

1. **全体監査の指摘をまとめて実装する**（R48 はクローズせず R49 へ合流。
   「どうせ治すなら閉じる意味なくない？まとめてテストした方が効率的」）
2. **悪い芽は全て潰す**（「継ぎ足しで負債を隠すな。最大の足かせを特定し、
   必要なら設計から作り直せ」）

全体監査は 99 件の指摘を上げ、敵対的反証で 21 件を退けて **78 件が残った**
（HIGH 8 / MEDIUM 38 / LOW 32、うち **56 件が「静かに壊れる」型**）。
R49 はこのうち **外向きに実害が出るもの**と、**それを見逃した検問そのもの**を扱う。

## 1. このラウンドで分かった一番大事なこと

> **検問が在ることと、検問が効いていることは別である。**

R49 で修理した検査の穴は3つ。いずれも **「検査は存在し、ERROR 0 を返し続けていた」**。

| 検査 | 在ったのに見ていなかったもの | 塞いだ直後の検出数 |
|---|---|---|
| `vba_lint` 孤児Public | 裁定書に名前が出た Public は未接続でも永久に救済されていた | **隠れ孤児 5件** |
| `doc_gate` config 既定値 | bool と str（モデル名）を1文字も見ていなかった。表形式の台帳（MASTER_SPEC §5・約60行）も1行も見ていなかった | **実在のずれ 5件** |
| `doc_gate` 配布文書のUI名 | 「タブで画面を切り替えろ」の綴りを**1通りしか**見ておらず、実際の文書の語順はばらばらだった | **7件（4文書）** |

そして **容量台帳は35件ずれていた**。原因は不注意ではなく**構造**で、
CLAUDE.md §12 は日付つきスナップショットが4枚（R43 / R46 / R48 / 受け皿）
重なった状態だった ―― 同じモジュールが3か所に3つの違う数字で載る。
ラウンドごとに「前の行を直す」のではなく「新しい行を足す」ので、ずれは必ず増える。

**§12 自身が「伝聞のまま持ち回ると、実装班が『入る』と判断して入らない」と
書いているとおりの事故が、その台帳の中で起きていた。**

→ 裁定: **台帳は人が書かない。** `doc_gate --write-cap` が実測から1枚を書き、
`--only cap` が検査する。これで判明した副産物:

- 旧台帳に**一度も載っていなかった** WARN 直下が2本（`optGsTxt` / `modRagParse`）
- `modClarify` は残233 ではなく**残32**（逼迫ではなく実質凍結だった）

## 2. 裁定（R49-1）解決済みQ&Aに個人情報の関所を通す【監査 H-7・HIGH】

### 2-1. 何が起きているか

共有フォルダへ出ていく経路は3本ある。

| 経路 | 運ぶもの | 名乗り | PII の関所 |
|---|---|---|---|
| `EmitGap`（困りごと） | 質問文のみ | 匿名ID | **あり**（`:107`） |
| `EmitCorrection`（訂正） | 回答の先頭200字 + 訂正文 | 匿名ID | **あり**（2本を別々に） |
| `EmitVerifiedQA`（解決済みQ&A） | **質問全文 + 回答全文 + 実名** | **実名** | **無し** |

**いちばん重い荷物を運ぶ経路だけが、1度も走査していなかった。**

### 2-2. 「本人が押したのだから同意がある」は成り立たない

コード中のコメントは、この経路を「本人が ✅解決した を押して共有すると
分かっている経路」として実名掲載を正当化している。**実名についてはそのとおり。**

だが同意の対象は【自分のQ&Aを部内に出すこと】であって、
【そこに混ざった取引先の携帯番号を部内全員に配ること】ではない。
まして**回答本文は LLM が生成した文**で、利用者が一字ずつ選んだものではない
（質問文を復唱する癖があるので、質問に入った個人情報は回答にも移る）。

共有フォルダに一度書いたものは取り消せない。だから出す前に見る（憲章§3-6）。

### 2-3. 直し方と、副作用への構え

`modInsightGate.QaBlocked(q, ans)` を新設し、`EmitVerifiedQA` の冒頭で通す。

- 走査は **質問と回答を別々に**。連結すると片方の末尾と他方の先頭の数字が
  繋がって偽の長い数字列になる（R32 F4 と同じ真因）
- `ScanClean` を通す。`Clean1` 済みを渡すと改行が半角スペースへ均されて同じ事故（R32 F17）
- **資料名だけが当たったときは Q&A ごと見送らず、資料名を伏せる**
  （`IsMemoSource` と同じ作法。知恵そのものは部内に残す値打ちがある）

**副作用の自覚**: 回答本文は社内資料が根拠なので、長い数字（証券番号・金額）で
誤検知する余地がある。それでも**見る側へ倒す** ―― 取り消せない経路での
取りこぼしは、見送りの不便と釣り合わない。誤検知は後から個別に潰せるが、
出てしまった番号は戻せない。ただし**見送りは必ず利用者へ伝える**。黙って捨てない。

### 2-4. テスト（S群・9件）

**陽性2件だけでなく、陰性の反例7件を必ず置く。**
この関門は過検知すると部内ナレッジのフライホイール（憲章§1 の目的そのもの）を
止めるので、「日時を書いただけの質問」「約款の条番号・金額」「改行で分かれた数字」が
**通る**ことまで固定しないと、次に閾値を触った人が静かに壊す。

ネガティブ確認済み: S1（携帯番号）の期待値を True→False に壊して
`FAIL 1（R48-47-S1_携帯番号 実際=True 期待=False）` → 復元。**PASS 3507 → 3516**。

## 3. 裁定（R49-2）✅解決した の共有失敗を黙って捨てない【監査 H-H-3・HIGH】

### 3-1. 何が起きているか

3経路のうち Q&A だけ、書込み失敗時の `Else` が無かった（他2本は R32 F5 で持った）。
**しかも呼び出し元 `modAsk:488-492` は成否を見ずに断言する:**

> この質問と回答は「解決済みQ&A」として部内に共有され、
> 同じことで困っている人がすぐ答えにたどり着けるようになります。

`modAsk:487` のコメントは「共有していないのに共有したと言わない（憲章§3-3）」と
書いている。**意図は正しいが、`CanShareInsight` の枝しか塞いでおらず、
書込み失敗の枝は塞がれていなかった。**

### 3-2. 直し方（暫定であることを明記する）

`modAsk` は**凍結かつ残300字**で、MsgBox を成否で分ける分岐を足せない。
そこで **トーストが後から打ち消す形**にした。

- トーストは `waitless=True`（`OnTime` 消去）なので、**モーダルの MsgBox が
  開いている間は消えない**。利用者が OK を押したあと最後に残るのは訂正文のほう
- 文面をそのように書く: `【さきほどの『部内に共有されます』は取り消しです】…`

**これは暫定である。** 本筋は2つあり、どちらも層1なので R50 へ送る:

1. **MsgBox 自体を成否で分ける** = `modAsk` の凍結解除と分割（残300字）
2. **送信待ち箱**: 書けなかった Q&A を溜めて次回起動で送り直す。
   共有フォルダが一時的に届かないだけで**組織の知恵が消える**のは、
   憲章§1 の「自己成長・自己改善」に正面から反する

## 4. 裁定（R49-3）ノイズ報告の既定ボタンと取り消し【監査 A-A-3・HIGH】

### 4-1. 何が起きているか

ナレッジ詳細のダイアログは `vbYesNoCancel + vbDefaultButton2`。
**`vbDefaultButton2` は [いいえ] ＝ ⚠️ノイズ報告。**
資料カードを開いて Enter か Space を押しただけで:

- その資料が自分の検索から即座に消える（個人ミュート）
- 共有フォルダへ「この資料は品質が低い」という**1票が飛ぶ**

**全社12,000名が使う前提では、誤操作は事故ではなく確定事象**（憲章§2）。
しかも2つ目は**他人の検索結果を変える**。

さらに、報告を本人が戻す導線は製品のどこにも無かった。復帰できるのは
`config admin_users` に載った管理者が `modP2P.ClearNoise` を呼ぶ経路だけで、
これは**その資料への全員の票**を消すもの ―― 1人の誤操作を直すのに
管理者が組織全体の判断を巻き戻す、という釣り合わない操作しか無かった。

### 4-2. 直し方

1. 既定を `vbDefaultButton3`（[キャンセル]＝閉じる）へ。**Enter が何も壊さない状態にする**
2. 報告直後に取り消しを出す（`vbOKCancel`。[キャンセル]＝取り消す）
3. 取り消しの中身:
   - `modStats.UnreportNoise` … `noise:<資料名>` を 0 へ（`ExcludedSources` は `>= 1` 判定）
   - `modP2P.RetractNoiseVote` … **自分の票ファイルだけ**削除。他人の票・`gexcl` には触らない。
     票を引いた結果として閾値を下回れば、次の `CollectNoiseVotes` が
     ファイルから数え直すときに自然に復帰する
4. **共有が到達不能なときに「消せた」と言わない**。`KillRetry` は「既に無い」も
   成功として返す（並行GC耐性・意図的な仕様）が、ネットワーク断の `Dir` も
   同じく空を返す。先に `modShare.Reachable()` で確かめる

実体は新設 `modNoiseReport` へ。`modVaultGallery` が残271字（§12 逼迫＝分割裁定必須）
だったため、§12 の裁定を実行した形になる（**残271 → 残459**）。

## 5. 裁定（R49-4）起動中は見えないタブで画面を切り替えろ、と案内していた【監査 G-G-2】

`modUI:71` / `modShared:171` / `modViewport2:96` が `DisplayWorkbookTabs = False` に
している。**起動中、シートのタブは1枚も見えない**（閉じるとき `modUI:420` で True へ戻すだけ）。

それなのに、**配布zipへ同梱する文書4本7箇所**と**製品の文言3箇所**が
「タブで画面を切り替える」手順を書いていた。読んだとおりにやっても、押すものが無い。

さらに `doc_gate` にはこれを見るための検査が**既にあった**のに、
`「マイ本棚」タブ` という**綴りを1通りしか**見ておらず、実際の文書
（`タブから **「マイ本棚」** をクリック` / `タブ「ホーム」を開く` /
`「📊 ダッシュボード」タブ` / `**ホーム** タブ`）は**1行も引っかからなかった**。

→ 語順の両向きを見る形へ直し、即座に7件検出。
**`「シートタブ」を右クリック→再表示` は対象外**にしてある ―― あれはマクロを
有効にせずに開いた状態（`Auto_Open` が走っていない＝タブが見える）の案内で、
実際に実行できる。

製品側も `「ナレッジと本棚」` という実在のボタン名へ直した
（`modUIMain` ×2 = 空の本棚の案内と豆知識、`modDiag` ×1 = 診断の未変換チャンク）。

## 6. 裁定（R49-5）中断の文言を1本へ【R48 持ち越し】

`"#ERR:E0207:利用者の操作で中断しました"` が `modGateway` / `modAskMulti` /
`modAskThorough` の3箇所に手で書かれていた。`IsCancelled` は先頭11字
（`#ERR:E0207:`）しか見ないので、**文言だけが食い違っても検査に掛からず、
画面に出る言葉だけが段によって変わる**。気づける人はいない（憲章§4-5）。

→ `modRibbonFail.CancelledErr()` を単一情報源に。作る側も判定する側もここから取る。

## 7-2. 敵対的レビュー2周が見つけたもの（このラウンドで一番読む価値がある節）

### 1周目 ― MAJOR 4件は**すべて司令塔の欠陥**だった

| # | 何が起きていたか |
|---|---|
| REV-03 | **「部内に共有されます」は出荷既定では今も嘘をついていた。** 書込み失敗の `Else` を足して直したつもりが、`EmitVerifiedQA` は `WriteShared` の手前に無言の `Exit Sub` を3本持っていた。しかも**出荷既定 `nexus_share_path=""` → `Reachable()` 偽 → `SubDir` が空**で、そのうち1本がいちばん通る道 ―― **足した通知は一度も発火しない**まま画面は毎回断言していた。共有フォルダ未設定は導入直後の既定状態＝最頻ケース。**直したのは最後の一区間だけだった。** |
| REV-01 | 取り消しが「あなたの検索に戻ります」と断言するが、`gexcl`（組織的除外の確定）が立っていると戻らない。`ExcludedSources` は `noise:` と `gexcl:` の**和**なのに `gexcl` を一度も見ていなかった。`muteCleared` を取りながら文面に一度も使っていなかった |
| REV-02 | 確定後は `CollectNoiseVotes` が個別票を全部GCするため票ファイルが存在せず、`KillRetry` の「既に無い＝成功」がそのまま「1票も引っ込めました」になっていた。さらに次の集計は確定フラグを読んで**票を数え直さない**ので、1票引いても復帰しない |
| REV-04 | **孤児検査が `vba_lint.py` 自身で無効化され続けていた。** `outside` は `tools/` を丸ごと読み、CONTRACT は Public 名を文字列で列挙する ―― つまり**CONTRACT に載っている Public は全部「使われている」ことになる**。R49 は同じラウンドで `docs/dev/` を外したのに、**塞いだのは小さいほうの穴だった**。外したら隠れ孤児8件が露出 |

### 2周目 ― MAJOR 3件は**すべて Fix 波が作った新しい縫い目**だった

§8 が「R33 の2周目は14件全部が Fix 波の新しい縫い目だった」と書くとおりの型が再現した。

| # | 何が起きていたか |
|---|---|
| REV2-01 | 取り消しの文面が、**実際に票を引っ込めた直後に「引っ込めることはできません」**と言う。確定済みの資料のカードも押せる（`modVaultGallery` は色と警告行を変えるだけで `OnAction` はそのまま）ので、「確定済みを報告→取り消す」は正規の経路。`EmitNoiseVote` が票を書き直した直後なので撤回は成功する。**Fix が潰したはずの型を Fix 自身が作り直していた** |

| REV2-03 | タブ検査に足した `(?<!の)` が、**同じ Fix で足した「括弧無しの素の書き方を拾う」能力だけ**を、日本語で最も自然な「画面下のホームタブ」という文脈で打ち消していた。外しても現行 docs/ で誤検知は増えない（実測 0） |

MINOR も3件手当てした（通知の印を理由ごとに持ちトーストの**後**に立てる／取り消しの見出しも結果を見てから書く／`vbYesNo` を問いかけ文に直す）。

どちらも lint・LO・doc_gate では1件も捕まらなかった。**検問は回帰を止めるもので、設計の欠陥は止めない。**
