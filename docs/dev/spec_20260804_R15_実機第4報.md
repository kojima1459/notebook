# R15 要件定義: 実機テスト第4報への対応(2026-08-04)

基点: f67f312(R14完了)。裁定者: Fable。実装: Opus/Sonnet。判定基準: docs/dev/00_プロダクト憲章.md。
調査4班(チャンク規定/OCR進捗/254頁実現性/E0202+save_fail)の報告を統合裁定。全てfile:line証拠つき。

## 根本原因(確定)

RC1. チャンク数は規定どおり(欠陥なし)。チャンク化は取込経路(OCR/GSテキスト)に依存せず
     modShelf.bas:183-188 の1点に合流し、pdf別設定(450/100/900)が正しく効く。
     画面の「127」と記録の「125」の差は、生成数(chunkN)と重複排除後保存数(acceptedCount、
     modShelf.bas:249-251)の乖離が最有力だが、この差分がログにもUIにも一切残らない診断欠落
     がある。modVaultGallery.bas:451 は modUIShelf.ParseStats の頑健版を使わない重複実装。
RC2. OCRのETAが「ほぼ最後まで出ない」: knownTotal は最終バッチ到達まで0のまま
     (optOcrPage.bas:112,164-171)で、OcrPageBanner は totalPages>=p でしかETAを出さない
     (optOcrCore.bas:497)。24頁中20頁(83%)・76頁中60頁(79%)がETA非表示。一方、OCR経路に
     入る前のtxtwrite分類パスのGS出力には「Processing pages 1 through N」が既に出ており
     (実機ログで確認)、GsTotalPagesFromLog(optOcrCore.bas:317-324)で拾える。
RC3. 中断機構なし。Esc/err18方式は modGateway.TryRibbonRun/CallLLM の全捕捉ハンドラ
     (modGateway.bas:439,476-479)が握りつぶす構造リスクがあり不採用。頁/バッチ境界の
     DoEvents(optOcrPage.bas:231,291,294,304)がフラグ方式の挿入点。
RC4. 254頁を阻む上限: PAGES_MAX=200 ハードクランプ(optOcrCore.bas:59,577)+config既定100
     (optVision.bas:424)。さらに optVision.OcrCapMemo(:409-419)は capN に SafeMaxPages を
     掛けず、config>200設定時に「54ページは読み取れませんでした」という嘘に近いメモを出す。
RC5. 【最重大】再入ガード4本が「開始から30分」で自動失効: modShelf.bas:28 /
     modShelfBatch.bas:43 / modEmbed.bas:53 / modShelfSync.bas:77。85〜127分の取込では
     t=30分以降ボタンが全面解放され二重取込が構造的に可能(憲章§3-5違反)。現行100頁上限
     (〜50分)でも既に露出。
RC6. 頁単位OCR失敗が truncated に反映されない: failN は数えるだけ(optOcrPage.bas:296-309,
     317-320)で、全画像化成功+一部Vision失敗なら status="done" の顔で頁が無言欠落
     (optOcrPage.bas:252-257)。上限エラー連続時の打切り(modEmbed.bas:211-215相当)も無く、
     レート制限に当たると残頁を全部叩いて全部失敗する。
RC7. ChatGPTV に待ち秒数の引数が無い(RIBBON_API_CONFIRMED.md:29)。HTTPタイムアウト設定は
     direct経路(modGatewayDirect.bas:78-79)のみで Vision経路はゼロ。1頁のハング=永久待ち。
     VBA側から制御不能(検証不能層)として記録し、RC5是正+R15-7チェックポイントで被害限定。
RC8. E0202の実体はAI通信ではなく Application.Run("optVision.ExtractPdfTextNoOcr") の
     自己呼び出し失敗(modFeatures.bas:92→modGateway.bas:438-479)。GS完了待ちDoEvents
     (optGsTxt.bas:386)中のHub操作の入れ子実行との衝突が最有力。BlockIfIngesting漏れ2箇所:
     modHubStat.OnSyncPending(:69-105)/modApp.OnRefreshUI(:506-519)。E0202は呼び出し内
     再試行が無く、Word/Acrobat空振り→次回同期まで持ち越しになる。
RC9. save_fail の実体: 保存経路は自己インストーラのopen時Save(build_mybookshelf.py:
     1006-1007)と終了ボタン(modApp.OnSaveAndExit)のみ。セッション中の中間保存がゼロで、
     取込済みチャンク・ログが数時間メモリ上のみになる(憲章§3-5違反)。9:58のsave_failは
     再オープン由来の可能性大。多重起動/ReadOnly検知も無い。
RC10. KillBatchJpgs は OERN(optOcrPage.bas:423)で、EDRロック等で削除失敗すると
     CountBatchFiles(:405-419)が残骸を誤カウントし頁番号が静かにズレる。GS描画待ち総予算
     gs_abs_timeout_sec=1200秒(optVision.bas:338)は254頁13バッチでは不足リスク。

## 実装項目

### R15-1 再入ガードのハートビート化 [P0]
1a. 失効判定を「開始から30分」→「最終ビートから30分」へ。modShelfBatch に
    Public Sub TouchBusy() / Public Function LastBeat() As Date を新設し、
    modShelf / modShelfBatch / modEmbed / modShelfSync の4箇所の失効判定は
    max(開始時刻, LastBeat) 基準に変更。modShelfSync は失効判定行のみ最小差分で変更可
    (他は接触禁止を維持)。
1b. ビート更新点: modUIMain.SetStage と modShelfBatch.StageBanner の先頭に TouchBusy 1行
    (全長時間ループが既にどちらかを通る)。optOcrPage の頁ループからは既存の
    StageBanner 呼び出し経由で自然に更新される(新規呼び出し追加は不要なことを確認する)。
1c. 純テスト: 失効判定の真理表(開始古い+ビート新しい=生存 / 双方古い=失効)。判定式は
    純関数に切り出してテスト(GuardExpired(startAt, beatAt, nowAt, limitMin))。

### R15-2 再入保護の穴とE0202の是正 [P0]
2a. modHubStat.OnSyncPending(:70直後)と modApp.OnRefreshUI(:507直前)に
    If modUiLock.BlockIfIngesting() Then Exit Sub を追加(既存40箇所超と同一パターン)。
2b. tools/vba_lint.py に新検査: OnAction 配線される Public Sub(配線箇所を走査して収集)の
    先頭付近に BlockIfIngesting または Enter 呼び出しが存在すること。除外allowlist機構を
    設け、中断ハンドラ(R15-6)等の「取込中でも動くべきハンドラ」を登録できること。
2c. modExtractorPdf: TryRibbonRun 結果が #ERR:E0202: のときのみ、Word/Acrobatへ譲る前に
    その場で1回だけ即時再試行(E0202は入れ子衝突由来の一時失敗であり資料の中身と無関係)。
    再試行も失敗なら従来どおり。usage_log "gs_e0202_retry" に成否を1行。
2d. modLog の E0202 Friendly文言に「(実行中の処理と操作が重なった可能性。少し待って再度
    お試しください)」の趣旨を追記(AI通信不調と誤読させない)。

### R15-3 中間保存とReadOnly検知 [P0]
3a. modShelfBatch のファイルループで「1ファイル取込成功ごと」+同期(modShelfSync)の末尾で
    OERN つき ThisWorkbook.Save。失敗時のみ usage_log "save_fail" (既存イベント名を踏襲)+
    トースト「保存に失敗しました。終了ボタンからの保存をお試しください」。成功時は記録不要。
3b. Boot 時に ThisWorkbook.ReadOnly なら E0805(新コード) LogError+目立つ表示「このファイルは
    読み取り専用で開かれています。取り込んだ資料は保存されません(既に別のExcelで開いて
    いないか確認してください)」。取込機能は止めない(閲覧・質問は可)。
3c. 純テスト: ReadOnly文言・save_fail文言の生成関数。

### R15-4 OCRの正直さ強化 [P0]
4a. optOcrPage: failN>0 かつ okN>0 の第3の出口を追加し、truncated=True 相当の partial へ。
    メモ「全N頁中M頁が読み取れませんでした(もう一度取り込むと再試行します)」(新純関数、
    R15-7のキャッシュがあれば失敗頁だけ再試行になる)。
4b. 上限エラー打切り: 頁失敗の理由が modGateway.LooksLikeLimitError 相当で3連続したら
    バッチループを中断(aborted=True)し、メモに「AI利用の上限に達した可能性があります。
    時間をおいて再度取り込んでください」。modEmbed.bas:211-215 と同型。
4c. optVision.OcrCapMemo: capN に optOcrCore.SafeMaxPages を適用(嘘メモ解消)。
4d. RenderBatch の描画前に作業フォルダの page_*.jpg を全削除(完了フラグのみでなく)。
    削除失敗が残った場合は当該バッチを LAUNCH_FAIL 扱いにして頁ズレを防ぐ。
4e. 純テスト: 4a/4bの真理表(okN×failN×連続上限)、4cのクランプ表。

### R15-5 総頁数の早期確定とETA/終了時刻 [P1]
5a. txtwrite分類パスで GsTotalPagesFromLog により総頁数Nを取得し保持(optGsTxt に
    Public Function LastGsTotalPages() As Long、分類実行時にモジュール変数へ)。
    modShelfVision→optVision.ExtractPdfOcrPagedText→OcrPdfByBatch へ引数で受け渡し、
    knownTotal の初期値にする(0なら従来どおり最終バッチ確定+バッチ描画ログからの
    機会的取得を試みる。取れなくても現行動作へ自然縮退)。
5b. 新純モジュール src/opt/optOcrEta.bas: OcrPageBanner / RemainingWaitSec / BatchLabel /
    OcrCapMemoFor / OcrAbortMemoFor を optOcrCore から移設(optOcrCore は純減させ追記禁止を
    守る)。バナー拡張:「OCR中… p/N頁 (バッチ b/B) 残り約M分・終了目安 HH:MM」
    (60秒未満は秒表示。完了時刻は Format$(Now + remSec/86400, "hh:mm"))。画像化フェーズも
    N判明時は「画像化中… バッチ b/B (全N頁)」。
5c. 事前レート: バッチ完了ごとに modState "ocr_avg_page_ms" へ modUtilText.BlendPerItemMs
    でブレンド保存。実測2頁未満の間はこの過去実績でETAを出す(初回端末はレート無し=
    従来表示)。usage_log への vision_page_ms 記録は現行維持。
5d. ゴールデンテスト: バナー文字列(N確定/未確定×レート有無)、ETA分表示境界、移設関数の
    既存テスト追随(modTestsPure11 の参照先変更)。

### R15-6 中断ボタン [P1]
6a. 進捗バナー(nx_progress)に「⏹中断」の小Shapeを追加し OnAction=modShelfBatch.OnCancelIngest。
    ハンドラは即座にフラグ(modShelfBatch モジュール変数+TouchBusy)を立てるだけの最小実装
    (再入安全)。lint allowlist(R15-2b)に登録。
6b. optOcrPage の頁境界/バッチ境界でフラグを確認し、立っていれば aborted=True で抜ける。
    既存の aborted→truncated→partial 経路に接続。OcrAbortMemoFor に理由引数を追加し、
    利用者中断は「利用者の操作で中断しました。ここまでのX頁を保存しました(もう一度
    取り込むと続きから再開します)」(R15-7キャッシュ前提の正直文言。キャッシュ無効時は
    「最初から再試行します」)。
6c. modShelfBatch のファイル間ループでもフラグを確認し、残ファイルをスキップ
    (「中断のためN件を見送りました」トースト)。フラグは取込開始時に必ずリセット。
6d. 純テスト: 中断メモ文言(理由×キャッシュ有無)、フラグ真理表。

### R15-7 254頁対応(上限引上げ+事前確認+チェックポイント再開) [P1]
7a. PAGES_MAX 200→300(optOcrCore.bas:59 の定数変更のみ許可)。vision_pdf_max_pages
    既定 100→300(optVision.bas:424 と build config:440)。modTestsPure4:184-186,204-206 の
    ゴールデン値追随。docs/43_画像PDFのOCR取込設定.md / MASTER_SPEC.md の記載更新。
7b. 事前確認: N判明時(R15-5a)、推定所要時間(N×レート)が config ocr_confirm_min_minutes
    (新設、既定15分)以上なら取込前に確認ダイアログ「全N頁・推定約M分かかります。途中で
    ⏹中断でき、続きから再開できます。取り込みますか?」。拒否時は status="image_pdf"
    (E0303経路の実装上の帰結。波4検収で実挙動へ訂正。errCode="declined"で「見送り」に分離)+正直メモ
    「推定約M分のため取込を見送りました。再度取り込むと実行します」。文言は純関数+テスト。
7c. GS描画待ち予算のN連動: 予算秒 = max(gs_abs_timeout_sec, N×8) を純関数化しテスト。
    optVision の予算取得部で適用(他経路のgs_abs_timeout_sec利用には触れない)。
7d. 新モジュール src/opt/optOcrCache.bas: 頁チェックポイント。
    - 保存先: xlSheetVeryHidden シート "ocr_cache"(modEmbed.EnsureVectorSheet と同作法)。
      1行=1頁: key / text / saved_at。key = Fnv1a64Hex(フルパス) & "|" & FileLen & "|" &
      FileDateTime & "|p" & 頁番号(サイズ/更新日時で差し替え検知。SafeLeft 32000)。
    - 書き込み: バッチOCR完了直後、KillBatchJpgs の前に当該バッチの成功頁を一括保存。
    - 読み出し: OcrPdfByBatch 開始時に当該資料のキャッシュを辞書化。キャッシュ済み頁は
      Vision呼び出しをスキップし pages() へ復元(GS描画はバッチ単位で従来どおり行い、
      復元頁のJPEGは単に捨てる=CountBatchFiles の想定を崩さない)。
    - 後始末: 取込 status="done" で当該資料の行を削除。孤児行は modBoot の既存GCと同じ線で
      7日超を起動時削除。
    - 正直さ: 復元があった取込は usage_log "ocr_resume"(cached=X;fresh=Y)+カードメモ
      「前回の続きから再開しました」。
7e. 統合テスト観点(LOで可能な範囲は純ロジックで): キーの生成/照合、差し替え検知
    (size/mtime不一致でキャッシュ不使用)、部分キャッシュのバッチ跨ぎ復元、done時削除。

## 記録のみ(コード変更なし・裁定理由つき)
- ChatGPTV の待ち秒数引数の有無をリボン担当部署へ照会(後方互換追加の前例あり。存在すれば
  optOcrPage.bas:303 の1行でRC7根治)→利用者アクション。HANDOFFに記載。
- 教えてBOX xlsx が MAX_CHARS_PER_SHEET=300,000(modExtractorExcel.bas:33)でクリップされて
  いないかの実機確認(単一シートなら本文末尾に注記があるはず)→利用者アクション。
- SourceList の manifest/pack 同名非合算(modShelf.bas:455-518): pack利用時のみの表示問題。
  pack出所の明示という現仕様も一理あるため今回は変更せず記録。
- modGateway 全捕捉による ESC(err18)握りつぶし: 共有コアの変更は爆風半径が大きく、
  R15はフラグ方式中断で代替するため触らない。次回以降の検討事項。
- GS専用処理が Application.Run(自己呼び出し)経由である設計疑問: R2/R3の疎結合規約由来。
  E0202即時再試行(R15-2c)で症状は緩和。構造変更は行わない。
