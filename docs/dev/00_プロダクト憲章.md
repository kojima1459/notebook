# プロダクト憲章(起草: Fable司令塔 2026-07-31)

この文書は本プロダクトの目的・体験基準・工学基準・プロセス基準を定める
最上流の文書である。R11以降の全ての要件定義・実装・レビュー・裁定は
本憲章を判定基準とする。憲章に反する成果物は、理由の記録なしに
受け入れない。

## 1. プロダクトの目的(2026-09-18 改訂・PO裁定)

**社内の照会業務をゼロにする。** 営業が自走し、自分で照会を完結できる状態にする。
達成の指標は社内の既存照会システム「**おしえてBOX**」の**利用者数が減ること**である。

そのために、このプロダクトは次の3つを同時に満たさなければならない。

1. **答えが返る。** 散在する資料とナレッジを「聞けばすぐ返ってくる」形に変える。
2. **使うほど賢くなる。** 使用頻度に応じてアプリケーションが**自己成長・自己改善**し、
   質を高めていく。**答えられなかった質問を、次の人のための知識に変える。**
3. **誤りが集約されて直る。** フィードバックや意見によって、誤った出力・質の低い出力を
   **発行者側で集約**し、出力精度を高められるようにする。これにより**安定的かつ
   持続的に運営保守**できる状態を保つ。

追加インストール不要・Excelファイル1つ(+同梱フォルダ)で完結することが存在意義であり、
管理された会社端末でそのまま動くことが生命線である。

### 1-1. 「削る」ではなく「ゼロにする」と書いた理由(改訂の要点)

本憲章は R10(2026-07-31)制定時、目的を「調べ物の**時間を削り**」と書いていた。
2026-09-18 の全体監査(8観点・敵対的反証つき)を現行憲章を基準に実施した結果、
**基準そのものが実際の目標より小さい**ことが判明したため改訂した。

この2つは**必要な設計が違う**。

- **「削る」なら**: 当たらなかった質問は人に聞けばよい。🔴 を出して
  「うのみにしないでください」と言えば誠実さは保たれる。
- **「ゼロにする」なら**: **当たらなかった質問こそが照会そのもの**である。
  それを吸収する経路 ―― 人へ繋ぐ → 答えを知識へ戻す → 次から機械が答える ――
  が閉じていなければ、目的に届かない。

したがって本プロダクトは、**答えの質だけでなく「ループが閉じているか」で測る。**
部品が存在することは成立の証明にならない(CLAUDE.md §7-4「作ったのに繋いでいない」)。

### 1-2. このプロダクトは道具ではなく相棒である

**難しい操作を要求してはならない。** 使いやすく、没入しやすく、美しい UI/UX で、
仕事の現場に溶け込むこと。UI/UX は装飾ではなく**要件**である。

理由は目的から出てくる。照会をゼロにするには、**迷ったときに最初に開く先**が
このアプリでなければならない。操作を覚えないと使えない道具は、迷っている人には開かれない。
§3(体験原則)はこの条項の具体化である。

## 2. 利用者像と前提環境

- 利用者: **全社員(約12,000名)**。ITに詳しくない人を基準にする。
  エラーコードもフォルダ構成も知らない。
  「わけの分からない表示」が一度出たら、その機能は二度と使われない。
- **その規模で起きること**: 誤操作は確率ではなく**確定事象**になる。
  1万人が1回ずつ触れば、1%の誤操作は100人に起きる。
  **取り消せない操作を、既定の位置に置いてはならない。**
- **運用の担い手も設計に含める**: 知識を入れる人・正典を発行する人・
  フィードバックを読む人が「誰か」を決めずに配ると、**その全員分の照会が新しく生まれる。**
  照会を減らす道具が、新しい照会を生んではならない。
  発行者が1人でも回り続ける形にすること(持続的な運営保守)。
- 環境: Windows / Excel 32bit / 管理端末(CreateObject制限・EDR・
  SmartScreen・Mark of the Web・ネットワーク共有・OneDrive リダイレクト)。
- 検証の構造的制約: 開発環境で実行検証できるのはロジックとコンパイルのみ。
  描画・COM・Shell・ウィンドウ挙動・モーダルは実機でしか確かめられない。
  ゆえにこの層は「動くはず」で書くことを禁じ、防御と観測で固める(§4)。

## 3. 体験原則(UXの憲法)

1. **押せるものは必ず反応する。** 無反応は故障と同義。ブロックする場合も
   「なぜ待つのか」を必ず見える場所に出す。
2. **全ての待ち時間に進捗と目安を示す。** 「止まっているのか動いているのか
   分からない」状態を作らない。
3. **全ての失敗は日本語で「何が起きたか+次の一手」を伝える。** エラー
   コードだけの表示、専門用語だけの案内は失敗の隠蔽と同じ。
4. **利用者を不安にさせない。** OSやOfficeの生のダイアログ(OLE待ち等)に
   利用者を晒す設計を避ける。出さざるを得ないものは事前に説明を出す。
5. **利用者のデータは失敗しても失わない。** データ保全は全ての機能要件に
   優先する。「消える」「欠ける」を伴う不具合は重大度を常に最上位とする。

## 4. 工学原則(コードの憲法)

1. **無言の失敗禁止。** 全ての失敗経路は err_log か usage_log に痕跡を
   残す。「後から原因を特定できないエラー」を作った時点で設計の欠陥。
2. **観測性ファースト。** 機能を足すときは「失敗したとき何が記録されるか」
   を要件に含める。障害は必ず起きる前提で先に観測を仕込む。
3. **検証不能層は防御的に書く。** COM/Shell/Activate/FileDialog/描画の
   全呼び出しは、失敗時挙動・ログ・復旧(または安全な断念)を設計してから
   書く。成功前提のコードを検証不能層に置かない。
4. **表示系は業務ロジックから隔離する。** 進捗・トースト・実況の失敗が
   取込や保存を壊してはならない(逆も同じ)。
5. **場当たりパッチ禁止。** 同型の問題は共通部品で一度だけ解決する。
   2箇所で違う答えを出す実装を残さない。
6. **容量と保守性は先手で管理する。** WARN帯(28,000字超)のモジュールに
   機能を足さない。足す前に分割を裁定する。
7. **Aを直してBを壊さない。** 変更の影響範囲(呼び出し元・呼び出し先・
   画面遷移・ログ)を要件書に明記し、検証はそこまで届かせる。

## 5. プロセス原則

1. 要件定義(司令塔)→実装(Opus/Sonnet)→検証(lint・LOテスト・両ビルド)→
   敵対的レビュー(読取専用)→裁定(司令塔)。省略なし。例外なし。
2. 実装者は発見した問題を勝手に直さず司令塔へ報告し、裁定を受ける。
   裁定は必ず記録に残す(受容するなら理由も)。
3. 配布物には必ず実機スモークテスト手順(短時間で全機能を一巡できる
   チェックリスト)を添える。実機テストを「探索」にしない。
4. 実機からの不具合報告は、症状への対処で閉じず「なぜ上流(要件・設計・
   レビュー観点)で漏れたか」を1行で記録し、観点表を更新する。
