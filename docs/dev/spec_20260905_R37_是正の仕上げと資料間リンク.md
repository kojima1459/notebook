## 0. 起点とユーザー裁定

ユーザー依頼（09-05）: ①「間違った回答を是正して次から直す」の完成 ②NotebookLM 越えの精度。②は「無理しなくてよい。体感できない・確実でない精度アップは作業コスパが悪く、大きな外科手術で他が壊れるならやめる」。加えて「A を取り込んだあと B を取り込むと Obsidian のように全体を俯瞰し、資料同士の関連を抽出し、深さ調整で間接的な繋がりを再構築する動的グラフナレッジは効果があるか。最新の RAG も調査していけそうなら実装。判断は任せる。最悪①だけでもいい」。

**司令塔の結論（要旨）**
- ①は **R36 で本体を実装済み**（是正メモ＝質問文つき・回答生成の直前に出典の先頭へ注入）。残っているのは「**誤答の根拠になった資料は残ったまま**」の1点 → **本ラウンド A で仕上げる**。
- ②の「フル GraphRAG（エンティティ抽出・コミュニティ要約・グラフ探索）」は **やらない**。理由: (a) この環境（Excel 32bit VBA・ワークシート・リボン同期呼び出しのみ）では R17 設計で「不可能／工数対効果が合わない」と裁定済み（`design_20260805_R17_構造グラフ設計.md:69-74`）。(b) 外部ベンチでもグラフが勝つのは多ホップ・要約型で、単純な事実検索では互角（GraphRAG-Bench 2026: 複雑推論 53.4 vs 42.9、事実検索 60.9 vs 60.1）。(c) 取込時の LLM 呼び出しが1資料あたり数百回増える（現状でも 20章 PDF で約 524 回）。(d) **精度を測る土台がこの環境に無い**（`bench_retrieval.py` はスパース側だけの Python 再実装で、seed パックはリポジトリ外）。測れない改善は「たぶん良くなった」で終わる。
- ②の「資料同士の関連を抽出して繋げる」は、**LLM 0回・既存データだけで作れる軽量版**なら筋がよい → **本ラウンド B（資料間リンク）**。取込のたびに「章ごとの代表ベクトル（重心）」を作り、他資料の章との近さを表に残す。回答時は「上位の根拠が属する章」と強く繋がる章の候補を**topK で切られた候補プールから救い上げて末尾に足す**（新しい検索は走らせない）。効果が出るのは「A の言葉で聞いたが答えは B にある」型（多ホップ）だけで、単純な質問では変わらない。**効果の約束はしない**が、危険側（無関係な規程の第8条が混ざる）は既存の裁定（`modAskFocus.bas:204-207`）を尊重して「章の重心同士の類似度が高いときだけ・末尾に・score 0・最大2件」に絞る。
- 精度の**測定**は本ラウンドでは「材料を残す」に留める（C）。

## 2. A: 誤根拠の降格（是正の仕上げ）

### 2-1. 裁定
- ❌違う で是正メモを作るとき、**そのとき出典に出ていた資料名とページ（最大4件）**を本文に残す: `誤答の根拠: <source> p.<page> | <source> p.<page> …`（1行・`|` 区切り）。
- 回答時、是正メモが **MatchLevel 2（完全一致）** で先頭に入ったターンだけ、hits の中から「誤答の根拠」に載っている `(source, page)` と一致する hit を**末尾へ降格**（除外はしない。R36 §7 のリスク台帳「誤爆」を踏まえ、語一致 1 のときは降格しない）。
- 「誤答の根拠」が是正メモ自身の source の場合（前の是正が誤っていた場合）は記録しない。

### 2-2. 契約
- `modCorrect.BuildMemoBody(question, fixText, answerExcerpt, sourcesLine)` に第4引数を追加（既存の3引数呼び出しを同一コミットで更新。`sourcesLine` は空でもよい）。書式は §2-1。
- `modCorrect.CollectAnswerSources() As String`（modAsk の `LastGenHitCount`/`LastHitSource`/`LastHitPage` を読んで `source p.N | …` を組む。是正メモ source は除く）。呼び出しは `modAppAct.RecordCorrection` の是正経路のみ。
- `modCorrect.ExtractWrongSources(memoText) As String`（純関数・`誤答の根拠:` 行を返す）と `modCorrect.DemoteWrongHits(memoText, hits(), nHits, topK) As Long`（`PrependHit` と同じ配列作法で、一致 hit を末尾へ移す。先頭の是正メモは動かさない）。`InjectHits` の中で MatchLevel=2 のときだけ呼ぶ。
- Pure テスト（`modTestsPure40` へ追記）: `BuildMemoBody` の4引数書式／`ExtractWrongSources`（有・無・複数）／`(source,page)` 一致判定の純関数（`WrongSourceMatches(line, source, page) As Boolean`: 資料名は大小無視・ページは数値一致）。`DemoteWrongHits` は Hit 型を跨ぐので Pure テストは書かない（LO 死角）。
- 文書: `05_図解ガイド.html` §7 の右ボックス小字「元の間違った資料は残ります」→「同じ質問のとき、誤答の根拠になった資料は後ろへ下げます（消しません）」。

## 3. B: 資料間リンク（LLM 0回・章の重心）

### 3-1. 裁定
- **新シート `doc_links`**（hidden・`EXPECTED_SHEETS` に追加＝23シート）: `src_a, chap_a, src_b, chap_b, sim, built_at`。`(src_a,chap_a)` から見た他資料の章を **sim 降順で最大3件**だけ保持（双方向は別行）。`sim` は章重心（その章の全チャンクベクトルの平均を L2 正規化）同士のコサイン。
- **取込時**（`modOutlineBuild.BuildOutlineFor` の末尾に1行。`BuildSynonymsFor` の隣）: 新資料の各章の重心を作り、**既存資料の章重心と総当たり**して `doc_links` を更新（新資料側の行を書き、既存側の上位3件も更新）。既存資料の章重心は毎回 `my_vectors` から再計算せず、**新シート `doc_centroids`**（`source, chap, vector_csv, chunk_n`）に保存して再利用（hidden・23→24シート）。
- **削除時**: `doc_outline` の掃除と同じ場所で `doc_links`／`doc_centroids` の当該 source 行を消す（両側）。
- **回答時**（`modAskRetrieve` に1行×2）: `StashDispersionPool` の直後で pool を `modXDoc.RememberPool hits, n` に控え、最終 hits 確定点（`:243` の後）で `n = modXDoc.Expand(hits, n, topK)`。`Expand` は「hits 上位2件の `(source, chap)`」に `sim ≥ config xdoc_min_sim`（既定 0.80）で繋がる章を `doc_links` から引き、**pool にいてまだ hits に無い候補**のうちその章に属するものを score 0 で**末尾に最大 `xdoc_add`（既定2）件**足す。pool に無ければ何もしない（新しい検索は走らせない）。chunk→章の解決は `chunk_meta.section_path` から（`modChunkMetaStore` の既存 read を使う）。
- **表示**: `modTextView.ShowForSource` のメタ行に「関連する資料: B（第3章）、C（第1章）」を1行（`doc_links` の上位3件。無ければ出さない）。Hub・本棚 UI は増やさない。
- config: `xdoc_links`（`on`／`off` で取込時の計算と回答時の Expand を両方止める）、`xdoc_min_sim`（80＝0.80。整数×100）、`xdoc_add`（2）。
- **効かない・約束しないこと（README/使い方には書かない。spec に記録）**: 単一資料で完結する質問には何も変わらない。効果は「A の言葉で聞いたが答えは B にある」型のみ。数字での検証は C の材料が溜まってから。

### 3-2. 契約
- 新モジュール `src/qa/modXDoc.bas`（qa 層・UI 非依存）: `Public Sub RememberPool(hits() As Hit, n As Long)`／`Public Function Expand(ByRef hits() As Hit, ByVal n As Long, ByVal topK As Long) As Long`／純関数 `Public Function CosineCsv(a As String, b As String) As Double`（CSV 2本のコサイン。次元不一致は 0）／`Public Function ChapterOf(sectionPath As String) As String`（`ChapterKeyOf` と同じ規則。modOutlineBuild の Private を Public 化して呼んでもよい）／`Public Function PickLinked(hitsSrcChap() As String, linksCsv As String, minSim As Long, maxN As Long) As String`（純関数: 上位 hits の `src|chap` 列と links 表（`src_a|chap_a|src_b|chap_b|sim` の行）から、追加候補の `src|chap` 列を返す。テスト対象）。
- 新モジュール `src/ingest/modXDocStore.bas`（ingest 層）: `doc_centroids`／`doc_links` の読み書き・`BuildLinksFor(source)`（章重心の計算→総当たり→上位3件更新）・`RemoveFor(source)`・純関数 `MeanNormalizedCsv(csvRows() As String, n As Long) As String`（平均→L2 正規化。テスト対象）／`TopNLinks(pairs() As String, sims() As Double, n As Long, keep As Long) As String`。ベクトル CSV の解析は `modVecCache`／`modUtil` の既存関数を再利用（自前実装しない）。
- フック: `modOutlineBuild.BuildOutlineFor` 末尾に `modXDocStore.BuildLinksFor sourceName`（`On Error Resume Next` 下・失敗しても取込を止めない）。削除は `doc_outline` 掃除の隣に `modXDocStore.RemoveFor`。`modAskRetrieve` に上記2行（残 333 字に収める）。`modTextView` のメタ行1行。

- `modMigrate`／`modPack`／`modChannel`: **触らない**（リンクは取込時に再計算できる派生データ。引き継ぎ・パックには載せない＝記録）。版上げ引き継ぎ後・パック取込・部門チャンネル由来の資料は `doc_links` を持たない（`BuildOutlineFor` を通らない）。復旧は**その資料を取込し直すか ⚡資料の仕上げ（`modBackfill`）**だけ（🔄同期はローカルフォルダの再取込しかしない。班B 指摘で訂正）。全量の再構築ボタンは R38 送り。

## 9. 検問と司令塔のマイクロ修正（2026-09-05）

- 波A/B マージ後の LO compile で **`modXDocStore` が 15 秒タイムアウト**（構文エラーの疑い）。司令塔が単体コンパイルで再現→手続き単位の二分探索→識別子の単体リネームで特定: `TopNLinks` 内の **`Dim takeN As Long` と `Dim taken() As Boolean` が大小同名**（VBA も LO も識別子は大小無視＝同一名の二重宣言。実Excel でもコンパイルエラーになる型）。`taken`→`takenFlag` に改名して PASS。**lint の死角**: `vba_lint` は同一プロシージャ内の「大小違いの同名 Dim」を検出しない → R38 で `check_dim_case_collision` を足す（記録）。CLAUDE.md §10 の逆向きの罠リストに追記する。
- 2つ目: Pure40 C10（`WrongSourceMatches`）が LO で3本 FAIL。原因は `InStrRev(ent, " p.", -1, vbTextCompare)` の**4引数形**（LO は Start=-1＋Compare 指定で不一致を返す。Excel では通る）。src の他8箇所はすべて2引数形で LO 合格済みだったので2引数形へ（`" p."` は大小無関係）。→ **pure PASS 3,149 / FAIL 0 / SKIP 14**（LO compile 166/166）。
