## 2. 「未修正4件」の事実確認

## 3. 「メガコンテキスト一撃投入」の実行可能性（レビューが知らない制約）

1. **LLM は社内リボン経由**（`Application.Run("ChatGPT", …)` → Azure OpenAI）。入力上限は会社側のデプロイ設定で、超過はエラー文字列で返る（`RIBBON_API_CONFIRMED.md §0`）。**20万トークン入力が通るかはここからは確認できない**。実機で1回測るしかない。
2. **同期呼び出し**: 呼び出し中 Excel は応答なし表示。1回 30 秒でも4回 30 秒でも見え方は同じ。往復回数の削減は「合計秒数」の話。
3. **量の検算**: 実機 my_knowledge 約 20,500 行 × 約 900 字 ≒ 1,800 万字。200 頁級の規程 1 冊 ≒ 500 チャンク × 900 字 ≒ 45 万字 ≒ 30 万トークン超。**「資料丸ごと」は大きい1冊すら 20 万トークンに入らない**。現実的な単位は章で、章要約から章を選んで全文を読む経路は **R17 Phase2 `modAskGlobal`（俯瞰）として既にある**（入念モードの内側・最大4章）。
4. **利用上限**: リボンには `LimitCheck` と上限エラー（E0204）がある。1問 20 万トークンが日次上限に触れるかは未知。
5. **測る土台**: R37 C の `ask_sources` ＋ ✅/❌ が初めての材料。まだ1件も貯まっていない。測れない全面移行は「たぶん良くなった」で終わる（spec R37 §0 と同じ判断）。

## 4. 採否（司令塔裁定）

| 提案 | 採否 | 理由・置き場 |
|---|---|---|
| ScreenUpdating 停止 | **採用・実施済** | §1-2 |
| 降格同士の順序安定化 | 記録 | §1-3。実害なし。触るなら R38 のレビュー付きで |
| 誤根拠を枠外へ落とす（除外） | 選択肢として保留 | R37 §2-1 は「除外しない」。是正メモが先頭で正答を示すため、誤根拠を残しても LLM は上書きできる設計。除外に変えるなら層1 |
| 入念モードの 1 パス化 | **R38 候補（config スイッチで A/B）** | 既定は現行4段のまま、`thorough_onepass=on` で「章単位の全文＋1回」に切替。実機で秒数と ✅/❌ を比べてから既定を決める |
| max_context_chars 引き上げ | **config だけで今すぐ試せる** | R34 C の手引きどおり 60,000→80,000→120,000 と1段ずつ。リボン上限の実測も兼ねる |
| 表の Markdown 構造化（取込時） | R38+ 候補 | 取込1頁ごとに `ChatGPTV` 呼び出しが増える。まず「表で誤答した実例」を ask_sources から拾ってから |
| 引用クリックで本文ジャンプ＋強調 | R38 候補（UX） | `text_view` と出典タグが揃っているので実装可能。層1 |
| Studio 自動生成（要約/FAQ/用語） | 一部既存 | 章要約は `doc_outline`（R17）、想定質問は `BuildQuestionsPrompt` にある。残りは用語集 |
| 鮮度・部署メタデータのブースト | 保留 | 測る土台ができてから |
| 履歴・突合・700字の「修正」 | **不採用** | §2 のとおり前提が誤り |
