## 0. 実機事実と根本原因(調査6班の裏付け済み)

実機環境プロファイル(この端末で確定した事実):
- CreateObject("Word.Application") は組織ポリシーでブロック。GetObject(相乗り)はWordが起動中のみ成功。Acrobat COMなし。
- 共有パス config `nexus_share_path` に配布テンプレートのダミー値 `\\pgiofs01\Nexus_Share\` が残存(実在しない)。実在するのは `\\pgiofs01\share\E2T\...`。
- ファイル名にMac由来のNFD分解文字(U+3099結合濁点)を含むPDFが流入する。
- ユーザーIDはAD CN由来。チームコード規約は「氏名_E2T22」形式(3字部コード+2桁)が保存者プロパティで観測されている(AD CNに同形式が付くかは未確認)。

確定した根本原因(全て調査班のfile:line証拠つき):

RC1. スキャンPDF(文字層なし)で txtwrite 出力が空になると、optGsTxt.bas:185-192 の
     「txtwrite出力を読めず err#0」(E0302)が、設計済みの画像PDF判定
     (optOcrCore.GsTextVerdict→E0303→OCR)より先に発火し誤分類する。
     その結果フォールバックがWordへ流れ、WordのPDFリフローが生成したゴミが
     「総文字数 >= ページ数x10」というザルゲート(modExtractor.bas:266-274)を通過し、
     44頁の約款が chunks=1, status=done で「登録成功」になった(憲章§3-3/§4-1違反の最悪形)。
RC2. WaitForDoneFlag(optGsTxt.bas:313-326)は完了フラグの「存在」のみで完了と判定し、
     直後に読む中身が空(flag=[] rc=?)でもそのまま進む(TOCTOU)。診断のgs_out読みは
     「先頭500字」固定(optOcrCore.bas:349)のため、全頁完走でも途中で切れて見える。
RC3. RunGsAsync は wsh.Run(...,0,False) の完全fire-and-forgetでPID未保持。タイムアウトしても
     GS/cmd.exe を止める手段がなくorphan化しうる。タイムアウトは固定120秒でサイズ非依存。
RC4. mbtmp_一時コピー名は元ファイル名をそのまま連結(modExtractor.bas:353-364)し、
     クラシックOpen(ANSI/CP932経路, modExtractor.bas:396)で作成するため、U+3099等の
     CP932非対応文字でディスク上の実名とGSへ渡す文字列が乖離しうる(/undefinedfilename)。
RC5. 取込中の可視進捗は modShelfBatch の「N/M件 ファイル名」バナー1回のみ。
     GS待ち/Word変換/Acrobat中は一切更新されない。SetStageの3出力先はNexus画面では
     実質不可視(modUIMain.bas:343-347に自認コメント)。1件のみの取込ではETAが構造的に空。
RC6. 「Wordを開いたままにして、もう一度お試しください」という正確な案内文
     (modUtil.bas:773-779)が、modShelf.bas:158 で汎用E0302文言(Ghostscript前提)に
     上書きされユーザーに届かない。またWord閉+CreateObjectブロック端末では
     mPreferredMode が毎回0にリセットされ、1ファイルごとに4回の無駄な試行と
     word_doc_count_unknown x4 が再発し続ける。
RC7. deep(深掘り)とthoroughは同一フロー(RunDeepFlow)でパラメータ量の差のみ。
     会話で引用済みの資料へスコープを絞る機構は存在しない(modRetrieve.Search/
     SearchExpandedに包含フィルタ引数なし)。followupのeffortは「その瞬間のトグル値」を
     暗黙適用。入力は素のInputBox(幅制御不可)で、既存の幅広い nx_input を使っていない。
RC8. Hub「みんな(今日/今月)」= 全員のP2Pビーコン(自己解決クリック数x15分)のTTL600秒集計。
     共有パス未到達だと0分のまま凍結し「正常にゼロ」と区別不能。到達不能をUIに出す経路が
     ない(パス文字列が非空だと「未設定」警告も出ない)。15分係数は3モジュールに重複
     ハードコード。ビーコンに部署/チーム情報なし。sv:日付キーにはGCなし。
RC9. ナレッジ画面の「チャットへ」ボタンは実装済み(modKnowledgeBar.ToolbarSpec末尾、
     ハンドラOnToChatはActivateSheetRobust使用済み)だが、ツールバー最右端に配置され
     実機で見切れていた。ウィンドウリサイズ検知イベントは構造的に持てない
     (自己インストーラはクラスモジュール注入不可)。
RC10. thorough 114秒の内訳は計測不能(CallLLMのlatency_msを誰も記録していない)。
     質問処理中の段階ナレーションもない。E0303は3箇所から同一コードで発報され
     detail書式が異なり診断者が取り違える。

## R13-1: GS完了判定・タイムアウト・診断の根治 [P0, optGsTxt/optOcrCore]

1a. フラグ内容の検証: WaitForDoneFlag を「flagファイルが存在し、かつ中身が非空で数字として
    読める」まで完了とみなさない形へ。存在確認後、最大2秒(100ms x 20)の内容リトライ。
    2秒たっても中身が空なら「flag書込遅延」として扱い、さらに rc をログへ残す。
    これで rc=? flag=[] の症状クラスを消す。
2b. 空出力の正しい分類: finished=True かつ txt空 の場合、「txtwrite出力を読めず」で
    即E0302にせず、次で分類する:
      - rc=0 かつ gs_out に "Processing pages" がある -> 文字層なし(画像PDF)。
        optOcrCore.GsTextVerdict の "image" と同じ扱いで ERR_303 を返す(->OCRへ)。
      - rc<>0 -> 従来のE0302(GS実行失敗)。gs_outのtailを添える。
      - rc不明(1aのリトライ後も空) -> E0302だが detail に "flag_delayed" を明記。
    分類判定は純ロジック関数 `ClassifyGsTextResult(rc, txtLen, gsOutHasPages) As String`
    として optOcrCore(または新設modGsVerdict)に切り出し、LOテストで真理表を固定する。
1c. 生存監視型待機: 待機ループを「アイドルタイムアウト+絶対上限」の二段へ。
      - 2秒ごとに gs_out.log の末尾から "Page N" の最大値と gstext.txt のサイズを読む。
      - どちらかが前回より進んでいれば deadline を延長(アイドル起点リセット)。
      - アイドル上限 = 既存 vision_pdf_timeout_sec(既定120秒)を流用(意味を
        「無進捗許容秒数」へ変更、docs/70の該当記述も更新)。絶対上限 = 新config
        `gs_abs_timeout_sec` 既定1200秒。
      - 進捗は 1d の表示へ流す。
1d. 進捗表示: 待機ループ内で1秒に1回、modUIMain.ShowProgress で
    「本文抽出中… p/Nページ (経過 s秒)」を更新(Nは "Processing pages 1 through N" から取得、
    取れるまでは経過秒のみ)。ページレートが得られたら「残り約s秒」を付す。
    重要: silent(自動同期)経路では表示しない。表示可否は呼び出し元から引数で受け取る
    (modShelfSync は触らないこと。既存の引数経路で判別できない場合は module変数の
    セッションフラグをmodShelfBatch側で立てる設計にし、Fableへ設計を報告してから実装)。
1e. プロセス停止: RunGsAsync を WMI(winmgmts: Win32_Process.Create)起動へ変更してPIDを
    保持し、真のハング(アイドル上限超過)時に taskkill /T /F /PID で系統ごと停止する。
    WMIが使えない端末(EDR)向けに従来のwsh.Runへ自動フォールバック(その場合killは不可、
    usage_log に "gs_kill_unavailable" を1セッション1回記録)。停止実行時は
    "gs_killed_on_hang" を記録。32bit環境で動作すること。
1f. 診断のtail化: GsFailureDetail / ReadTextHead を「先頭500字」から「末尾500字」へ
    (エラーはログ末尾に出る。Processing pagesの行頭が切れても構わない)。

## R13-3: 品質ゲートと正直な失敗 [P0, modShelf/modLog/modExtractorPdf]
