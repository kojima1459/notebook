### ラウンド1: ChrW異体字バグ(確定・修正) — commit `3c095c7`
- **症状**: Nexus画面が真っ白/一部だけ描画されて止まる。`err#5`
  (プロシージャの呼び出し、または引数が不正です)。
- **原因**: `ChrW()`はBMP(0〜65535)しか受け付けないが、絵文字(📚等、U+10000以降)を
  `ChrW(&H1F4DA)`のように**1引数のみ**で渡していた。UTF-16サロゲートペア
  (`ChrW(&HD83D) & ChrW(&HDCDA)`のように2回に分ける)が必要。
- **調査手法**: 全.basファイルの`ChrW(&H...)`を機械的に走査し、コードポイントが
  0xFFFFを超えるもの(=異体字面・壊れている)76箇所/16ファイルを特定→Pythonスクリプトで
  一括サロゲートペア化。
- **別バグ(同時に発見・修正、原因は別)**: リテラル(ChrWでなく直接埋め込んだ)絵文字が
  VBEのソースバッファ制限で`AddFromString`注入時に「??」化する、見た目だけの別問題。
  126箇所発見、文字列内(コメント外)の15ファイル分のみ修正(コメント内は開発者しか
  見ないので無視して正しい)。
- **確度**: 完全確定。err#5のエラー番号・メッセージ・症状パターン全て一致。

### ラウンド2: Alignment=0バグ(確定・修正) — commit `1e33f5d`

  (指定された値は境界を超えています)。

  `.TextRange.ParagraphFormat.Alignment = 0` が無効値。msoParagraphAlignmentは

- **調査手法**: 同一プロパティへの代入をコードベース全体でgrep→他30箇所以上は
  全て1/2/3を使っており、この1箇所だけが0という矛盾を発見して確定。
  **これが「他に似たバグがないか横展開でチェックする」ことの威力を示した好例。**
- **同時に修正(別の独立バグ)**: 「戻る」ボタン群(`modApp.OnNavChat`/`SummonNexus`、
  `modDash.OnDashBackToChat`、`modHelp.OnBackToNexus`、`modVault.OnVaultBackToChat`)が

  (`DisplayWorkbookTabs=False`)、ユーザーは完全に閉じ込められていた。
  → `modUI.GoToNexus`共通ヘルパーを新設。Activate失敗時は`RestoreExcelUI`
  (既存の緊急脱出関数)でネイティブタブを復元し、最低限マウスで手動脱出できる

  Nexusタブに戻ってこれる」)= 実機で効果を確認済みの数少ない修正の1つ。**
- **確度**: Alignment=0は完全確定。GoToNexusは実機確認済み。

### ラウンド3: 名前入力ダイアログのタイミング仮説(検証→否定) — commit `145dd1f`

  **過去に実際に解決された同種の問題**の記録も見つけた。
  → 「モーダルダイアログ表示等、特定操作の直後はExcelのActivateが不安定になる」
  という同種の問題が、今回は名前入力ダイアログによって再発している可能性、という
  仮説を立てた。
- **対応**: この仮説は「推測」に近いと自己判断し、**AskUserQuestionでユーザーに
  明示的に許可を取ってから**実装した(標準の「推測禁止」指示を尊重しつつ前進する
  ための判断)。`modBoot.RunFirstRunPromptEarly`(新設Public)を追加し、自己インストーラの
  `Workbook_Open`内、`Application.OnTime`でBootを予約する**前**に同期呼び出しするよう
  変更。OnTime自体はユーザー指示どおり維持し、ダイアログの発生タイミングだけを
  変えた。
- **結果: 否定された。** 次のラウンド(`fe8c382`、この仮説修正を含むビルド)でも

  「はじめにお読みください」がActiveSheetのままActivateに失敗し続けている。
- **教訓**: この仮説は棄却してよい。名前入力ダイアログのタイミングは原因ではない
  (少なくとも単独では)。**この方向のコード変更を再度提案してはいけない。**

### ラウンド4: 4件の確定バグ発見 — commit `fe8c382`
このラウンドの発端は、ユーザーが「マイ本棚は空/ダッシュボードボタンを押しても
遷移しない/ナレッジ倉庫の登録画面がおかしい/チャット入力欄が見当たらない」等
複数の症状を一度に報告してきたこと。全部を1つずつ画像とコードを突き合わせて
確定させた。

1. **`modUIDashboard.RenderBadges`**: `ws.Range("A8:H8").Value = line`を
   **未結合の複数セル範囲**に代入していた。VBAでは未結合の複数セル範囲に
   スカラー値を代入すると**全セルに同じ値が複製される**(バグではなく仕様)。
   2行上のタイトル行は`.Merge`してから代入していたのに、バッジ行だけ抜けていた。
   スクショの「同じ文言が全列に並ぶ」症状と完全一致。→ `.Merge`を追加。
2. **`modVault.ShowVaultInput`**: 白い角丸の背景をShape(図形)で描画していたが、
   **Excelでは図形は常にセルより手前に描画される**(ZOrderはShape同士の前後関係
   にしか効かず、セルとの関係には無関係)。そのため下に書いていたタイトル/本文/
   タグの入力欄ラベルが完全に図形に隠れていた。ボタンだけは後から追加された
   別のShapeなので見えていた。→ 図形をセルの塗りつぶし色に置き換え。
   **この「Shapeは常にセルより手前」という知見は今後も重要。同種のバグを
   他で見つけたら即座に疑うこと。**
3. **`modUI.DrawInputArea`**: チャット入力セル(`nx_input`)が2行目(D2)にあったが、
   その行のY座標(18〜36pt、全行RowHeight=18pt均一のため)は、トップバー背景Shape
   の範囲(Y=0〜TOPBAR_H=45)に完全に収まっており、**上と全く同じ理由で入力欄
   自体が最初から100%不可視**だった。「チャットの入力画面がどこにあるか
   わからない」という報告と一致。→ 4行目(トップバーの外)に移動し、白背景+枠線を
   付けて視認可能に。`ApplyTheme`の一括`ws.Cells.Interior.Color`塗り直しが
   この背景を消してしまうため、そこでも再塗りするパッチを追加。`ParkFocus`の
   D2参照もD4に修正。
4. **`GetOrCreateNexusSheet`/`GetOrCreateGallerySheet`/`GetOrCreateVaultSheet`/
   `GetOrCreateDashSheet`(4関数)**: いずれも`Worksheets.Add`→`ws.Name = X`という
   2段階でシートを作成しているが、**Name代入が失敗した場合、追加されたシートは
   Excelの既定名(Sheet2等)のまま孤児化して残る**。これは確実に存在する不具合。
   実機で繰り返し報告されている謎の「Sheet2」タブの**唯一の原因かは未確定だが、
   もっともらしい説明候補**。→ 4関数とも失敗時にそのシートを削除するよう修正。

**確度**: ①②③は完全確定(コードの矛盾/仕様から明確に導出)。④は「確実なバグでは
あるがSheet2の唯一原因と断定はできない」という中間的な確度。

### ラウンド5: KPIカード1枚しか出ない問題(確定・根本原因特定) — commit `2cb72fe`
- **経緯**: ラウンド4で`modDash.ShowDashboard`/`OnDashRefresh`のFailハンドラが
  エラーを無言で握りつぶしていたことに気づき、`modLog.LogError`を追加していた
  (この時点では原因不明、証拠だけ仕込んだ)。次のラウンドでこのログが実際に
  発火し、証拠を掴めた。
- **症状**: ダッシュボードのKPIカードが4枚中1枚しか出ない。バッジ棚・グラフ・
  管理者セクションも一切出ない。
- **原因**: `modDash.DrawKpiCard`が3行のテキストを`vbLf`で連結して1つのShapeに
  入れ、`.TextRange.Paragraphs(2).Font`で2段落目を装飾していた。しかし
  **TextFrame2のParagraphsコレクションは`vbCr`でしか段落として分割されず、
  `vbLf`では全体が1段落のまま**になる。存在しない`Paragraphs(2)`へのアクセスが
  「指定したコレクションに対するインデックスが境界を超えています」
  (err#-2147024809)で例外を投げ、1枚目のカードのShapeが追加された**直後**に
  `DrawKpiRow`以降の全処理(カード2〜4、バッジ、グラフ、管理者セクション)が
  中断されていた。「1枚だけ出る」という症状と完全に一致。
- **対応**: `vbLf`→`vbCr`に修正。加えて`mDashStep`という段階トラッカーを追加し、
  今後`DrawDashboard`のどこで失敗してもログに残るようにした
  (この「先に計装してから次のラウンドで証拠を得る」パターンは今日最も有効だった
  手法。§6参照)。
- **確度**: 完全確定。エラーメッセージ・番号・症状すべて一致。他のバッジカード
  (`DrawBadgeCard`)は`Paragraphs(1)`しか使っておらず(常に安全)、同じ問題は
  持っていないことも確認済み。

### ラウンド5(同時): WriteSafeマージバグ(確定・修正、ラウンド4①と同系統)
- **症状**: マイ本棚タブの「本棚フォルダ: (未設定...)」「自動同期: オフ...」の
  文言が全列に複製表示される。ラウンド4①のバッジと全く同じ見た目の症状。
- **原因**: `modUIMain.bas`と`modUIShelf.bas`に**それぞれ独立して存在する**
  `WriteSafe(cell, text)`ヘルパーが、`cell.Value = t`を**Merge確認なしに**実行
  していた。これは「EnsureLayoutが既にそのセル範囲を`.Merge`済みである」という
  前提に依存したコードだったが、**EnsureLayoutはこのセッション中ずっと1004で
  途中終了し続けている**ため、Mergeが実行されないままこのヘルパーが呼ばれ、
  結果的に複製表示が起きていた。
- **重要な洞察**: これは独立したバグというより、**未解決の根本1004問題の
  下流症状**。EnsureLayoutが最後まで走っていれば発生しなかった。
- **対応**: 両ファイルの`WriteSafe`に、書き込み前に`If cell.Cells.Count > 1 Then
  cell.Merge`を追加。根本原因(1004)を直さなくても、この防御だけで症状は
  出なくなるはずの堅牢化。
- **確度**: バグの存在自体は完全確定(コードの前提が崩れているのを直接確認)。
  ただし「なぜMergeされていないか」の根っこは1004問題そのもの。

### ラウンド5(同時): PDF取込エラーの生ログ漏れ(防御的対応のみ、原因未特定)
- **症状**: 「取込に失敗しました:取込に失敗[ファイルからの本文抽出](#462)」
  「err#462: リモート サーバーがないか、使用できる状態ではありません。」という
  意味不明なエラーがユーザーに表示される。
- **調査**: `modShelf.IngestFile`→`modExtractor.ExtractFile`→
  `ExtractPdfWithFallback`→`modExtractorWord.Extract`/`modExtractorAcrobat.Extract`
  の全チェーンを読んだ。**各アダプタ(Word/Acrobat)は自分のCOM呼び出しを
  `On Error GoTo Failed`で適切に捕捉し、Boolean+errDetailへ変換する作りに
  なっている**ことを確認済み。しかし実際のログには、その整形済みメッセージ
  (「Word: X / Acrobat: Y」形式)ではなく**生のエラー番号**が出ていた
  = どこかで例外が捕捉されずに素通りしている。
- **正直な結論**: **静的解析だけでは正確な漏れ箇所を特定できなかった。**
  各アダプタの内部は確認したが、抜けている1行を見つけられていない。
- **対応(防御のみ)**: `modExtractor.ExtractFile`のディスパッチャ自体には

  ここに保険的な`On Error GoTo ExtractFailed`を追加し、どこから漏れても
  E0302+説明文に変換されるようにした。**これは根本原因の修正ではなく、
  症状を隠すための防御。次に失敗したら、今度はE0302の整形されたメッセージで
  ログに残るはずなので、そこから追える。**
- **確度**: 低い。根本原因不明のまま防御だけ入れた状態。

## 2. 良かった点(思考面・作業面)

1. **証拠ベースの絞り込みが徹底できていた**: 毎ラウンド、err_logの生データと
   実機スクショを直接読み、コード内の矛盾(「他の30箇所は正しいのにここだけ違う」)
   を横展開で探すという手法が終始一貫していた。単なる思いつきでコードを触った
   ケースはほぼゼロ(唯一の例外がラウンド3の仮説で、それすらユーザーの明示的な
   許可を取ってから実行した)。
2. **確度の3分類を最後まで崩さなかった**: 「確定バグ」「検証が必要な仮説」
   「原因不明のまま入れた防御」を常に明確に区別し、ユーザー報告でもその区別を
   崩さずに伝えた。仮説が外れたときも正直に「否定された」と報告した
   (成功したふりをしなかった)。
3. **「1つ見つけたら他にもないか横展開する」を徹底**: Alignment=0バグは
   全コードベースの同種代入を横断チェックして確定させた。WriteSafeバグは
   1箇所(modUIDashboard)で見つけた後、同じヘルパー名を持つ他の2ファイル
   (modUIMain/modUIShelf)まで能動的に探しに行って発見した。GetOrCreateXSheetの
   孤児化バグも1つ見つけてから同型の他3関数を横展開でチェックした。
4. **「先に計装、後から診断」パターンが効いた**: ラウンド4で
   `modDash.ShowDashboard`/`OnDashRefresh`のFailハンドラにログを追加した時点では
   原因不明だったが、そのログが**次のラウンドで実際に発火し**、Paragraphs(2)
   バグを突き止める決定打になった。これは「わからないなら証拠を仕込んでから
   待つ」という、無闇な推測より確実で早いアプローチだった。
5. **仮説実行前にユーザー許可を取った**: ラウンド3(名前入力ダイアログの仮説)は
   「推測に近い」と自己判断し、AskUserQuestionで明示的に説明・許可を取ってから
   実装した。結果は否定されたが、これは「無断で推測ベースの変更をした」の
   ではなく「合意の上で仮説検証をした」ので、プロセスとしては正しかった。

## 6. 今後の思考法(エラーにどう向き合うと最短で直せるか)

このセッションで機能した/しなかった思考パターンを整理する。**この節は今後
毎回のエラー対応で参照すること。**

### やるべきこと
1. **err_logとスクショを1行も読み飛ばさず、まず全体像を掴む。** 特に
   `version`列(どのコミットか)と`ActiveSheet`/`ws.Visible`等の診断値は
   毎回必ず突き合わせる。
2. **「同じパターンが他にもないか」を必ず横展開でチェックする。** 1箇所の
   バグを直して終わりにせず、同じ関数名(WriteSafe)、同じイディオム
   (未Merge代入、Shape背景+セル文字、Paragraphs(n)アクセス)がコードベース内に
   他にないかgrepする。今日の成功例の大半はこれで生まれた。
3. **わからない時は、直そうとする前に「証拠を残す仕組み」を先に入れる。**
   Failハンドラが無言で握りつぶしているのを見つけたら、まずログを追加して
   次のラウンドを待つ。これは「当てずっぽうの修正」ではなく「観測点を増やす」
   行為であり、ユーザーの「推測禁止」指示にも抵触しない。
4. **確定・仮説・防御を常に3つに分けて考え、その区別のままユーザーに伝える。**
   仮説を試すときは、ユーザーの明示的な許可を取る(AskUserQuestion)。
5. **コードだけで説明がつかなくなったら、環境要因を疑う番だと認識する。**
   今日の1004問題のように、あらゆる静的解析・ログ計装・仮説検証をやっても
   説明がつかないなら、それはコードの中に答えがない可能性を意味する。
   Windows/Officeのバージョン、Trust Center設定、セキュリティソフト、
   イベントビューアーのログなど、**アプリの外側**の情報を取りに行くべき
   タイミングを見極める。
6. **モジュールサイズ上限のトリミングは、最初から簡潔に書いて後工程を減らす。**
   新しいコメントを書くときは、「実機報告(日付)」のような冗長な枕詞を
   多用せず、要点だけを1〜2行で書く。

### やってはいけないこと
1. **同じ仮説を形を変えて何度も提案しない。** ラウンド3で「名前入力ダイアログの
   タイミング」説は明確に否定された。似た理由付け(「モーダルダイアログの
   タイミングが原因」系)を別の形で再提案しない。
2. **「他のバグを直したから、たぶん根本原因も直っただろう」と楽観視しない。**
   周辺バグを直すことと中核症状が直ることは別。テストで確認できるまでは
   「まだ直っていない」という前提で報告する。
3. **ユーザーの許可なしに、検証されていない仮説でコードを変更しない。**
   低リスク(絵文字除去のような、機能に影響しない変更)は許容されるが、
   起動シーケンスやアーキテクチャに関わる変更は必ず先に説明し許可を取る。
4. **ビルドスタンプの1コミット遅延を、毎回「バグ」として扱って無駄な
   resyncコミットをしない。** これは原理的な制約(§7)であり、ユーザーには
   タイムスタンプ部分を信用してもらうよう既に伝えてある。

### ビルドスタンプの仕様(重要・毎回思い出すこと)
`build/build_mybookshelf.py`の`compute_build_stamp()`は`git rev-parse HEAD`を
**ビルド時点**(=コミットする前)に読む。コミットは自分自身のハッシュを
埋め込めない(ハッシュはコンテンツから計算されるため)ので、**dist/*.xlsmに
埋め込まれるハッシュは、それをpushしたコミットの1つ前を指すのが常に正しい
仕様**。ユーザーには「ハッシュではなくタイムスタンプ部分で鮮度を判断してほしい」
と伝達済み。

### 検証・ビルドの決まり手順(cwd=リポジトリルート)
```
python3 tools/vba_lint.py                 # ERROR:0であること
python3 tools/run_lo_tests.py              # PASS件数/FAIL0であること
python3 build/build_mybookshelf.py --dev
python3 build/build_mybookshelf.py --prod
git add -A dist/ src/... (触ったファイルのみ明示的に)
```

### 今日発見した恒久的な技術知見(次に似た症状を見たら即座に疑うこと)
1. **未結合の複数セル範囲に`.Value = scalar`すると、全セルに同じ値が複製される。**
   Merge済みの前提で書かれたUpdate系ヘルパー(WriteSafeのような)は要注意。
2. **Excelの図形(Shape)は常にセルグリッドより手前に描画される。** ZOrderは
   Shape同士の前後関係にしか効かず、セル文字を隠しているShapeがあれば
   ZOrderをどういじっても解決しない。デザイン上「背景パネル」が欲しいなら
   セルのInterior.Colorを使うこと。
3. **TextFrame2のParagraphsコレクションは`vbCr`でしか段落分割されない。**
   `vbLf`を段落区切りに使うと`.Paragraphs(2)`以降が「コレクションの
   インデックスが境界を超えています」で例外になる。
4. **`Worksheets.Add`→`.Name = X`は、Name代入が失敗すると孤児シート
   (Sheet2等)を残す。** シート作成ヘルパーはFailハンドラで必ず後始末
   (`ws.Delete`)すること。
5. **ネイティブMsgBox(Win32)は、Excelの図形テキスト(TextFrame2/DrawingML)
   より絵文字グリフの表示が弱い可能性がある**(未確証・推測)。

## 9. 現在の懸念点とその理由

1. **1004問題がこのユーザーの環境固有(コードの問題ではない)である可能性を
   まだ排除できていない。** もしそうなら、これ以上コードを変更しても直らず、
   Trust Center設定の変更やIT部門の関与が必要になるかもしれない。この可能性を
   検証する手立て(§4・§8)がまだ手つかずなのが最大の懸念。
2. **AddShapeがActivate失敗と連動して失敗するが、セル書き込みは連動せずに
   成功する、という非対称性の意味がまだわかっていない。** この環境固有の
   挙動(Shapes.AddShapeが「真にアクティブな」シートを要求するように見える)を
   説明できる具体的な仕組みが不明なままなので、次にコードで対策を打つとしても
   何をすべきか判断材料がない。
3. **今日直した11件は全て「周辺症状」であり、中核の起動シーケンスは
   一度も実機で完走が確認できていない。** ホーム画面での質問機能、
   マイ本棚への資料追加機能という、このアプリの一番のコア機能が、
   今日1日を通して一度も実機で動作確認されていないという事実を、
   周辺バグの修正数の多さで見誤らないこと。
4. **各ラウンドのフィードバックループが非常に重い**(実機再現→スクショ→報告→
   コード修正→検証→ビルド→push→再度実機テスト、を1往復するのに人間側の
   実機作業時間がかかる)。今後も同じペースで続くなら、1往復あたりの
   価値(できるだけ多くの確定バグを同時に潰す/できるだけ多くの診断情報を
   同時に集める)を最大化する意識を持つこと。
