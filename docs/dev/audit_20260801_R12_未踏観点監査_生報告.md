# 監査報告: ライフサイクル・グローバル状態の完全性(HEAD a541474)

## 指摘

### 1. [Critical] アプリ内「終了」ボタンが本番ビルドでは Auto_Close を一切実行しない(OnKey残存・UI復元不能・条件次第でOnTime幽霊再オープン)

**ファイル:行**: src/ui/modApp.bas:648、build/build_mybookshelf.py:844-846(自己インストーラ)

**根拠(コード引用)**:
- modApp.bas:633-648 `OnSaveAndExit`:
  ```
  modUiLock.Leave
  ThisWorkbook.Close SaveChanges:=(resp = vbYes)
  ```
  Close前に `modBoot.Auto_Close`/`RunAutoMacros` の呼び出しが無い。
- インストーラ(_INSTALLER_SRC_TEXT、build:844-846)は
  ```
  Private Sub Workbook_Open()
    Install
  End Sub
  ```
  のみで **Workbook_BeforeClose が存在しない**。本番ビルドでは ThisWorkbook ストリームをこのインストーラが恒久占有する(modules.json:598-599 で src/ui/ThisWorkbook.cls は vba_src:false=参照用)。
- Excelの仕様上、VBAからの `Workbook.Close` は Auto_Close マクロを実行しない(実行されるのはユーザー操作の閉鎖時のみ。Workbook_BeforeClose イベントなら発火するが、本番ビルドには存在しない)。

**実害シナリオ(現実性: 高)**: 「終了」ボタンは「安全な終了方法が分からない」という実機要望で追加された推奨経路であり、Hub(modHub.bas:596)・ナレッジ(modKnowledge.bas:270)・Nexusヘッダー(modUINexusDraw.bas:303)・ダッシュボード(modDash.bas:294)の全画面から到達する。本番configは nexus_ui=TRUE 既定(build:291)なので毎回 InitUI がグローバル状態を変更済み。この経路で閉じると:
1. `Application.OnKey "^z", ""`(modUI.bas:492)が残存 → **閉じた後もExcel全体で Ctrl+Z(元に戻す)が死ぬ**(セッション終了まで)。
2. `^+q`/`^~`/`^{ENTER}` が閉じたブックのマクロに紐付いたまま → 他ブックで Ctrl+Enter を押すと「マクロを実行できません」の生ダイアログ(modBoot.bas:546 自身が「残存するとブック閉鎖後にエラー」と明記する事象)。
3. RestoreExcelUI 不実行 → リボン非表示(SHOW.TOOLBAR)・DisplayFullScreen=True・数式バー/ステータスバー非表示がExcel全体に残る(数式バー表示はExcelのオプションとして次回起動後も残り得る)。
4. modTelemetry.Publish(設計上「送信は終了時」)が実行されず、この経路で終了する利用者の利用統計は送信されない。
5. sync_interval_min>0 設定時は AutoSyncTick の OnTime 予約が未解除のまま → **閉じたブックをExcelが勝手に再オープンし、インストーラが走って保存までする**(docs/40:186 が「出ないはず」と主張する事故そのもの。既定0のため既定構成では発生しない)。

docs側(MASTER_SPEC §12、解説書:1228、docs/40:186)は「Auto_Closeが必ず解除する」前提で書かれているが、その前提が主要終了経路で成立していない。開発構成(ThisWorkbook.cls あり)では Workbook_BeforeClose 経由で救済されるため、実機の本番ビルドでのみ発現する。§3/§5-9/HANDOFF §2-3 に該当裁定なし。

**修正方向**: `ThisWorkbook.Close` の直前に `modBoot.Auto_Close` を明示呼び出しする(Auto_Closeは冪等に書かれており二重実行は安全)。または `ThisWorkbook.RunAutoMacros xlAutoClose`。

### 2. [Med] X閉じ→保存確認「キャンセル」後、ホットキーと自動同期が死んだまま復帰しない

**ファイル:行**: src/ui/modBoot.bas:534-566(Auto_Close)

**根拠**: Auto_Close はユーザーのX閉じ時、Excelの保存確認プロンプトより前に実行される(R7 A-2 が「閉じる→キャンセルで表示が崩れる」を実測済み=RestoreExcelUIが先に走った証拠)。キャンセルで閉鎖が中止されてもAuto_Close の副作用は残る。表示系は EnsureAppView(modUI.bas:384)が次の遷移で自己修復する裁定済みだが、**OnKey 3種(`^+q`/`^~`/`^{ENTER}`)の解除と CancelAutoSync・CancelPendingInstallerBoot は再登録経路が無い**。

**実害シナリオ(現実性: 中〜高)**: ui_state 書込み等でブックはほぼ常時dirtyのため、X閉じでは毎回プロンプトが出る。「キャンセル」を押した利用者は、以降そのセッション中 Ctrl+Enter 送信・Ctrl+Shift+Q 召喚が無反応(ボタンクリックは可能なので機能全損ではない)、sync_interval_min>0 なら自動同期も停止。無言の機能低下で、利用者には原因が見えない。

**修正方向**: Workbook_BeforeClose が使えない以上、キャンセル検知は困難。ホットキー登録と ScheduleAutoSync を EnsureAppView 相当の「遷移時の自己修復」に含めるのが同型解(既存裁定 R7 A-2 の拡張)。

### 3. [Med] 新旧2版併存時のグローバル資源衝突(OnKey上書き・先に閉じた側が生存側の資源を解除・OnTimeプロシージャ名がブック非修飾)

### 4. [Low(可能性指摘)] L-23フォールバック(ui_state経由のOnTime解除)は CStr の15桁精度で予約時刻が完全一致しない可能性

**ファイル:行**: src/ingest/modShelfSync.bas:504/533、src/core/modState.bas:66

**修正方向**: SaveState の値を文字列でなく数値セル直書きにする専用保存(インストーラE1と同方式)へ変更するか、解除失敗時に Err を確認してログを残す。

### 5. [Low] インストーラの再保存失敗が完全無言+「Setup incomplete」ガードの検知漏れ

### 6. [Low] ScheduleAutoSync の予約失敗が Debug.Print のみ(実機では観測不能)

## 指摘1 [Med] 連続利用日数(streak)が実機Excelで永久に1のまま — セルの日付型自動変換と文字列比較の不整合

**ファイル:行**: src/stats/modStats.bas:140-148(読み比較側)/ modStats.bas:524-531(書き側)/ modStats.bas:534-547(読出実装)

**根拠(コード引用)**:
- 書き側(SetStatValue → 汎用セル書込。my_stats value列はビルドで書式指定なし=General):
  ```vb
  ws.Cells(r, 2).Value = value        ' "2026-08-01" はExcelが日付型へ自動変換する
  ```
- 読み側(GetStatValueString):
  ```vb
  Dim v As Variant: v = ws.Cells(r, 2).Value
  GetStatValueString = CStr(v)        ' 日付型セルはロケール短形式 "2026/08/01" になる
  ```
- 比較(TouchToday):
  ```vb
  If lastStr = todayStr Then                                        ' "2026/08/01" vs "2026-08-01"
  ElseIf lastStr = Format$(PrevBusinessDay(Date), "yyyy-mm-dd") Then ' 同上
  Else
      SetStatValue "streak_days", 1                                  ' 毎回ここに落ちる
  ```
この「文字列で書いた日付がセルで日付型化し、CStrでロケール表記に変わる」現象は、本リポジトリ自身が実機バグとして記録済みである(src/ui/modUIShelf.bas:630-635「【2026-07-16 恒久修正】セルの日付型自動変換により…"2026/07/16 15:02:33"(日付型セルをCStrしたロケール表記)の両方があり得る」)。表示系(modUIShelf.ShortDate / modVaultGallery.ShortStamp / modDashStat.IsThisMonthStamp)はIsDate分岐で対処済みだが、modStats.TouchToday の等値比較だけが未対処。なお同モジュール内の IsBusinessDay(modStats.bas:167)は `Replace(hol, "/", "-")` で正規化しており、この型の防御が streak 比較にだけ配られていない(憲章§4-5「同型の問題は共通部品で一度だけ解決」に反する状態)。

**実害シナリオ(現実性: 高・無条件)**: 既定の日本語Windows(短い日付形式 yyyy/mm/dd)の実機Excelで、営業日を何日連続で使っても `lastStr`("2026/08/01")と `Format$(...,"yyyy-mm-dd")`("2026-08-01")が一致せず、毎回 Else 分岐で streak_days=1 にリセット。結果: Hubタイル「連続利用」が常に1日(src/ui/modHubStat.bas:281)、バッジ streak7「7日連続利用」が構造的に獲得不能(modStats.bas:207)、telemetry の streak 送信値(modTelemetry.bas:69)とプロンプト参照(modPrompts.bas:413)も常に1。エラーは出ず、静かに壊れる型。LOテストでは検出不能(セル型変換はExcel実機挙動)で、実機スモーク(15分)でも多日運用が要るため見えない。

**修正方向**: 読み側で正規化してから比較する。例: `If IsDate(lastStr) Then lastStr = Format$(CDate(lastStr), "yyyy-mm-dd")`(ShortDateと同型)。または my_stats value列を書込前に NumberFormat="@" にして型変換自体を封じる(後者は既存データの移行考慮が要る)。

## 指摘2 [Med(条件付き・実機未確認)] Windows「カレンダーの種類=和暦」端末で失効判定(guard_last_reach)が誤作動し得る — 知識の誤消去または kill switch の無言無効化

**ファイル:行**: src/stats/modGuard.bas:138(書き側)/ modGuard.bas:156-167(読み側)/ src/core/modShareRule.bas:216-222(wipe到達経路)

**根拠(コード引用)**:
- 書き: `modStats.SetStatText K_LAST_REACH, Format$(Date, "yyyy-mm-dd")`
- 読み: `DaysSinceReach = CLng(Int(Date - CDate(s)))`

VBAの Format$/CDate は地域設定のカレンダー種別に従う(ja-JPの「カレンダーの種類=和暦」設定時、`Format$(Date,"yyyy")` が元号年を返すのはVBA/VarFormatの既知挙動)。この端末では guard_last_reach に "0008-08-01"(令和8年)型の文字列が書かれる。年8はExcelのセル日付として認識されないため文字列のまま残り、読み側 `CDate("0008-08-01")` の解釈は環境依存で、(a) 過去年(2桁年窓処理で2008等)に解釈されると `Date - CDate(s)` が数千日となり、ExpiryDecision が warn_first(1回目の起動で警告)→ wipe(2回目の起動で my_knowledge/my_vectors 全消去)に到達する。(b) 変換エラーなら On Error Resume Next で DaysSinceReach=0 に落ち、失効タイマーが永久に発火しない(持ち出し対策の無言無効化)。左辺 `Date` はシリアル値で常に西暦のため、文字列側だけが元号化する非対称が問題の核。

**実害シナリオ(現実性の評価)**: 発生には (1) カレンダー種別=和暦の端末、(2) knowledge_expire_days>0(出荷既定は0=無効。HANDOFF §3で本格展開時に30以上へ変更予定)、(3) nexus_share_path 設定済みかつ到達記録あり、の3条件が必要。現時点の配布既定では実害ゼロ。ただし本製品は保険営業向けで、和暦運用の強い業種であり「日本語Windows前提」はこの設定を排除しない(和暦は ja-JP の設定である)。方向(a)ならデータ喪失(憲章§3-5の最上位)、方向(b)なら防御機能の無言喪失(憲章§4-1)。(a)の場合も warn_first の警告モーダル(「○○日間つながっていません」に異常な日数が出る)が1回挟まるため完全無言ではないが、利用者が意味を理解して止められる可能性は低い。方向は実機でしか確定できないため条件付きMedとする。

**修正方向**: 日付の永続化を文字列でなくシリアル値(CLng(Date) や CDbl(Now))に統一するか、読み側で `Like "####-##-##"` +年範囲(1990-9999)検査を行い、範囲外なら「判定不能」として guard_material_fail ログ+失効見送りへ倒す。書き側も DateSerial 逆算のロケール非依存整形(自前で年月日を連結)にする。

## 指摘

### 指摘1 [Med] 既定チャンク化(structure)のブロック組立てがループ内文字列連結 — 見出しの無い大きなテキストでO(n²)化しExcelが数分〜無応答化する

- **ファイル:行**: src/ingest/modChunker.bas:402-403(ChunkAllPagesStructured)、同473-474(ChunkOnePageStructured)
- **根拠(コード引用)**:
  ```vb
  If LenB(blockText) > 0 Then blockText = blockText & vbLf
  blockText = blockText & rowText
  ```
  blockText のフラッシュ契機は「見出し行(ClassifyLine=1/2)」と「終端」のみで、**サイズ上限によるフラッシュが無い**。見出しが一つも検出されない資料では blockText が資料全文まで単調成長し、行数nに対し総コピー量が Σ(累積長) = O(n²) になる。本リポジトリ自身が modSparse.bas:126-130 で「文字列を "toks = toks & x" で伸ばしてはいけない。O(n²)になり900字で200ms(実測)。規約§12にも明記」と規定しており、その規約に反する実装が既定取込経路に残っている。
- **実害シナリオ(現実性評価)**: chunk_mode 既定は "structure"(build_mybookshelf.py:268、modShelf.bas:166)。txt/md/csv は全文1ページ扱い(modExtractor.bas:602)のため、見出し記法(「# 」「第N章」等)を含まない数MB級のtxt/csv(エクスポートした一覧表など)で無条件に発現する。概算: 2MB/4万行 → 累積コピー約80GB(数十秒〜)、10MB/10万行 → 約1TB(分〜十分単位)。この間ループ内に DoEvents が無く「(応答なし)」となり、憲章§3-2(止まっているのか動いているのか分からない状態を作らない)に反する。利用者は強制終了し取込は失敗扱いになる。R12-3-4 の 50MB ガードは本件を防がない(50MB未満で既にハングする)。数百KB級の通常PDFでは累積コピーが数GB以下で体感1-2秒に収まるため、発現は「MB級かつ見出し無し」に限られる。
- **修正方向**: 行を String 配列に積み、FlushBlock 時に Join(…, vbLf) で結合する(Tokenize と同じ作法)。併せてブロック長が mx を大きく超えた時点での中間フラッシュを検討(FlushBlock は超過ブロックをスライディング分割するので機能互換)。

### 指摘2 [Low(可能性)] JoinSplitNumbers の1文字ずつ連結 — 「第」を含む超長単一行でのみO(len²)ハング

- **ファイル:行**: src/ingest/modChunker.bas:187-222(`out = out & c`、193/202/214/217)
- **根拠**: 行内に「第」があると行全体を1文字ずつ `out = out & c` で組み立て直す。行長Lに対しO(L²)。通常の行(〜1,000字)は無害だが、改行を持たないtxt/CSV行(1行=数十万字)に「第」が1つでも含まれると、その1行だけで数十GB〜のメモリコピーになる。NormalizeForIngest は全取込経路の入口(modChunker.bas:152-153)。
- **実害シナリオ(現実性評価)**: 発現には「1行が10万字級」+「第を含む」の複合が必要。抽出系(GS/Word/OCR)は改行を出すため、実質は改行なしtxt/巨大セルCSVに限られる。可能性ベースのためLow。
