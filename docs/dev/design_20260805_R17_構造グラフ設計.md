# R17設計書: 軽量ナレッジグラフによる取込・回答の根本精度向上(2026-08-05)

状態: オーナー提案待ち(GOでR17として実装)。裁定者: Fable。
背景: 実機第5報④「取り込み精度・アウトプット精度の改善余地は? 取込か、意味づけか、
プロンプトか、パイプラインか。コスト度外視でよい」+共有文献(Zenn『ナレッジグラフ実践入門』)。

## 1. 診断(どの層がボトルネックか)

システムプロンプトではない。原因は上流の2点(調査I3/I4で確定):
1. 取込時の構造捨象: 章・節・条・項の階層と「第8条参照」「別表2」のような明示的参照
   関係を捨ててフラットなチャンクにしている(modChunker は構造単位で切る所までは
   やっているが、構造の「ラベル」も「参照」も保存していない)。
2. 点検索: dense+sparse のスコア上位k個の「点」を拾うだけで、規程文書の回答に必要な
   「面」(条文全体+参照先+但し書き)を組み立てる機構がない。
   ※R16-3C(近傍束ね)が「同一文書内の面」の第一歩。本設計はその発展形。

## 2. 文献の評価(正直な注記つき)

Zenn本(全9章)は本文がSPA描画のため直読不可。同一著者の関連記事群+一般文献
(GraphRAG/LightRAG/Entity Resolution)からの再構成で評価した(調査I4)。
結論: フルGraphRAG(グラフDB・Leidenコミュニティ検出・embedding ANN)はこの環境
(Excel 32bit VBA/ワークシートのみ/ChatGPTV同期のみ)では不可能。しかし本質は移植可能:
- グラフDB → ワークシート上のエッジ表(参照リスト)で代替
- コミュニティ要約(グローバル検索) → マニュアルが既に持つ「章」を人手コミュニティと
  みなし章単位要約で代替
- エンティティ抽出・名寄せ → 取込時のChatGPTV呼び出し(スキーマ駆動・行形式出力)で代替
皮肉なことに、汎用KG構築より「規程文書が既に持つ構造を機械抽出する」方が
この文書種別ではROIが高い、が最終評価。

## 3. 三段構成(実装順に効果/コスト昇順)

### Phase 1: 構造メタデータ+参照エッジ(純VBA・LLM追加0回) — 最優先
- 取込時: チャンク確定後に自前パーサ(InStr/Mid。VBScript.RegExp は非推奨化・
  政策リスク・LOテスト不能のため不使用)で
  (a) 各チャンクの構造ラベル: 直近見出しから「第3章>第12条」形式の section_path
  (b) 本文中の明示参照: 「第N条」「第N項」「別表N」「様式N」「第N章」→ 参照先ラベル列
  を抽出。
- 保存: 新シート chunk_meta(chunk_id, section_path, refs_out)。既存 my_knowledge の
  10列スキーマは変更しない(列追加は配布済み本棚の移行が必要になるため不採用。
  新シートは「無ければ全機能が従来どおり」のフェイルセーフで導入できる)。
  既存資料は再取込で生成(移行処理は書かない)。
- 検索時:
  (a) 質問に条文番号が含まれる場合(既存 DistinctiveKeys が「第N条」を最優先抽出済み)、
      dense検索より先に section_path/参照ラベルの直接キー検索を試す(0呼び出し・即答性)。
  (b) ヒットチャンクの refs_out を1ホップ展開し、参照先チャンクを R16-3C の精読束に
      合流させる(「第6条を読むなら、6条が参照する8条と別表2も同じ束で読む」)。
- 期待効果: 最大。規程QAの最頻質問(「第5条の免責は?」「8条との関係は?」)に直撃。

### Phase 2: 章単位要約による疑似グローバル検索(章数ぶんのLLM・254頁で20〜30回)
- 取込時: section_path の最上層(章)ごとに CallLLM 1回で200〜300字要約+主要語を生成、
  新シート doc_outline(source, section, summary, keywords, chunk_id範囲)へ保存。
  取込時間は254頁で+3〜8分(R15のETA/中断/再開の枠組みに乗せる)。
- 検索時: R16-3A の段0判定に verdict=global を追加。「〜を全部教えて」「全体像は?」型は
  全章要約を1呼び出しに与えて関連章を選ばせ、選ばれた章のチャンクを精読束で回答
  (クエリあたり+1呼び出し)。
- 期待効果: 大。現行が最も苦手な俯瞰質問(点検索では原理的に拾えない)を新設カバー。

### Phase 3: エンティティ辞書+名寄せ+enrich常時ON(チャンク数ぶんのLLM・最大コスト)
- 取込時: 既存 modEnrich(summary/keywords 列は最初からスキーマに存在、既定off)を
  拡張し常時ON化。チャンクごとに要約+用語を埋め、全用語一覧をバッチで名寄せして
  新シート synonyms(term, canonical)を生成。
- 実行方式: 取込直後の一括ではなく、既存の後追い方式(embedded列と同じ「未処理マーカー
  を巡回で埋める」)でアイドル時に逐次処理。254頁≒500チャンク相当は一括だと1時間級に
  なるため、ここだけは「コスト度外視」でも同期実行の壁(②)を尊重する。
- 検索時: DistinctiveKeys のクエリ展開に synonyms を適用(「回収」⇔「リコール」の
  語彙ズレ吸収)。summary はrerank・digest段の材料として利用。
- 期待効果: 中。用語が統制された規程文書では Phase1/2 より劣後(だからこそ3番目)。

## 4. 不採用(理由つき)
- グラフDB/Neo4j/Docker/ベクトルDB: 実行環境が存在しない。
- embeddingベクトルのANN・コミュニティ検出(Leiden): 純VBA再実装は工数対効果が合わない。
- ScriptControl(MSScript.ocx)によるJSON.parse: 政策ブロックリスクとLOテスト不能。
  LLM出力は既存流儀(タグ+|区切りの行形式)で受ける。
- my_knowledge への列追加: 配布済み本棚の移行リスク。新シート方式で代替。

## 5. R16との接続と実装順
R16-3C(精読束)= Phase1 の受け皿、R16-3A 段0判定= Phase2 の verdict 拡張点として
設計済み。実装順は Phase1→2→3 で、各フェーズ間に実機検証を挟む。
