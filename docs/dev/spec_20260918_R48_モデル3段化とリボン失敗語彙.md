## 1. 裁定（R48-1）リボンの失敗語彙を1モジュールへ集約する

### 1-1. 何が起きているか

`modGateway.CallLLM`（`src/core/modGateway.bas:71-137`）が失敗へ倒す分岐は5本しかなく、
**上の失敗文字列5種はどれにも当たらず `:128` で素通しする**。素通しした文字列は
`modRagParse.ExtractAnswer:619-621` がタグ無し応答として全文を answer に採るため、
**利用者には「AIの回答」として、確信度バッジと出典つきで表示される。**

これは憲章 **§4-1「無言の失敗禁止」** と **§3-3「全ての失敗は日本語で何が起きたか+次の一手を伝える」**
の二重違反であり、本製品の価値基準（出力の品質・誠実さ）に直接反する。

`CallLLM` の呼び出し元は本番コード28箇所で、**28箇所すべてが既に `#ERR:` 分岐を持つ**。
したがって **`CallLLM` の中で `#ERR:` へ変換すれば全経路が同時に塞がる。**

### 1-2. なぜ新モジュールなのか（分割裁定）

`modGateway` は python `len()` 実測 **29,875字・残125字**。CLAUDE.md §12 の
「残300字未満は分割裁定必須」に該当する。**1〜2行を押し込むのは継ぎ足しであり、
次に触るときに詰む。**

また、既存の `LooksLikeLimitError` / `LooksLikeRealAnswer` も「**リボン／LLMが返す
失敗の語彙を判定する**」という同じ関心事である。憲章 §4-5「同型の問題は共通部品で
一度だけ解決する」に従い、**新設 `src/core/modRibbonFail.bas` へ集約する**。

前例は R47 の `modEmj`（絵文字の単一情報源）。登録先も同じ3箇所。

### 1-3. 判定規則（**InStr（部分一致）を使わない**）

このリポジトリは部分一致による誤爆を **R21 D2 と R30 W2-2 の2回**やっている
（`modGateway.bas:486-502` のコメントが実例を残す）。`接続切れ` は4字で、
通信障害の手順書を引いた回の**正当な回答に literal で現れうる**。3度目を作らない。

判定は次の順序・方式に限定する。

1. `LooksLikeRealAnswer(s)` が真（`[本棚:` 等の出典・構造タグを含む）なら **無条件で「失敗ではない」**
2. `Left$(s, 7) = "(error:"` **かつ** 直後が数字 → `http`。**status が 429 なら `limit`**
3. `Trim$(s) = "接続切れ"`（**完全一致**） → `conn`
4. `Trim$(s) = "content_filterに該当しました"`（**完全一致**） → `filter`
5. `Left$` が `レスポンスから当該テキストを抽出できません` で始まる → `parse`
6. `Trim$(s) = "レスポンスのJSON文字列が途中で終了しています。"`（**完全一致**） → `parse`
7. `LooksLikeLimitError(s)` が真 → `limit`（**既存ロジックを1文字も変えない**）
8. それ以外 → `""`（失敗ではない）

### 1-4. エラーコード

`E0201`〜`E0204` は使用中。`E0205` 以降は `src/` `docs/` `build/` `tools/` のどこにも
存在せず空き（`grep -rn "E020[5-9]"` で 0 件）。

| 分類 | コード | 理由 |
|---|---|---|
| `limit` | **E0204（既存）** | 文言「本日のAI利用上限に達した可能性があります」が事実と合う。**かつ `modEnrich.bas:220` の取込打ち切り判定が E0204 系に依存しているため、ここを動かすと打ち切りが壊れる** |
| `http` / `conn` / `parse` | **E0205（新設）** | 通信そのものの失敗。次の一手は「時間を置いて再試行、続くなら診断結果を管理者へ」 |
| `filter` | **E0206（新設）** | 内容が社内フィルタに該当。次の一手は「表現を変えて試す」。**通信失敗と混ぜない**（利用者がとるべき行動が違う） |

**E0202 へ寄せない。** E0202 の文言は「混み合っている／操作の重なり」で、主因が違う。
**E0204 へ寄せない。** 401/403/500 に「明日『同期』を押せば続きから再開」は嘘になる。

### 1-5. 観測（憲章 §4-2）

## 2. 裁定（R48-2）埋め込みベクトルの流用を止める ★本題外・最重要

### 2-1. 何が起きているか

`src/core/modGateway.bas:559-567`（`RibbonEmbedRange`）:

```vba
For i = iFrom To iTo
    Dim t As String: t = modUtil.NormalizeForHash(texts(arrLo + i))
    Dim v() As Double                                       ' ← 手続きスコープ
    If LenB(t) > 0 Then v = GetEmbeddingRibbonOnly(t, dim_)  ' ← 空なら代入されない
    If modUtil.HasVector(v) Then                            ' ← 前回の v が残る
        outCsv(i) = SerializeVector(v, prec)                ' ← 前のかけらのベクトルを書く
        okCount = okCount + 1                               ' ← しかも【成功】として数える
```

VBA の `Dim` はループ内に書いても**プロシージャ全体で1回しか実行されない**。
本文が空のかけらが1つ混じると、**そのかけらには直前のかけらのベクトルが書き込まれ、
成功として記録され、`embedded=1` が立つ。**

### 2-2. なぜ重いか

そのかけらは**まったく無関係な質問に「似ている」と判定されて出典に出る**。
利用者がクリックすると中身が空か別物。確信度バッジ（`modMode.ConfidenceOf`）も
そのヒットを根拠として数える。**検索の正しさそのものが壊れており、しかも
err_log にも usage_log にも痕跡が残らない。** 憲章 §4-1 違反。

到達経路は `modGateway.bas:353`（ribbon 経路）と
`modGatewayDirect.bas:41/103/130/156`（direct 失敗時のフォールバック）の計5本。

### 2-3. 直し方と、直すことで新たに壊れるもの

**`Erase v` を1行足すだけでは取込が止まる。** `modEmbed.bas:248-254` は
`outCsv(n)` が空なら `consecutiveFail` を増やし、**3連続で「3連続失敗」として取込を中断**する。
いまは空のかけらが「成功」に化けているためこの安全装置が鳴っていない。
`Erase` を入れると空が3つ続く資料で**取込が途中で止まる**。

さらに、空のかけらは `embedded` が立たなくなるので**同期のたびに永遠に再試行**される。

したがって**次の3点を同じ波で入れる**（片方だけ入れると実機報告に化ける）。

1. `modGateway.RibbonEmbedRange` で、成否を**明示の Boolean（`okV`）で持つ**
2. `modEmbed` の失敗枝で、**元テキストが空のかけらは「失敗」に数えない**。
   `embedded=1` を立てて先へ進め、`usage_log` へ `embed_empty` を1行残す
   （ベクトル行は書かない＝検索に出てこない。これが正しい状態）
3. 「空のかけら」の判定を両者で**同じ式に揃える**（どちらも `LenB(Trim$(...)) = 0`）

### 【訂正 2026-09-19・敵対的レビュー R48-REV-03 / R48-REV-04】

初版は 1 を **`Erase v`** で実装していた。**これは LibreOffice では効かない。**

司令塔が soffice headless で実測した結果:

```
ReDim v(0 To 1) : v(0)=9 : Erase v
  → LBound=0 / UBound=1 のまま。値が 0 になるだけ（配列は解放されない）
一度も割り当てていない配列の LBound も 0 を返す（VBA は Err 9）
```

実Excel の VBA は `Erase` で動的配列を解放するが、**LO は境界を保持する**。
その結果 LO では `HasVector` が True のままになり、**全0のベクトルが「成功」として
保存される** ―― 直したつもりの穴が engine を変えると開く。しかも
**LO で回帰テストを書くと逆の結論が出る**ので、機械では守れない。

→ `Erase` の意味論に依存しない形（明示の Boolean フラグ）へ書き換えた。
CLAUDE.md §10 の「逆向きの罠（LOだけが違う）」へ実測を追記した。

あわせて R48-REV-04: 「空のかけら」の定義が `modGateway`（`NormalizeForHash` の結果が空）と
`modEmbed`（`Trim$` の結果が空）で**食い違っていた**。空白・タブだけのかけらが
片方では空、もう片方では非空になり、3連続失敗の安全弁を誤爆させうる。
`modGateway` 側も `LenB(Trim$(t)) = 0` に揃えた。
