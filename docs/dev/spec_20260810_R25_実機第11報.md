## R25-1 セル結合警告→フリーズの根治【③④・配布ブロッカー】

### 確定事実(司令塔直接調査)

- 症状のポップアップはExcel標準の「複数の値を持つセル範囲への Range.Merge」警告。**リポジトリ内に Application.DisplayAlerts=False で描画系Mergeを保護している箇所は1つも無い**(DisplayAlerts設定はファイル削除・シート削除・Word COM等の非描画系のみ)。
- 描画系 .Merge は40箇所超(modUIMain 10/modUIShelf 12/modVault 8/modShared 5/modHub 2/modUINexusDraw 1/modVaultGallery 1/modUIMainShape 2)。
- **modHub.DrawBadges(:566-573, :597-604)が最有力の初回セットアップ時警告源**: 見出し行 B_r:F_r と本文 B_(r+1):F_(r+br) をMergeして値を書き込む。rは実測(RowAt(StatTilesBottom))由来で**再描画のたびに移動しうる**。旧描画の値(見出し+本文の2個)が残ったまま新しいrで結合すると「複数値の結合」警告が確定的に出る。**旧領域のUnMerge/ClearContentsをせずにMergeしている**。初回セットアップ直後はWindowResize再フィットでHubが2度描かれるため、設置直後でも発症する。
- チャット/回答側も同型: 回答領域・入力欄(modUINexusDraw:454)・本棚一覧(modUIShelf)のMergeはいずれも既存値領域と重なった瞬間に警告を出す構造。
- フリーズの機序: 警告モーダルが回答パイプライン途中(4/6=描画前後)で出る→OK後、値が破棄された/描画が中断された状態でパイプラインが継続不能→**進捗バナーとUIロックが残存**(=砂時計のまま)。err_logが空なのは「例外ではなく仕様ダイアログ」だから。
- ④逆質問未発動は、dispersion記録(rel=50)まで到達した後にこのフリーズが先行しているためと判定(独立バグの証拠なし)。フリーズ解消後の実機で再確認する。

### FA-R25-1a 描画Mergeの無害化【二層防御】

1. **DisplayAlerts層**: modUI(または新設modUiGuard)に `Public Sub AlertsOff()` / `AlertsOn()`(元値控え+復元、ネスト対応の深さカウンタ付き)を新設し、**各画面の描画エントリ**(modHub.EnsureHubLayout / modUI.EnsureLayout+Repaint / modUIShelf.RenderShelf / modKnowledge.DrawChrome / modDash.DrawDashboard / modVault系 / modShared.Show / modUIMain.EnsureLayout)の冒頭でOff・末尾(全Exit経路とエラーハンドラ)でOnする。これで**描画中のMerge警告は全滅**する。エラーハンドラでの復元漏れが恒久False化(削除確認まで消える)を招くため、復元はFailハンドラ含め全経路必須(レビュー重点項目)。
2. **クリア層(根本)**: modHub.DrawBadges の2つのMergeの直前に、対象を含む旧バッジ領域(B10:F56=rの可動域全体)の UnMerge+ClearContents を1回実行(移動したrの旧残骸を確実に除去)。他画面は既存のClear作法(ws.Cells.Clear等)が入っているため今回は触らない(記録のみ: 同型の「クリアせずMerge」が他にないかはレビュー面で走査)。

### FA-R25-1b パイプライン中断の後始末+可観測性【エラーハンドリング強化・ユーザー要求】

- RAG質問パイプライン(modApp送信ハンドラ)の最外殻に中断時後始末を追加: 回答描画に到達せず抜ける全経路(エラー・早期Exit)で (1)進捗バナー消去 (2)modUiLock解放 (3)usage_logへ `ask_abort`(段階名+Err.Number+Err.Description)を記録。**「無言で砂時計のまま」を構造的に不可能にする**。凍結modAskの外側(呼び出し元modApp)で実装。
- 実装前に送信ハンドラの現行のエラー処理・Exit経路を全読し、既存のLeave/バナー消去との二重実行に注意(冪等に)。

## R25-2 右余白の恒久修正【①・班2の数値解析で機序確定】

- **FA-R25-2a Dashのラチェット根治**: modDash.bas:232 の列幅リセットを吸収列K込みへ(`ws.Columns("A:K").ColumnWidth = 9` 等)。機序: 吸収列を毎回リセットしないため FitTarget→FullyVisibleWidth が「前回の帯幅」を自己参照し、SAFE_MARGIN 2ptが複利で効く(実測1010→988と完全一致)。チャットが完璧なのは吸収列込みリセット(modUI.bas:100)をしているから。
- **FA-R25-2b Hubの同型修正**: modHub.bas:83-89 の列幅リセットへ吸収列Lを追加。**modHub残187字のため、列幅セットアップブロックをmodHubStatへ移設して1行呼び出し化**(modDashStat/modUIShelfと同型の先例)。移設に伴うmodHubStat容量(28,760)の実測必須。
- **FA-R25-2c ギャラリーの46pt超過修正**: modVaultGallery.bas:276-277 の `B:N=12` を「実際に値を持つ列だけ広く他は1」へ(tableの作法に合わせる。検索欄B5:E5が使う列だけ確保)。固定列合計が可視幅を超えてFitが構造的に無効化されていた。
- shelf-tableの25pt下振れ(band=987)はユーザー評価「ほぼ完璧」のため**今回は触らない**(FullyVisibleWidthの共有ロジック変更はチャットの完璧なfitを壊すリスクがあるため、実機再計測後に別途)。「？見切れ」は静的解析で再現せず(記録のみ: ContentRight系のViewportWidth/VisibleCellW基準不一致=12ptの設計欠陥は実在。次期にmodChrome側で統一)。
- 下スクロール1〜2回分は**Excelのマウスホイール仕様限界**(ScrollAreaはホイールを止められない=コード注記済みの既知事実)。修正対象外としユーザーへ説明する。
