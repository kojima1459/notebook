## R19-2 ②コンパイルエラー(調査②班・配布ブロッカー)

原因確定: modSynonymStore.bas の3箇所(:291/:305/:316)が `AddTerms Split(...), box, cnt` と
Variant配列を返す Split() を `ByRef arr() As String` 引数へ直渡し。実VBAはコンパイル拒否
(プロジェクト全体が停止)。LOは配列型引数の型検証を課さず、compileモードは実行もしない
二重の穴で見逃した。他の Split 140件/Array 65件は全数精査済みで合法(唯一の3箇所)。

R19-2a 3箇所を A案(呼び出し側で受ける)で修正:
  Dim parts() As String: parts = Split(kwCsv(i), ",") / AddTerms parts, box, cnt
  (:305 は ">"、:316 は "|" 区切り)。AddTerms のシグネチャは不変。
R19-2b lint検査15新設(tools/vba_lint.py): 「Split(/Filter(/Array( を実引数位置に直接置き、
  呼び先の該当仮引数が具体配列型(As T())である」場合を ERROR。設計は調査②班(4)章のとおり
  シグネチャテーブル(全Sub/Function宣言のパース・Private含む)+引数境界解決+
  Variant受け(InvokeFeature/TryRibbonRun等)は素通し+組込関数(UBound/Join等)は許可リスト。
  本リポの現状データで誤検知0・真陽性3(修正前)を確認してから修正をコミットする
  (=検査が3件を検知することを一度実証してから直す)。tools/README.md へ検査15追記。
R19-2c docs/45 の冒頭前提に「新版導入後、最初に小さな資料を1件取り込み、コンパイル
  エラーが出ないことを確認」を追加(実機コンパイルは実機でしか検証できない事実の明文化)。

## R19-1 ①余白・下スクロールの根治(調査①班・最重要)

確定した機序: (i)ScrollAreaはマウスホイールを止めない(公式仕様=セル選択の制限のみ)。
(ii)右余白はスクロールではなく寸法の問題——列幅合計(Hub625/チャット671/Dash1,020pt)と
可視幅(600〜900pt)の不一致。ScrollAreaでは原理的に消えない。R18-3aの範囲限定塗りは
余白を「素の白」にして見た目を悪化させた。(iii)宣言した境界自体が無限
(チャットA1:P2000=約31,000pt、本棚N412=6,200pt)。(iv)Dashは塗りA1:T120(1,800pt)/
列A:T(1,020pt)に対し内容590pt=空塗り最大。(v)既存ブックのUsedRangeは保存まで縮まない。

裁定: (a)列幅viewport連動(余り吸収列方式)を主、(b)塗り/行下端の実測化を副、
(c)ScrollAreaは補助として維持(コメントの効能記述を実態へ訂正)。行のHiddenは
容量事故実例(8KB→3MB)により不採用。列Hiddenも(a)で不要。

R19-1a modViewport に共通部品2つを新設:

  - ContentRight(ws, bandAddr, rightPad): 右端の単一情報源
    (modKnowledge.ToolbarContentRight と同思想の汎用化)。

## R19-5 ⑤作業用Excelとの同居フリーズ(調査⑤×2班)

確定した機序: 再起動時に本体xlsmをダブルクリック→Excel既定のインスタンスマージで
生存中の作業用①プロセスへ本体が吸収→①のプロセス内で本体のOCRブロッキングが走り
プロセス全体のメッセージポンプ停止→①も中断ボタンも全滅。①に見えた「OCR中…」は
Application.StatusBar(プロセス単位)=同居の物的証拠。DisableMergeInstance はダブル
クリックに無効(公式)。完全な実装解は存在せず「検出+入口一本化」の二段構え。

裁定: 自動の自己再起動は不採用(ファイルロック競合・cmd遅延ハックの脆さ。記録のみ)。
「検出して正直に伝え、危険な操作をブロックし、正しい入口を配る」構成とする。

R19-5a 起動時の同居検出: modIntegrity.WarnAtStartup に相乗り——Boot時に
  Workbooks.Count > 1(自分以外のブックが同一プロセスに存在)ならモーダル1回:
  「他のExcelブックと同じプロセスで開かれています。このまま取込を行うと、そのブックも
  一緒に固まります。いったんこのファイルを閉じ、同梱の『MyBookshelfを起動』から
  開き直すことをおすすめします。」(BMPのみ)。usage_log("cohabit_detected")。
R19-5b 取込開始時の再確認: 取込入口(AddFilesResult 冒頭)で同居検出時
  「他のブックが同じプロセスにあります。取込中はそれらも操作できなくなります。
  続行しますか?」(vbYesNo)。いいえ→中止。silent同期では出さない(usage_logのみ)。
R19-5c ランチャー同梱: build --zip に「MyBookshelfを起動.bat」を追加
  (start "" excel.exe /x "%~dp0MyBookshelf.xlsm"。App Paths 解決で excel.exe は
  フルパス不要)。README/ガードシート/docs(10/20)に「起動は必ずこのランチャーか、
  他のExcelを全て閉じてからダブルクリック」を明記。MOTW/SmartScreen の初回警告への
  対処(プロパティ→許可)も1行。
R19-5d docs是正: docs/10:330 の「作業用Excelでファイル→開く」案内を削除し
  「作業用Excelで開くのは仕事のファイルだけ。MyBookshelf本体を作業用Excelの中で
  開かない」へ書き換え。docs/10:336 のダブルクリック注意に「生き残った作業用Excelに
  吸い込まれて後で一緒に固まる」リスクを追記。docs/45 に同居検出の確認項目を追加。
R19-5e 作業用Excel起動時のセッション記憶(mLaunched)に加え、起動案内文へ
  「仕事が終わったら作業用Excelは閉じてください(開いたままにすると、次回本体を
  開くときに吸い込まれることがあります)」を一言(トースト/確認文のどちらか短い方)。

## R19-4 ④「免責は？」で逆質問不発(調査④班)

確定: 「短いが複数の異なる資料に強く分散ヒット」は既存の(A)低スコア判定にも
(B)25字複合ゲートにも掛からない第3の曖昧さ。深掘り「計算方法」も同じ盲点に再落下。

R19-4a 純関数 HasScoreDispersion(srcScoreLines, gapX100) を modClarify に新設
  (Hit()を受けず "source&TAB&score" のvbLf連結文字列を受ける=LOテスト可能。
  資料2種未満はFalse。source別最高スコアの1位と2位の差が gap 未満なら True)。
R19-4b IsTooVague(modAskRetrieve)の発動条件を拡張: 短い(≦ambiguous_max_chars) かつ
  俯瞰でない かつ (best<thr OR HasScoreDispersion(...))。呼び出し側で hits から
  srcScoreLines を畳む(modAsk は無変更)。聞き返し文面は既存 BuildClarifyPrompt
  (資料選択+意図5区分)をそのまま使用(分散時も自然に読める文面かを確認し、
  必要なら分散時の1行目だけ「複数の資料に該当します。どの資料の内容ですか?」へ)。
R19-4c config: ambiguous_dispersion_gap_x100(既定10。0で無効)。
R19-4d 誤発動対策: 質問文にヒット資料名の主要語が含まれる場合はスキップ
