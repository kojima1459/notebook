# R12-4 要件定義: 検索スケール恒久対策(起草: Fable司令塔 2026-08-01)

背景: 3観点監査(スケール)で、公称上限20,500チャンク時の1質問が
推定60〜300秒・DoEventsゼロ(応答なし白画面)と定量確定。支配項は
(a) CsvToVector のベクトルCSV毎クエリ再パース(1.74億反復/クエリ)、
(b) CompactForMatch/NormalizeForSearch のテキスト正規化やり直し
(1,540万反復/クエリ)。内積自体は支配項ではない。既定 retrieve_mode=multi
でこれが4〜5倍。設計書の旧見積り(1〜3秒)は内積のみの過小評価。
場当たり最適化は禁止(裁定済み)。本書が実装の正。

## ゴール(検収条件)

1. 20,500チャンク時の1質問の純VBA計算を「初回(キャッシュ構築込み)
   十数秒・2回目以降は数秒以内」の見積りに落とす(概算根拠を実装報告に
   明記。実機実測は docs/45 追補の測定項目で確認)。
2. 検索中の無応答ゼロ: 全ての重ループに定期的な進捗更新(ShowProgress/
   SetStage)+DoEvents(N行ごと)。憲章§3-2適合。
3. 挙動等価: 検索結果(スコア・順位)はキャッシュ有無で完全一致
   (等価テストで固定)。
4. docs/70 の公称値を実装後の見積りで改訂(誇張禁止。実機測定項目を
   docs/45 系に追加)。

## 実装項目

### 1. セッション内ベクトルキャッシュ(新モジュール modVecCache)
- my_vectors 全行を初回検索時に1回だけパースし、モジュール変数の
  Double配列(次元×行)+chunk_id配列で保持。
- 構築中は ShowProgress「検索の準備をしています… i/N」+N行ごと DoEvents。
- **世代カウンタ**: modAppState(または modVecCache 内)に埋め込み世代
  (generation)を持ち、(a)取込/削除/再埋め込み(EmbedPending の書込・
  MarkAllForReembed・DeleteSource)で必ずインクリメント、(b)キャッシュは
  自分が構築した世代と現世代の不一致で無効化・再構築。
- modBitwiseOpt.CacheStamp にも同じ世代を混ぜる(RAG監査3の
  「再埋め込みを検知しない」を同時解消)。
- 32bitメモリ: 上限時 Double で約126MB。構築失敗(err7)は捕捉し、
  「キャッシュ無しの従来経路」へ自動フォールバック+usage_log 1行
  (機能は落とさない)。キャッシュ解放手段(ResetVecCache)を用意し、
  取込前(バッチ開始時)に解放してピーク重複を避ける。
- modRetrieve(単段/多段)は CsvToVector の行内呼び出しをキャッシュ参照へ。
  HasVector 判定もキャッシュ構築時に前計算。

### 2. 正規化済みテキストの前計算
- 取込時(modShelfStore の書込点)に NormalizeForSearch 済み文字列を
  my_knowledge の新列(第10列 norm_text)へ保存(SafeLeft 上限は現行の
  照合仕様に合わせる)。
- 検索側(modSparse/modRetrieve の照合)は norm_text 列を一括Range読み
  して使用。**空セル(旧データ)は検索時にその行だけ従来どおり正規化し、
  結果をセルへ書き戻す(遅延バックフィル。書き戻しはOERN+ScreenUpdating
  配慮・200行ごとバッチでも可)**。全行が埋まれば以後は前計算のみ。
- 列追加は R12-3 の fail_count(manifest 10列目)と同じ冪等作法
  (見出し自動付与・空=未計算扱い・列ズレ防止の詰め直し整合)。
- modChunker/取込側の追加コストは1チャンク1回の正規化(現行の検索毎
  から移動するだけ=総量不変で償却)。

### 3. binary_rag の自動有効化
- config `binary_rag_auto`(既定TRUE)を新設: binary_rag=FALSE でも
  チャンク数 >= binary_rag_min(既定5000)なら粗選別を自動有効化。
  明示 binary_rag=TRUE/FALSE の**明示FALSE は自動を上書きしない**
  (キーの意味を「明示指定」と「自動」に分離: binary_rag は
  TRUE/FALSE/AUTO の3値にする案でも可。実装が単純な方を選び報告)。
  ※R12-3 の救済union(条番号完全一致)が入っているため設計保証は維持済み。
- 粗選別の HammingLongs 入力もベクトルキャッシュから量子化キャッシュを
  構築(既存 BuildCache を世代対応に)。

### 4. 進捗とDoEvents(全重ループ)
- modRetrieve の行ループ(単段/多段/粗選別)へ 2,000行ごとに
  SetStage/ShowProgress 更新+DoEvents。再入は既存関所
  (modUiLock.Enter が OnSend 系で取得済み)で守られていることを確認し、
  DoEvents 追加による新規再入面が無いことを検証観点に含める。

### 5. docs 改訂
- docs/70: 公称値を「実装後の見積り+実機測定で確認」の誠実な表現へ。
- docs/45(または追補): 大規模時の実測項目(1,000/5,000件時の体感)を追加。
- MASTER_SPEC/HANDOFF: 新config・新列・世代カウンタの記録。

## 制約・注意

- 新モジュール modVecCache は modules.json/lint CONTRACT へ登録。
  純ロジック部(世代判定・添字計算)は分離してテスト。
- 等価テスト: 同一入力での「キャッシュ経路 vs 直接パース経路」の
  スコア一致を純ロジック層で固定(LOで実行可能な範囲に設計)。
- 容量: modRetrieve(22,053)ほか対象の30,000未満厳守。
- 検証: lint ERROR 0 / LOテスト全PASS(641+新規) / 両ビルド自己検証 /
  --prod --zip。実装は R12-9+5 完了後に排他で(Opus)。

## 追記(2026-08-01 R12-H・敵対的レビュー Low-8 の記録)

kData を7列読みから10列読み(norm_text 追加)へ広げたため、1質問あたりの
同時ピークは「my_knowledge 10列 + ベクトルキャッシュ」になる。norm_text は
本文とほぼ同じ長さの文字列を全行ぶん持つので、20,500件で最大 +数十MB。
32bit Excel(実質1.2GB程度)では余裕があるが、上限いっぱいの本棚では
無視できない増分である。full_text / norm_text を必要な行だけ後から読む
(遅延取得)形への変更は、影響範囲が検索の全経路に及ぶため次期課題とする。
