## 2. 実装順（司令塔の裁定）

**順序そのものが裁定である。** 並べ替えると、消える予定の構造に対して直しを積むことになる。

### P0. 前提を確かめる（実装より先・Windows機）

**D3: 30,000字の壁が実在するかを実機で測る。**

これが幻なら、**逼迫18本・実質凍結7本・回避コメント48箇所・受け皿モジュール制度・
「実体は受け皿へ、呼び出しは1行」という作法**が全部いらなくなる。
P1 以降の直しのうち何本かは「容量が無いから受け皿へ出す」という迂回を含むので、
**先に測らないと、消える壁を避けるための迂回をまた作る。**

### P1. 検問の自己無効化を塞ぐ（これが先。理由が重い）

R47 で「人の注意力では止まらないから機械にした」と宣言した検問が、**自分で自分を無効化している。**
緑を信じられない状態では、**以後どのラウンドの結論も信用できない。**

| ID | 何が起きているか |
|---|---|
| `A-A-5` / `H-6` | `doc_gate` の config 検査が **int 値だけ**を見る（`doc_gate.py:116`）。**bool と文字列は1文字も検査されていない** ―― R48 で入れ替えたばかりのモデル名3つも無検査 |
| `H-H-10` | 孤児Public検査が、**過去の監査報告書に名前が載っているだけで救済**される辞書を持っており、自分を無効化している |
| `B-1`（第1陣） | 容量台帳の検査が、**守るべき CLAUDE.md §12 の台帳を書式違いで1行も見ていない**（28箇所ズレたまま緑） |

**この3本が塞がるまで、「検問が緑だから大丈夫」と言わない。**

## 4. この表の使い方

- **1件ずつ裁定して実装する必要はない。** P1〜P3 は**同じ根**を持つものが多く、
  まとめて直すほうが安い（例: P1 の3本はどれも「検問が自分を守れていない」）。
- **LOW を軽視しない。** LOW 32件のうち **silent 型が多数**を占める。
  LOW は「実害が小さい」ではなく「1件あたりの実害が小さい」であって、
  12,000人 × 32件 の母数では別の話になる。
- **潰れた21件は再議論しない。** 反証の根拠が残っているので、
  次の監査で同じ指摘が出たらその記録を先に読む。
