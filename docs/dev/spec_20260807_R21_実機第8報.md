# R21-1【⑦・5回目にしない】レイアウトの構造的完治（波A・Opus）

原因は3つの独立欠陥の合成（調査A班・数値トレース済み）: (1)中身の右端が帯に張られていない（Hubのみ張っている）、(2)dash/chatの窓高測定が水平スクロールバーON前で24pt過大、(3)境界計算が「+24pt→行切り上げ→最低1画面」の三重切り上げで必ず窓を超える。以下S1〜S7を全て実装。

## S1 測定の単一化と順序固定
- `modViewport.EnsureViewState(ws)` 新設: Activate → Gridlines/Headings/Tabs/**水平スクロールバー**を最終形へ → その後にのみ測定を許す。全画面の描画エントリ（modHub/modDash/modKnowledge(3モード)/modUI）はこれを最初に通す。
- dash/galleryの「描く→活性化→Display*」を「活性化→Display*→描く」へ反転（modDash.bas:87-105 / modVaultGallery.bas:79-96）。
- 保険: 描画末尾に再測定し、差>4ptなら**1回だけ**再描画（ワンショット、無限ループ禁止）。

## S2 帯は必ず可視幅以下
- Fitのtarget = 可視セル幅 − 安全余裕2pt。`SCROLLBAR_W=12`定数決め打ちをやめ、`VisibleRange.Width`との突合で校正・キャッシュ。
- Fit事後検証: `Range(band).Width > target` なら吸収列を差分減で再設定（最大2回、PadUnitsRefine流用）。
- 水平スクロールバーは「帯≤可視幅」が成立する画面でOFF（狭窓<625ptの安全弁としてONは残す。modUI.bas:484の一律ONを条件化）。
- 受け入れ基準: 全画面・全モードで `帯実幅 ≤ 可視セル幅`（横スクロール構造的に不能）。

## S3 中身の右端の単一情報源化（不変条件: 本文要素の右端 == ContentRight(band,8)）
- dash: センタリング（CenterX0）を廃止し、カード上限220ptで生じる余りを**カード幅とKPI_GAPに配分**して右端まで張る（`gap=(bandW-2*X0-4*cardW)/3`、cardW上限は撤廃または260ptへ）。サブタイトルのKPI_X0固定もRowX0()へ統一。管理者行は既にRowX0（R20H FA-7）。
- gallery: カード幅を弾性化 `cols=Clamp(Int((avail-leftX+GAP)/(CARD_W_MIN+GAP)),3,6)`（CARD_W_MIN=170）、`cardW=(avail-leftX-GAP*(cols-1))/cols`（上限240）。1024pt窓で5列×186.75pt=右端1004ぴったり＆9枚が2段=406ptで縦も解決。
- table: J列吸収は維持、J→N二段階Fitをやめ「列幅設定→Display*確定→Fit(N)一発」へ。
- 検証: 「本文Shape最大右端とContentRightの差>12pt」を検出する純関数テストを追加。

## S4 境界の丸めを切り下げへ
- `modViewport.RowAtFloor(ws,y,maxRow)` 新設（下端≤yになる最後の行=部分行を含まない）。
- BoundAddr分岐: 内容が窓に収まる(contentBottom≤viewH-8)→下端行=RowAtFloor(viewH)（境界≤窓＝スクロール余地ゼロ）／収まらない→RowAt(contentBottom+8)。BOTTOM_PAD 24→8。
- modHubStat.DrawFooterのlimitY底上げ(:680)も同じRowAtFloor(viewH)由来へ統一（「窓高で底上げ」3箇所の重ねがけを1本化）。
- 受け入れ基準: 内容が収まる画面で `境界高さ ≤ 窓高`（縦スクロール不能）。Hub実測: RowAtFloor(499)=行31(498pt)。

## S5 窓高適応圧縮（内容が収まらないときだけ）
- 圧縮係数 `s=Clamp((viewH-8)/need, 0.78, 1.0)` を可変要素にのみ適用。実装は**modViewport側の純関数**（modHub残1,380/modHubStat残1,569のため、両者は定数参照の置換など最小差分に留める）。
- Hub: CARD_H 68→60·プロフィール下18→12·TILE_H 52→46·GAP 8→6·バッジ4行→3行·フッター上10→6（s=0.90で計65pt節約、2段ヘッダー時542→477pt）。
- dash: KPI_CARD_H 92→80、BADGE_H 54→46まで（約40pt）。
- gallery: colsとcardW/CARD_Hの弾性（S3と同じ機構）。

## S6 再フィット経路の穴
- 本棚tableモード: RefitActiveScreen経路が RenderShelf（帯を触らない）に落ちる穴 → EnsureLayout相当（列幅+DrawChrome+Fit）を通す軽量経路を追加。
- チャット: modUI.Repaintに帯Fitが無い穴 → 実体をmodViewport側に置き、Repaintから1行呼び（modUIは残1,677字、最小差分）。

## S7 可観測性
- LogViewportを「フィット直後に毎回1行: 窓幅/可視幅/帯実幅/中身右端/境界下端」の5値記録へ拡張（次報で犯人が一意に決まる形）。

## 検証成果物（波A完了報告）
- 机上トレース表: 1024×499pt窓でHub/Dash/gallery/table/chatの帯実幅・中身右端・境界下端（すべて 帯≤可視幅・境界≤窓高 を満たすこと）。

# R21-2【⑧⑤】逆質問の計器修理とcritique復旧（波B・Sonnet）

## D1 分散判定の判定位置とスケール統一（modAskRetrieve内で完結・modAsk不触）

# R21-3【②】章検出の根治と俯瞰の復旧（波C・Sonnet）

根因: Visionプロンプトが全見出しに「# 」を付けさせ、ClassifyLineが「# 」を無条件に章境界扱い → 目次の各行・小見出しが全部「章」化 → 60上限張り付き＋目次ページ偏り。

## E1 取込側の根治（新規取込に適用）
- optVision.VISION_PROMPT: 階層指示へ変更「文書の最上位の章・部・編のタイトルだけ行頭に『# 』、節・条・小見出しは『## 』、目次ページの項目行には付けない」。
- modChunker.ClassifyLine: 「## 」をlbl=2（節）として受ける分岐を追加（「# 」のみ章）。
- modChunker: ページ単位の事前判定 `LooksLikeTocPage(pageText)` 新設（リーダー記号「……/．．/・・」+末尾数字の行が高密度なページ）。目次ページでは見出し判定を抑制（全行本文扱い）。RegExp不使用・純文字列走査（modChunkMetaと同じ制約）。
- 章の最小サイズガード: GroupChapters後、1〜2チャンクの章を隣接章へ統合（Visionが指示に従わない場合のフォールバック）。

## E2 outline構築側の改善（⚡仕上げの射程内=既存資料も再取込なしで改善）
- ChapterKeyOfの緩やか正規化: 末尾の「リーダー記号列+頁番号」を素手走査で除去してからキー比較（目次行キーと本文見出しの統合を促進）。
- GroupChaptersの2パス縮退: ユニーク章キー数がMAX_CHAPTERS超なら、粒度を上げて（小章の隣接統合）再集約。「先着60で無言切り捨て」を廃止。
- 切り捨て/統合が起きた場合は usage_log に `outline_capped detail=uniq=N merged=M dropped=K` を記録（現状は無言）。
- 上記E2は modOutlineBuild/modChunkMeta 側の変更のため、**⚡仕上げ（modBackfill）を再実行すれば既存資料にも適用される**。DetectLegacyDocsの「仕上げ済み」判定に outline世代キー（例: config/定数 `OUTLINE_LOGIC_VER` を doc_outline に記録し、旧世代なら未仕上げ扱い）を導入し、ロジック改善後に⚡仕上げが再提案される仕組みにする。
- 制約の明記: 章境界そのもの（breadcrumb）は取込時に焼き込まれるため、E1の効果は**再取込した資料のみ**。docs/45とアプリ内⚡仕上げ完了トーストに「OCR資料は再取込するとさらに章立てが正確になります」の1行を追加（正直な案内）。

## E3 テスト（C5準拠）
- 題材1（目次+A/B/C章立て最小資料）: 目次行が独立章にならない/ChapterBodyに本文が入る。
- 題材2（小見出し過多）: 上限到達時に縮退統合が働き、outline_cappedが記録される。
- 題材3（目次行vs本文見出しの表記ゆれ）: 正規化後に同一キーへ統合。
- 題材4（Backfill射程）: BackfillOneでchunk_meta/doc_outlineは再構築されるがbreadcrumbは不変。
