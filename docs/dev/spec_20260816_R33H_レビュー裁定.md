# spec_20260816_R33H_レビュー裁定

R33 敵対的レビュー1周目(4班・45件)の裁定。班A=新規実装4本 / 班B=容量手術と凍結 / 班C=波跨ぎとErr状態機械 / 班D=テストの形骸とUIUX。

**複数班が独立に同じ欠陥へ到達したものは確度が高い**。以下 (A)(B)(C)(D) で出所を示し、2班以上なら ★ を付す。

## Fix波1: 破壊操作と表示の嘘(最優先)

- **F1 [BLOCKER] 部門削除の巻き添えと、巻き添え側の永久復旧不能** (A)
  `modShelfStore.bas:364` / `modShareRule.bas:496` / `modShared.bas:658`。一致判定が `vbTextCompare` で、日本語VBAでは**全角/半角・ひらがな/カタカナを同一視**する。`営業1課` と `営業１課` が同居すると両方削除されるのに、版の記録クリアは `LCase$`(全半角を畳まない)なので**巻き添え側の `ch:` が my_stats に残り、`PendingUpdates` が「最新です」と判定して永久に戻らない**。
  **裁定**: この経路の一致判定を `vbBinaryCompare` へ寄せる(origin は機械が生成した内部タグであり、人が打つ検索語ではない)。削除の一致判定と my_stats のキーが**同じ正規化関数**を通ることを保証する。**LOもlintもこの差を検出しないので、純関数へ切り出してゴールデン固定すること**。
- **F2 [MAJOR] 削除のロールバック無し・再描画順序・失敗の握り潰し** (A)
  `modShelfStore.bas:379-385` / `modShared.bas:657-659`。「生存行を上へ詰めて一括代入 → 末尾 ClearContents → ベクトル削除」の3段が非トランザクション。途中で落ちると**生存行が二重に存在**し、孤児ベクトルが残り、`redraw = True` が `PurgeChannelChunks` の後ろにあるため**再描画すら走らない**。さらに `PurgeChannelChunks` の `On Error Resume Next` が失敗を呼び出し元へ伝えないため「0件 削除しました」と出る余地がある。
  **裁定**: (a)書き戻しを既存の200行バッチ作法へ揃える (b)順序を「先に `ClearContents` してから書く」(重複が残らない側に倒す) (c)`redraw = True` を `PurgeChannelChunks` の**前**へ移す (d)失敗を呼び出し元へ返し「削除に失敗した可能性があります。本棚を確認してください」と言えるようにする。
- **F3 [MAJOR]★ 購読解除の成否を見ずに「今後届きません」と断言する** (B)(D)
  `modShared.bas:663-672` / `modChannel.bas:167-174`。`Unsubscribe` は `On Error Resume Next` 下の Sub で `modConfig.SetValue` の成否を返さない。読み取り専用・シート保護で黙って失敗しても**無条件に成功トースト**を出し `usage_log` に `unsubscribed=yes` を残す。**R33 が繰り返し潰してきた「届いていないのに届いたと言う」型を、R33 自身が再生産している。**
  **裁定**: `Unsubscribe` を `Function As Boolean` 化し、書込み後に `IsSubscribed` を読み直して検算した結果を返す。成功時のみ現行トースト、失敗時は「設定を書き込めませんでした。管理担当にご連絡ください」。**W3-8(KillGsTree)と同型の手術なので作法を揃える。**
- **F4 [MAJOR] 部門名のカンマで購読解除が他部門を巻き込む** (A)
  `modChannel.bas:167-174` / `:136-141`。除外リストがカンマ区切り1本で、Windows のフォルダ名にカンマは使える。`品質保証,監査` を解除すると `品質保証` と `監査` の**両方**が届かなくなる。W5-28 でこの関数が**src で初めて生きた経路**になったため、潜在欠陥が顕在化した。
  **裁定**: 区切りをフォルダ名に使えない `|` へ変える(`ListChannels` に前例あり)。**旧カンマ形式を読み替える移行を必ず入れる**(既に手編集で設定した端末がある)。
- **F5 [MAJOR]★ 取込完了の再描画が別ブック前面で黙って落ちる** (B)(C)
  `modShared.bas:191-198`。`Application.ActiveSheet` は**アクティブ「ブック」**のシートを返す。取込は内部で別ブックを開く(`modExtractorExcel` の `Workbooks.Open`、作業用Excel)ため、その状態で完了すると再描画が飛び、**取り込んだ資料が本棚に出ないまま残る**。src の他の全箇所は `ThisWorkbook.ActiveSheet` を使っており、ここだけ主語が違う。
  **裁定**: `ThisWorkbook.ActiveSheet` へ変える(1語)。
- **F6 [MAJOR] 本棚の警告が「78%です」と出る** (D)
  `modHubStat.bas:587-589`。W5-17 は表示の分母を `shelf_max_chunks`(既定20,500)へ統一し、警告判定だけ `chunk_limit`(既定20,000)の8割に残した。既定のまま16,000で「⚠ 本棚の使用量が**78%**です」。`shelf_max_chunks` を40,000にした組織では「⚠ **63%** です」。非エンジニアには故障にしか見えない。
  **裁定**: 警告文から `ChunkUsagePercent()` を外し、警告固有の言い方にする(例「棚卸しの目安(20,000件)の8割を超えました」)。**判定ロジックは変えない**(テストが意図として固定済み)。
- **F7 [MAJOR]★ W5-21 の `mLastMode=""` が旧UIの「空質問専用」分岐へ流れ込む** (B)(C)
  `modAsk.bas:292` → `modUIMain.bas:411-430`。この分岐は「空質問ターン専用」として作られている。W5-21 以後、API失敗と逆質問もここへ入るため (a)状態セルが「準備できています」になる(通信失敗の直後に) (b)`mLastAnswerText` に到達せず、「Wordで開く」が**前のターンの回答**を出す。`nexus_ui=FALSE` の端末は正規の設定(`modDiag` の必須キー)なので旧3画面は死んでいない。
  **裁定**: 「検索も生成もしなかった」と「生成が成立しなかった」を別の印にする。`mLastMode` は従来どおり `mdMode` を入れ、**バッジ/出典の抑止だけを別フラグで行う**。`modAsk` は凍結なので実体は `modMode` 側に置き、modAsk の変更は最小に留める。
- **F8 [MINOR] 専門家召喚だけ失敗ターンの門をくぐっていない** (C)
  `modApp.bas:245-252`。`DrawConfidence` と `RenderCitations` は抑止されたが `OfferMentor` は `LastHitCount` だけを見るので、「AIとの通信に失敗しました」の直下に「💡 この分野は○○さんが詳しいです[質問を送る]」だけが残る。
  **裁定**: 同じ門をくぐらせる(1行)。

## Fix波2: 余白とスケール

- **F9 [MAJOR]★ `mCfOff` がシート横断で、張り済みのルールが旧テーマ色のまま永久固定** (A)(B)
  `modBackdrop.bas:622`。`mCfOff` が立つと `ApplyCF` は先頭で即 Exit するため、**既に張ってあるシートのルールが二度と `ClearOwnCF` されない**。テーマを切り替えると「明るいテーマなのに画面の下半分だけ濃紺」——W5-2 が背景画像経路で潰したのと同じ壊れ方を、条件付き書式経路で新規に作っている。しかも剥がす経路が1つも無い。
  **裁定**: `mCfOff` 判定を `Exit Sub` ではなく「Add はしないが `ClearOwnCF` は必ず通す」形にする。
- **F10 [MAJOR] 自己検算の基準値を「前回のルールを剥がす前」に測っており、2回目以降で構造的に無効化する** (A)
  `modBackdrop.bas:642` と `:649` の順序。「測る→剥がす→張る→測る」なので、UsedRange が伸びる端末では2回目以降 `usedLast` に**前回の膨らんだ値**が入り、(a)検算が永久に無罪放免になり (b)開始行が毎描画400行ずつ下へ行進する。**8ラウンド溶かしたのと同じ無言失敗**。
  **裁定**: `ClearOwnCF` を `usedLast` の実測より**前**へ移す。
- **F11 [MAJOR] 巻き戻しの `Rows.Delete` が ScrollArea を掛け直していない** (A)
  `modBackdrop.bas:685`。R30 F8 で確立した「削除の直後に `ApplyScrollBound` を掛け直す」作法を新経路が破っている。`ApplyCF` は `scrollAddr` を受け取っていないので復旧材料すら持たない。他の全 `Rows.Delete` にある `minRow` 保護も無い。
  **裁定**: `ApplyCF` に `scrollAddr` を渡して掛け直す。下限行の保護も入れる。
- **F12 [MAJOR] 検算そのものの失敗を「成立」として記録する** (C)
  `modBackdrop.bas:672-697`。(1)`after` の読み取りが `If Err.Number = 0 Then` に包まれ、失敗すると検算ごと飛ばして**成功ログへ到達する** (2)巻き戻しの `Rows.Delete` の成否をどこにも残さない(3行上では Err を退避しているのに)。**1回しか出ないログが嘘だと調査が完全に迷走する。**
  **裁定**: 読み取り失敗は「検算できなかった」として専用ログへ倒す(**合格側へ倒さない**)。`Rows.Delete` の成否を `delOk` と同型で退避してログに載せる。
- **F13 [MINOR] `usedrange_grew` が別の失敗に食われて消える** (A)
  `modBackdrop.bas:743`。`mCfFailLogged` を3種で共用しているため、先に `cf_add` が1回出ると**この波の答えである `usedrange_grew` が一切残らない**。
  **裁定**: `usedrange_grew` だけは共用フラグを無視して必ず1行出す。
- **F14 [MAJOR]★ 背景画像の失敗カウンタが単一スロットで、画面を行き来すると永久に打ち切らない** (B)(C)
  `modBackdrop.bas:378-390`。W5-3 は (シート,色) ごとに数える意図だったが**直前1組の鍵しか持たない**。3画面を行き来すると鍵が毎回変わりカウンタが0に戻る。失敗原因(TEMP書込不可・AV隔離)は端末全体に効くので3枚とも失敗する＝鍵が毎回変わる＝**R32 F7 m-3 の上限が実質無効化**。しかも W5-2 で1回あたりのコストが増えている。
  **裁定**: 鍵→回数の対を複数持つ(`mApplied` と同じ `"|key=n|"` 形式の文字列メモで足りる)。
- **F15 [MAJOR] `FileCopy` は原子的でなく、ヘッダだけ揃った壊れた集計を「ok」と判定する** (A)
  `modShare.bas:406` / `:275`。`FileCopy` は宛先を切り詰めてから先頭から書く。ヘッダは約80〜100バイトなので**部分読みの大多数はヘッダが完全**になり、`BoardHeadStatus` は列数と種別印しか見ないので "ok" と判定する。結果**部の合算が0・他人の称号が全滅**したまま「集計時点/N名ぶん」と自信を持って表示し、TTL 600秒それが続く。
  **裁定**: 末尾に終端行を必ず付け、`BoardHeadStatus`/`BoardReadRows` の入口で「終端行が無い＝broken」に倒す。あわせて `FileCopy` を `Kill dest` → `Name tmp As dest`(実質原子的)へ変える。
- **F16 [MAJOR] `FileCopy` は1回しか試さず、読み手と衝突すると10分間書けない** (C)
  `modShare.bas:389-414`。tmp 書込みは3回試すのに本番の置き換えは1発勝負。宛先は業務時間中ほぼ常に誰かが `ADODB.Stream` で開いており、`LoadFromFile` は書込み共有を許さない。落とすと次の機会は10分後で、24時間過ぎれば全端末が「更新されていません」に倒れる。
  **裁定**: F15 の rename 化とあわせ、置き換えも3回リトライする。
- **F17 [MINOR]★ `LoadSnapshot` が存在確認せず、summary 不在で毎回900msのビジーウェイトを払う** (B)(C)
  `modBoard.bas:535-541` → `:751-772`。`ReadBeacon` は「他人の書きかけ」を想定した3回×150/300/450ms のバックオフを持つが、**存在しないことが定常状態になりうる** summary.txt に流用している。導入直後・発行者不在の全端末が起動時とTTL満了ごとに払う。
  **裁定**: `Dir()` で存在確認してから読む。無ければ即 `ClearAggregate "none"`。
- **F18 [MAJOR]★ `SCAN_CAP=500` の打ち切りが「毎回同じ顔ぶれ」で恒久除外になる** (A)(D)
  `modBoard.bas:449-455`。ファイル名は `stats_<不変ハッシュ>.txt` で NTFS は名前順に返すため、**打ち切られる501人目以降は毎回まったく同じ**。その人たちは組織合計に一生入らず、感謝を20件集めても**称号が誰の画面にも付かない**。「感謝ベースの称号は偽装不能」という設計の売りがハッシュのくじ引きになる。退職者のビーコンが先頭スロットを恒久占有する(削除処理が無い)。
  **裁定**: (a)称号だけは全件走査する軽い経路にするか、(b)起点を日付でずらしてローテーションする。**恒久除外を作らないことが最低条件**。あわせて Hub タイルの「(概算)」に母数を入れる。
- **F19 [MINOR]★ 「更新」ボタンが60秒以内は完全に無反応** (A)(C)(D)
  `modBoard.bas:382-387`。すぐ上のコメントが R8 F9 の裁定「押しても値が変わらないのはボタンが壊れているのと区別が付かない」を残したまま、その直下でまさにそれをしている。**法則が2回反転している型**。加えて `mForceAt` を実行の成否と無関係に進めるので、共有が瞬断した1回で下限を使い切る。
  **裁定**: `Exit Sub` の代わりにトーストを1行出す。`mForceAt` の更新を「実際に走ったとき」へ移す。
- **F20 [MAJOR] `outKilled` 正常化で、GSが既に終了している一般的なケースでも作業フォルダが毎回残る** (B)
  `optOcrPage.bas:598` / `optGsProc.bas:157-188`。`ProcNameOf` は終了済みプロセスに `""` を返し名前照合に外れて False になるため、`outKeepWork=True` が立って `%TEMP%\nxocr_*` が丸ごと残る。修正前は消えていた。1回あたり数十MB。
  **裁定**: 「止める必要が無かった(既に居ない)」を成功側に倒す。契約コメントも実装に合わせる。
- **F21 [MAJOR] W4-6 の1秒閾値が、W2-2 が守ろうとした《冷えたVPN復帰》を撃ち抜く** (C)
  `modShareRule.bas:216-219`。B10 の救済は「構文起因だから即座に返る」を前提にしているが、SMB セッション未確立(VPN直後・スリープ復帰)では `GetAttr` が数秒かかる。`elapsedMs > 1000` で再試行が抑止され、正しく設定された共有が「到達不能」に確定する。**さらに W2-2 の `reachableNow=False` へ連鎖し、`TouchReach` 未実行のまま `ExpiryDecision` が "wipe" を返しうる**(既定 `knowledge_expire_days=0` なので opt-in だが、共有機能そのものは既定で全滅する)。
  **裁定**: 閾値を「観測で分けられる幅」(数十秒＝OSタイムアウト級)にするか、時間 AND エラー番号の両方が構文側を指したときだけ抑止する。**`modGuard` 側は `Reachable()` の False を「未確認」として扱い、判定不能では消さない側へ倒す**。

## Fix波3: テスト・文言・記録

- **F22 [MAJOR] W6-1 の純関数4本が一度もテストされず、称号行の解析経路も走っていない** (D)
  `BoardBodyText` / `BoardHeadLine` / `BoardStateText` が呼ばれておらず、`BoardReadRows` に渡す `td` が **Nothing のまま**なので `"T"`(称号)行の解析が1度も走らない。`modTestsPure34` は**残45字**で1本も足せない。
  **裁定**: `modTestsPure36` を新設(`modTestRunner`/`vba_lint`/`run_lo_tests`/`modules.json` の4点セット登録)。往復ゴールデンを1本、`td` は実 Dictionary を渡す。
- **F23 [MAJOR] SKIP に天井が無く「PASSの水増し」を「集計からの消去」に置き換えただけになる余地** (D)
  `run_lo_tests.py:956` は FAIL しか見ておらず、`[SKIP]` を貼れば PASS にも FAIL にも現れず exit 0 のまま。旧来の水増しは件数増で気付けたが、新方式は**件数が減るだけなので機械は何も言わない**。
  **裁定**: SKIP の期待値(12)をベースラインとして持ち、超えたら FAIL にする。PASS 件数の下限ラチェットも同じ場所に置く。
- **F24 [MAJOR] DoD 第8項が未達のままラウンドが閉じかけている** (D)
  仕様は「条件付き書式が UsedRange を膨らませないことをテストで固定する」を DoD に入れたが、実装は実行時の自己検算に置き換え、**その事実がどこにも記録されていない**。8ラウンド溶かした問題の成立条件が自動検査の外にある。
  **裁定**: DoD 8 を「**実機スモークの確認項目へ移送**」と明示的に裁定し直し、HANDOFF の実機第18報チェックリストへ入れる。診断画面に `backdrop_cf` / `backdrop_cf_failed` の直近1行を出す。
- **F25 [MAJOR] 波1の申し送り2件が宙に浮いている** (D)
  `modTestsPure22`(2件) と `modTestsPure19`(6件) は「模擬しか通らず実装をどう改変しても落ちない」とテスト自身が明記しているが、spec にも TODO にも回収先が無い。**次ラウンドの実装者には「回帰テストがある」と見える**。
  **裁定**: テスト名の接頭辞に `[MODEL]` を付けて「これは模擬であって回帰検知ではない」と明示し、TODO へ宿題として記録する。
- **F26 [MAJOR] 容量裁定表から最逼迫3本が漏れていた** (B)
  実測で `modSkin` **残27** / `modApp` **残36** / `modUINexusDraw` **残37**。仕様の容量裁定表に無い。R33 では誰も触らなかったので事故は起きていないが、**次に1行足した瞬間に上限を割る**。
  **裁定**: CLAUDE.md と HANDOFF の容量記述を実測値へ更新する。
- **F27 [MAJOR] 4バイト読むために ADODB.Stream がファイル全体をメモリへ読む** (A)
  `modShelfScan.bas:118-121`。`LoadFromFile` はファイル全体を読み込む。しかも VBA は引数を先に評価するので**拡張子が対象外でも必ず呼ばれる**。PDF 取込経路(`modExtractorPdf.bas:100` が Word の Extract を PDF パスで呼ぶ)では、判別不能へ落ちると分かっているのに**その前に PDF 全体をメモリへ読む**。32bit Excel で数百MBの PDF は OOM 域。
  **裁定**: (a)拡張子判定を先に通し、対象拡張子のときだけ読む (b)`Open For Binary` + `Get` の部分読みへ置き換える(`modBackdrop.WriteBmpFile` に前例)。
- **F28 [MINOR] 利用者向けFAQに `admin_users` というキー名が降りた** (D)
  `build_mybookshelf.py:1233`。手順は書かれていないので BLOCKER 条件には当たらないが、📊利用状況は「匿名を約束して集めた投書の全文」を出す画面。**一般利用者向けページから管理者権限の鍵の名前を消す**(「運営の権限がある端末に出ます」で用は足りる)。
- **F29 [MINOR] 赤い🗑ボタンが2つ隣り合い、破壊規模の桁差が視覚で区別できない** (D)
  `modKnowledgeBar.bas:355-366`。左は「部門ぶん一括」、右は「選択中の1件」。
  **裁定**: 字形かキャプションで規模差を語で示す(文字列変更1行)。
- **F30 [MINOR] 専門家召喚の宛先ハッシュが送信側だけ `SanitizeId` を通している** (C)(D)
  `modMentor.bas:497-498` 対 `:215`、`modBoard.bas:472` の称号キーも同型。CN のエスケープが残す `\` や64字超で不一致になり、**「送りました」が嘘になる**/称号が誰にも出ない。
