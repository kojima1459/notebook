# Nexus Agent — エッジケース・既知の罠カタログ

このプロダクトは複数回の監査(UI/UXレッドチーム・SRE/カオスエンジニアリング
監査・Endgameバグバウンティ監査)を経ている。ここではそれらで発見・対処した
エッジケースを、**再発防止のチェックリスト**として整理する。新機能追加時は
該当する項目に抵触しないか確認すること。

凡例: ✅=対処済み(コードに実装済み) / ⚠️=運用でカバー(コード対処なし・
既知のリスクとして許容) / 🔲=未対応(`docs/dev/TODO.md`参照)

## 1. VBA/Windows/Excel環境固有の罠

### 1.1 符号付きLong(32bit)の最上位ビット
**症状**: VBAのLong型は全て符号付き。bit31が1になった瞬間に負値化し、
ビットカウント(popcount)処理で単純なループがオーバーフロー/論理バグを
起こす。

**対処 ✅**: `modBitwiseOpt.PopcountLong`は「符号ビット(bit31)を先に+1で
数え、残り0〜30bitをバイト単位のルックアップテーブルで数える」符号安全
実装。Pythonリファレンス実装とdim768/1536/3072・全正/全負/bit31境界で
突き合わせ検証済み(オフライン)。

### 1.2 32/64bit環境でのAPI宣言(`Declare`/`PtrSafe`)
**症状**: Windows API呼び出し(`Sleep`等)は32bit/64bit Officeで宣言が
異なり(`PtrSafe`/`LongPtr`)、片方でしか動かないコードになりがち。

**対処 ✅ — 原則ゼロ、唯一の例外あり(2026-08-05更新)**: 本プロダクトは
`Declare`文を使わない方針を徹底している。時間待機(`WaitMs`/`MentorWait`等)は
`Timer`関数+`DoEvents`ループで実装しており、32/64bit環境依存が原理的に
発生しない。

**唯一の例外(R16-2b・`src/ui/modWorkExcel.bas`)**: 取込・入念な質問応答の
長時間ブロック中、DWM(デスクトップウィンドウマネージャ)が約5秒で
「応答なし」と判定し画面を白くゴースト化する現象を抑止するため、
`user32.DisableProcessWindowsGhosting`だけを例外的に許可する。この例外は
以下をすべて満たす場合に限る(この4条件を満たさないAPIを追加したい場合は、
例外を広げる前に司令塔の裁定を仰ぐこと):
- **表示系**(画面の見え方だけに影響し、データ・業務ロジックには一切触れない)。
- **引数なし・戻り値なし**(`void DisableProcessWindowsGhosting(void)`)。
  型のミスマッチや呼び出し規約の違いによる実機クラッシュの余地が無い。
- **user32.dll限定**(Windows全版に存在する最古参APIの1つ。廃止・署名変更の
  リスクが実質無い)。
- 呼ぶと**プロセス終了まで解除不能**という公式の既知の制約があるため、
  `config freeze_keep_banner`(既定on)でオプトアウトできるようにしている。

宣言は`#If VBA7 Then / Private Declare PtrSafe Sub ... / #Else /
Private Declare Sub ... / #End If`の32/64bit両対応形式で書く(本製品は
32bit実機前提だが、宣言自体は64bit Officeでも構文的に安全な形にしておく)。
2026-08-05の実験で、この宣言を含む`modWorkExcel.bas`が
`tools/run_lo_tests.py --mode compile`(LibreOffice構文チェック)を
通過することを確認済み(`#If VBA7 Then`分岐込みでコンパイルできることを
本モジュールで新規に検証した)。

### 1.3 LibreOffice構文チェッカーの罠(実機Excelでは無害・LOでのみ問題)
本番はWindows Excelのみが対象だが、CI相当の静的検証にLibreOfficeの構文
コンパイルチェックを使っている(`tools/run_lo_tests.py`、実行はしない・
構文のみ)。以下はLO特有の罠で、`tools/vba_lint.py`が自動検出する:

- `base`を識別子(変数名・引数名)に使うとStarBasic予約語(Option Base)と
  衝突し、**LOの構文チェックが沈黙ハングする**(実機Excelでは合法)。`rem`も
  同様にコメント扱いされて破綻する。✅ lint検出。
- 文字列リテラルの末尾に`\`を置く(`"foo\"`)とLOのトークナイザがハングする。
  ✅ lint検出。
- モジュールレベルの`Dim`宣言はプロシージャより前に書く必要がある(実機
  コンパイルエラー)。✅ lint検出。
- 変数/引数名が同一モジュール内のプロシージャ名と衝突すると実機コンパイル
  エラー(大文字小文字区別なし)。実例: `modBitwiseOpt.Prefilter`の引数名
  `prefilterN`が関数名`PrefilterN`と衝突しビルド時に検出・`poolN`へ改名
  (コミット履歴参照)。✅ lint検出。
- `ReDim x(0 To -1)`(負のサイズ)は実機実行時エラーだがLOは通してしまう。
  ✅ lint検出、件数ガードを徹底。
- 1モジュールあたり約30,000字の上限(実機VBAの制約)。✅ lintで検出、
  `docs/dev/CONTRIBUTING.md`のガイドで新規モジュール分割の目安を明記。

### 1.3b MsgBox/InputBox/Application.StatusBarは非BMP文字(絵文字サロゲートペア)を描けない
**症状**: `ChrW(&HD8xx)`+`ChrW(&HDCxx〜DFxx)`の組で作る非BMP文字(🗔🩺🔄等の
絵文字)は、Shape(TextFrame2)・セル値では正しく描けるが、ネイティブ
`MsgBox`/`InputBox`(Win32の旧来ダイアログ)と`Application.StatusBar`では
サロゲート1単位ごとに「?」化ける(2文字ぶんで「??」)。VBEへのUTF-8→CP932
注入で化ける§1.3の問題とは**別の問題**(こちらは実行時の描画限界)。

**発見済みの実インスタンス(2026-08-05調査・R18-6aで修正済み)**:
- `optOcrEta.OcrConfirmAskFor`(🗔)→`modShelfVision.bas`のMsgBox
- `modLog.FriendlyMessage`のE0201(🩺)/E0204(🔄)/E0705(🔄・予防)→
  `optDiffDoc.bas`のMsgBoxほか
- `modShelfSync.SyncNow`のcapped完了サマリ(🔄)→同モジュール内のMsgBox

**対処 ✅(該当5箇所は絵文字除去・「」括弧表記へ統一)/ ⚠️(StatusBar系は
`Application.DisplayStatusBar=False`が起動直後から常時かかっており実害なしと
判断・§4-3により将来DisplayStatusBar制御を変える際は要再点検)**:
MsgBox/InputBoxへ**文字列リテラルで直接**絵文字を書かない(既存MASTER_SPEC
§12のルール)だけでは不十分だった。**関数の戻り値経由**(`FriendlyMessage`
のように複数の消費先を持つ共通関数)で絵文字が紛れ込むケースがすり抜けて
いたため、「MsgBoxに渡りうる文字列を組み立てる関数は、その関数の本体全体
(呼ばれ方に関わらず全Case分岐)で非BMP ChrWを禁止する」という運用ルールを
追加した(検査15・`tools/vba_lint.py`の許可リスト方式。§2.2は誤検知ゼロ
優先のため呼び出しグラフ追跡はしない=直書き検出+許可リスト関数の全分岐
検査の組合せ)。

### 1.4 MAX_PATH(260文字)制限
**症状**: 深い共有フォルダ階層(`\\host\部\課\チーム\Nexus_Share\...`)配下に
生のユーザー名(最大64字、`SanitizeId`後)を含むファイル名を置くと、
`thx_<64字>_<nonce>`のような合成で合計パス長が260字を超え、`Dir`/`Kill`/
`ADODB.Stream.SaveToFile`(いずれも非Long-Path対応API)が失敗する。

**対処 ✅**: P2Pファイル名に載せるID成分は全て`Fnv1a64Hex`(16桁固定)で
圧縮し、生のユーザー名を使わない。payload(ファイル中身)側には引き続き
生IDを保持し、受信側の照合ロジック(`StrComp`)は壊さない。最悪ケースの
文字数試算は `docs/dev/ARCHITECTURE.md` §5参照。

### 1.5 アンチウイルスによる一時ファイルロック(実行時エラー70等)
**症状**: 共有フォルダへファイルを書いた直後、Windows Defender等が
数百ms〜1秒程度ファイルを掴み、直後の読み書き/削除が失敗する。

**対処 ✅**: 全P2P I/O(`modP2P`/`modMentor`/`modBoard`/`modAnalytics`)が
最大3回・250ms刻みバックオフの`WriteUtf8Retry`/`ReadUtf8Retry`/`KillRetry`
系ヘルパーを持つ。待機は`DoEvents`ループでUI応答性を保つ。
**並行GC耐性**: 複数ユーザーが同時に同じ投票/感謝状ファイルをGCすると、
後着の`Kill`が「ファイルが既に無い」(error 53)で失敗する。`KillRetry`は
削除前に`Dir()`で存在確認し、「既に無い=削除目的は達成」として即成功扱いに
することで、無駄なリトライ待機(最大1.5秒×ロック保持)を回避している。

### 1.6 マクロ無効での起動(壊れたUIを見せない)
**症状**: マクロを無効化して開かれると`Workbook_Open`が一切発火せず、
本来Shapeで隠されるはずのExcelネイティブUI(数式バー等)がそのまま
見えてしまう("Windows 95感"の最悪パターン)。

**対処 ✅**: `はじめにお読みください`シートを先頭・可視・アクティブ状態で
ビルドに焼き込み、マクロ有効化を促す案内を常設。起動(`modBoot.Boot`)が
成功したときだけこのシートを非表示化する(`HideGuardSheet`)。アクティブ
シートは非表示化できない仕様のため、隠す前に別の可視シートへ
フォーカスを移してから隠す。

### 1.7 セル編集モード中の全マクロ停止
**症状**: ユーザーが誤ってセルをダブルクリック/F2で編集モードに入ると、
Excelの仕様上すべてのVBAマクロが一時停止する。この間にタイマー同期や
API応答が来ると処理が詰まる。

**対処 ✅(選択制限+park方式)**: `ws.EnableSelection = 1`(xlUnlockedCells)
+ 全アクション完了時のフォーカスpark(`modUI.ParkFocus`)を併用し、
編集モードへの偶発的な進入機会自体を減らす。完全なシート保護
(`Protect`)は、Shape再描画のたびにUnprotect/Protectが必要になり
描画失敗時に保護状態が壊れるリスクがあるため不採用(オーナー承認済み判断)。

### 1.8 別ブック誤爆(ActiveWorkbook/ActiveSheetの暗黙参照)
**症状**: ユーザーがNexusを開いたまま別の業務Excelを操作している間に
Toast通知やタイマー処理が発火すると、`ActiveSheet`ベースの描画が
他人の業務ファイルにShapeを生成/選択状態を破壊する恐れがある。

**対処 ✅**: `modSkin.ShowToast`と`modUI.ParkFocus`の冒頭で
`ActiveWorkbook Is ThisWorkbook`を検証し、自ブックがアクティブでなければ
即座に何もせず終了する。

**監査所見(対処不要と判定)**: 自動同期(`modShelfSync`のOnTimeタイマー)は
`ActiveSheet`/`ActiveWorkbook`への参照が一切無い(全てThisWorkbook経由の
明示参照)ため、別ブック誤爆のリスクは無い。

### 1.9 画面暗転ロックアウト(ScreenUpdating=Falseで固まる)
**症状**: `Application.ScreenUpdating = False`で描画を開始した直後に
予期しないエラーが起きると、`= True`に戻す行へ到達できず、画面が
真っ黒に固まったまま操作不能になる(非エンジニアには「壊れた」としか
見えない)。

**対処 ✅(二重の安全網)**: (1) 全アクションの唯一の出口`modUiLock.Leave`が
無条件で`ScreenUpdating = True`を実行する(個々のハンドラが復帰を
忘れても、この関所で必ず戻る)。(2) `modBoot.Boot`正常終了時にも明示的に
復帰させる(起動シーケンス自体はロックの外で動くため)。`ToggleTheme`のような
ロック非経由の単発処理は個別に`On Error Resume Next`で包んでいる。

### 1.10 32bit Excelのメモリ制約とShape増殖
**症状**: チャットバブルや投票/バッジ等のShapeを無制限に生成し続けると、
32bit版Excel(社内標準)のメモリ上限に到達しクラッシュする。

**対処 ✅**: `modUI.CapBubbles`が`MAX_BUBBLES`(40件)超過時に古い順で
間引く。フローティング・アクションバーはバブル毎に個別ボタンを生成
せず、画面上部に1セットだけ常設(§ARCHITECTURE 3.2参照)。

## 2. RAG/データ整合性のエッジケース

### 2.1 埋め込み次元の不一致
**症状**: `mock_llm`切替等で異なる次元の埋め込みモデルに切り替わると、
保存済みベクトルと質問ベクトルの次元が食い違い、`DotProduct`が誤った
0点をランキングに混入させる(サイレント劣化。エラーにならない)。

**対処 ✅**: `modRetrieve.Search`/`SearchExpanded`は次元不一致を検出したら
そのチャンクをスキップし、`modLog.LogError "E0702"`へ1回だけ記録する
(同一検索内での重複ログは抑制)。

### 2.2 ナレッジ0件・検索結果0件
**対処 ✅**: Vaultギャラリーは0件時に「透かしアイコン+誘導文+緑CTA」の
Empty Stateを表示(単なる空白にしない)。検索経路自体は0件を正常系
として扱い(呼び出し側=`modAsk`の責務)、資料追加を促す案内を返す。

### 2.3 プロンプト本文の打ち切り
**対処 ✅**: `modPrompts.BuildSourceBlock`が`max_context_chars`(既定
40000字)を超える手前で打ち切り、打ち切った場合のみ末尾に
「(一部省略)」を挿入する(打ち切っていないのに省略表記が付く誤表示を防ぐ)。

### 2.4 P2Pファイル名/照合キーのサニタイズ漏れ(実バグ・修正済み)
**症状(発見時の実バグ)**: 感謝状ファイル名`thx_<author>_<nonce>`の
`author`部分が一時期サニタイズ前の生値で、Windowsファイル名禁止文字
(カンマ・コロン等)を含む作者名だとファイル作成が失敗し、感謝EXPが
永久に届かなかった。

**対処 ✅**: 送信側は宛先キーを`SanitizeId`してからファイル名・payload両方に
使用し、受信側の`Dir()`前方一致パターンも同じ関数で生成した文字列で
揃える(綴りの非対称を排除)。

## 3. ガバナンス・不正防止のエッジケース

### 3.1 EXPの自己申告不正
**症状**: 「自分で自分の投稿にいいねを押す」ような自己申告系の加点は、
バッジ・称号目当ての虚偽報告を誘発する。

**対処 ✅**: 感謝EXP(`thanks_received_total`)は**P2Pで他者から感謝状を
受信した時のみ**加算される設計。自分宛の感謝状を自分で送ることは
`EmitThanks`内で「自分自身には送らない」ガードにより不可能。称号
(💡🌟)・スキン解放(サクラ/オーシャン/ゴールド)はこの`thanks_received_total`
のみを条件にしており、自己申告経路を持たない。

### 3.2 ノイズ投票の水増し
**対処 ✅**: `(reporter_hash, source_hash)`の組で1ファイルのため、同じ人が
同じ資料に何度報告してもファイルは上書きされるだけ(投票数=一意な
報告者数=ファイル数、という不変条件が保たれる)。

### 3.3 Toast EXPバグバウンティ(ご意見箱)の連打稼ぎ
**対処 ✅**: `modHelp.OnFeedback`のEXP付与は`fb:yyyymmdd`キーで1日1回に
制限。空メール連打によるEXP稼ぎを防止。

### 3.4 週次サマリーの「空虚な自慢」
**対処 ✅**: `modBoard.ShowWeeklySummary`は先週の合計節約時間が0の場合、
何もToast表示しない(何もしなかった週に褒め言葉を出すと白々しく信頼を
損なうという判断)。

## 4. UI/UX状態管理のエッジケース

### 4.1 グローバル変数の揮発(強制終了・クラッシュ時)
**対処 ✅**: AD由来ユーザーIDのキャッシュ(`modP2P.mUserIdCache`)、
会話モード・言語設定・直近2往復の会話履歴(`ui_state`シート)は、
モジュール変数ではなく都度シートへ退避/復元する設計。強制終了しても
次回起動時に会話が「📜前回の回答」として薄く復元される
(`modApp.RestoreLastConversation`)。

### 4.2 多重発火・連打(Re-entrancy)
**対処 ✅**: `modUiLock`によるグローバルロック(§ARCHITECTURE 3.4)。加えて
`modAsk.mAsking`/`modShelfSync.mSyncRunning`など機能固有の再入防止フラグが
存在し、いずれも異常系(エラー発生時)でも確実に解除される
(`On Error`ハンドラ内でフラグリセットを行うパスを監査済み)。
`mSyncRunning`は加えて時間切れガード(`GUARD_EXPIRY_MIN`)を持ち、
何らかの理由でフラグが解除されないまま放置されても一定時間後に
自動的にロックが失効する。

### 4.3 孤児Shape(削除漏れによる蓄積)
**対処 ✅**: 再描画系の関数(`RenderCitations`/`ClearMentor`/
`RenderGalleryCards`等)は描画の**先頭**で必ず同名/同接頭辞のShapeを
`Delete`してから再生成する。Empty State用Shape(`nxg_empty_*`)も
`RenderGalleryCards`の掃除対象に含めている。

## 5. 「読みにくい」を生まないための設計判断

### 5.1 Markdown記号はこの画面では装飾されない
**背景**: 本UIはExcel Shapeへのプレーンテキスト描画であり、`##`や
`**太字**`のようなMarkdown記号は**そのまま記号として表示され**、
むしろ視認性を損なう(旧V2の「読みにくさ」の一因と分析)。

**対処 ✅**: LLMへのシステム指示(`modPrompts.StyleInstruction`)で
Markdown記号を明示的に禁止し、代わりに`■`見出し/`・`箇条書き/`【】`強調
というプレーンテキスト記法を強制している。
